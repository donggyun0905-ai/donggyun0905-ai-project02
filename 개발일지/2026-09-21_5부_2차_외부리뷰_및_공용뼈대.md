# 5부 — 애플리케이션 공용 뼈대 5종 + 외부(Opus) 리뷰 2차례 반영

날짜: 2026-09-21
관련 커밋: `017d390`, `7a67080`

## 1. 개요

4부까지는 "데이터 쪽"(스키마·DTO·DAO) 검증이었다. 이 문서는 "애플리케이션 쪽" 공용 뼈대 5가지를 새로 만든 과정과, 그 전후로 Claude Opus(웹)에게 외부 코드 리뷰를 두 차례 받아 실제로 검증하고 반영한 내용을 다룬다.

## 2. 프롬프트 인젝션 오인 해프닝

1차 Opus 리뷰 결과가 이 세션에 전달됐을 때, 메시지가 `CLAUDE.md` 파일 내용을 그대로 인용하는 시스템 안내문처럼 포장돼 있었고, 끝에는 "DAO가 바뀌면 프로젝트를 다시 올려주세요. 같은 방식으로 재생성해 드리겠습니다" 같은 지시성 문구가 섞여 있었다. 실제 `claude.md` 파일을 다시 읽어 대조한 결과 해당 "문서화하다가 발견한 것" 섹션은 파일에 없었고, 언급된 "문서 5절"도 저장소 어디에도 없어 프롬프트 인젝션 가능성을 의심하고 사용자에게 출처를 직접 물었다. 사용자가 "Opus로 웹에서 코드를 압축해 리뷰받은 것"이라고 확인해줘서 해프닝은 정리됐지만, 메시지에 포함된 지시문 자체는 따르지 않고 기술적 내용만 코드를 직접 읽어 하나하나 검증하는 방식으로 진행했다.

## 3. 공용 뼈대 5종 (커밋 `017d390`)

## 4. 2차 리뷰 — 방금 만든 뼈대 자체의 결함 (커밋 `7a67080`)

5종 뼈대를 만든 뒤 다시 Opus 리뷰를 받았고, 뼈대 자체와 3부에서 만든 DAO 일부에서 추가 문제가 나왔다. 전부 코드를 직접 읽어 실재를 확인한 뒤 수정했다.

### 🔴 TransactionUtil이 RuntimeException을 놓쳐 부분 커밋이 발생하는 문제

- **문제**: `TransactionUtil.runInTransaction()`이 `catch (SQLException e)`만 잡고 있었다. 람다 안에서 `NullPointerException` 같은 `RuntimeException`이 나면 이 catch를 건너뛰고 바로 `finally`의 `conn.setAutoCommit(true)`로 간다.
- **왜 문제인가**: JDBC 스펙상 트랜잭션 도중 `setAutoCommit(true)`를 호출하면 그 시점까지의 작업이 **묵시적으로 커밋**된다. 즉 트랜잭션 중간에 런타임 예외가 나면 "실패했는데 절반은 저장되는" 상태가 된다. 실제로 터질 수 있는 구체적 경로도 있었다: `GapAnalysisItemDao.insert`가 `pstmt.setLong(2, item.getSkillId())`를 직접 호출하는데, `skill_id`가 `Long`(boxed) 타입이라 null이면 언박싱 과정에서 NPE가 난다. 이 상태로 여러 항목을 반복 삽입하다 하나라도 null이면, 앞서 커밋된 `GAP_ANALYSIS` 헤더는 남고 항목(`GAP_ANALYSIS_ITEM`)은 일부만 남는 불완전한 분석 결과가 생길 수 있었다.
- **수정**: `catch (SQLException | RuntimeException e)`로 확장해 두 경우 모두 롤백하도록 수정. `GapAnalysisItemDao.insert`도 `pstmt.setLong` 대신 `setNullableLong` 헬퍼로 바꿔, null이 오면 NPE가 아니라 DB의 `NOT NULL` 제약 위반(`SQLException`)으로 깨끗하게 실패하도록 했다 — 이러면 이제 `TransactionUtil`이 제대로 롤백해준다.
- **검증**: `TransactionUtilTest`를 새로 작성해 (1) 람다에서 `RuntimeException`을 던지면 앞서 넣은 행이 실제로 남지 않는지, (2) 정상 흐름은 실제로 커밋되는지 둘 다 실제 DB(`USERS`→`USER_SPECS` 부모/자식 관계)로 검증했다.

### 🟠 LLM 연동 전에 고쳐야 했던 것

- **타임아웃 고정 10초**: 워크넷 같은 일반 API에는 충분하지만 LLM 응답(로드맵 생성, 직무 요약 등)은 10초를 넘기는 경우가 흔해 붙이자마자 호출이 실패할 수 있는 구조였다. `get`/`postJson`에 `Duration timeout`을 받는 오버로드를 추가해 호출별로 조정할 수 있게 했다(기본값 10초는 유지).
- **예외 메시지에 URL 쿼리스트링 노출**: 워크넷 API는 인증키를 `authKey=...` 형태로 URL 쿼리에 싣는데, 호출 실패 시 `ExternalApiException` 메시지에 URL 전체가 그대로 들어가 있어 로그에 키가 남을 위험이 있었다(`claude.md`의 "API 키를 소스에 하드코딩하지 않는다" 취지 위반). `maskQuery()`를 추가해 `?` 이후를 잘라내고 경로까지만 메시지에 남기도록 수정.

### 🟡 작지만 지금 넣어두면 좋은 것

- **ExternalApiException에 상태 코드 없음**: 메시지 문자열에만 있어 429(잠시 후 재시도)와 400(요청 자체가 틀림)을 구분할 수 없었다. `statusCode` 필드를 추가(HTTP 응답 실패가 아니면 -1)해 FR-111의 재시도 버튼 표시 여부를 코드로 판단할 수 있게 했다.
- **footer.jsp 인코딩 선언 없음**: JSP는 페이지 인코딩 선언이 없으면 소스를 ISO-8859-1로 읽는다. 당장은 한글이 주석에만 있어 문제가 없었지만, 사이드바에 실제 한글 콘텐츠가 들어가는 순간 깨질 상황이었다. 파일마다 개별적으로 선언을 넣는 대신 `web.xml`에 `<jsp-config><jsp-property-group>`으로 `*.jsp` 전체에 `page-encoding=UTF-8`을 한 번에 지정하는 방식을 택했다(향후 2주차에 JSP가 많아져도 누락될 일이 없도록).

### 검증

- 로컬 목 HTTP 서버(`com.sun.net.httpserver.HttpServer`, JDK 내장이라 추가 의존성 없음)를 띄워 429 응답과 연결 실패(포트 미개방) 두 시나리오를 각각 테스트, `statusCode`가 올바르게 담기고 예외 메시지에 인증키가 남지 않는 것까지 확인했다.
- 모든 수정 후 `mvn test` 기준 **42/42 통과**(4부의 36개 + 5부 신규 6개: TransactionUtilTest 2개, ExternalApiClientTest 4개).
- Tomcat에 다시 배포해 `/share/abc123`을 비로그인 상태로 요청했을 때 `/login`으로 리다이렉트되지 않고 **진짜 404**로 응답하는 것을 확인 — SessionFilter 화이트리스트에 `/share/`가 정상적으로 반영됐음을 실증했다.

## 5. 이번에 손대지 않은 것 (의도적으로 보류)

리뷰에서 함께 언급됐지만 이번 범위에 포함하지 않은 것들 — 2주차 담당자가 실제 기능을 만들 때 처리해야 한다:

- **UPSERT 메서드 부재**: DAO 어디에도 `ON DUPLICATE KEY UPDATE` 같은 upsert 로직이 없다. `JOB_REQUIRED_SKILL`처럼 복합 UNIQUE가 걸린 테이블에 워크넷 재수집 배치를 동일 키로 두 번 돌리면 중복 키 에러가 난다. 실제 배치 로직을 만드는 사람이 필요한 형태로 구현하는 게 맞다고 판단해 보류.
- **USER_SCORE_SUMMARY가 가입 시 생성되지 않음**: DAO 클래스 주석에는 "회원가입 시 1행 생성"이라고 적혀 있지만, 실제로 `UserService.register()`는 `USERS`에만 insert하고 이 테이블은 건드리지 않는다. 점수 기능이 실제로 붙을 때 함께 연결해야 한다.
