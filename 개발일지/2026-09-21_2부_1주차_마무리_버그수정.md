# 1주차 마무리 — 보안·검증 버그 수정 및 CRUD 완성

날짜: 2026-09-21
범위: `2026-09-21_1주차_개발일지.md`(1부)의 "6. 개선이 필요한 부분"에서 지적된 항목들을 실제로 고친 작업

## 1. 개요

1부 개발일지에서 1주차(회원/인증 + 프로필 CRUD) 코드를 리뷰하며 회원가입 검증 부재, TOCTOU 레이스 컨디션, 날짜 파싱 미처리, USER_SKILLS 중복 방지 무력화 등을 "개선 필요"로만 남겨뒀었다. 이번 작업은 2주차 진입 전에 그 항목들을 실제로 고치고, 리뷰 중 추가로 발견한 문제(세션 고정 공격, 회원 탈퇴 기능 미완성, 스펙/프로젝트/스킬 수정 기능 누락)까지 같이 정리한 것이다. 해당 커밋은 `48d7b42`.

## 2. 고친 것

### 2-1. 회원가입 입력 검증 부재

- **문제**: `RegisterServlet`이 `loginId`/`password`가 비어 있거나 지나치게 길어도 그대로 `UserService.register()`로 넘겼다. 서버 쪽에 길이·필수값 검증이 전혀 없었다.
- **왜 문제인가**: HTML `required` 속성은 브라우저 폼에만 걸리는 클라이언트 검증이라, 직접 POST 요청을 만들어 보내면 우회된다. 빈 아이디로 가입이 되거나, 극단적으로 긴 비밀번호를 보내 PBKDF2(반복 12만회) 해시 비용을 늘리는 것도 가능했다.
- **어떻게 고쳤나**: `UserService`에 `InvalidInputException`을 추가하고 `register()` 진입부에서 검증한다.
  - `loginId`: trim 후 1~50자(USERS.login_id가 VARCHAR(50)이라 컬럼 길이에 맞춤)
  - `password`: 8~100자 (최소 길이는 통상적인 보안 기준, 최대 길이는 과도한 해시 비용 방지)
  - `RegisterServlet`은 기존 `DuplicateLoginIdException`과 같은 방식으로 `InvalidInputException`을 잡아 `signup.jsp`에 에러 메시지로 표시한다.

### 2-2. 아이디 중복 체크 TOCTOU 레이스 컨디션

- **문제**: `existsByLoginId()`로 확인한 다음 별도로 `insert()`를 호출하는 구조라, 두 요청이 동시에 같은 아이디로 가입을 시도하면 둘 다 `existsByLoginId()`를 통과해버릴 수 있었다.
- **왜 문제인가**: 이 경우 두 번째 `insert()`가 DB의 `UNIQUE(login_id)` 제약을 위반해 `SQLException`이 발생하는데, `RegisterServlet`은 이를 `DuplicateLoginIdException`으로 잡지 못해 그대로 500 에러로 노출됐다.
- **어떻게 고쳤나**: `UserService.register()`의 `insert()` 호출부를 try-catch로 감싸 `SQLIntegrityConstraintViolationException`(UNIQUE 위반 시 MySQL 드라이버가 던지는 구체적 SQLException 서브클래스)을 `DuplicateLoginIdException`으로 변환한다. `existsByLoginId()` 사전 체크는 그대로 두되(응답 속도상 대부분의 경우 여기서 걸러짐), DB의 UNIQUE 제약을 최종 방어선으로 삼는 이중 구조가 됐다.

### 2-3. 로그인 세션 고정(Session Fixation) 공격

- **문제**: `LoginServlet`이 로그인 성공 시 기존 세션 ID를 그대로 쓴 채 `loginUser`만 세션에 심었다.
- **왜 문제인가**: 공격자가 피해자에게 자신이 미리 발급받은 세션 ID(쿠키)를 심어두고, 피해자가 그 세션으로 로그인하게 유도하면, 공격자는 로그인 전부터 알고 있던 그 세션 ID로 로그인 후 세션에 접근할 수 있다(세션 고정 공격).
- **어떻게 고쳤나**: `LoginServlet.doPost()`에서 인증 성공 직후, `loginUser`를 세션에 저장하기 전에 `req.changeSessionId()`를 호출해 세션 ID를 새로 발급한다. Jakarta Servlet 표준 API라 별도 의존성 없이 처리됨.

### 2-4. 날짜/숫자 파싱 실패 시 500 에러

- **문제**: `ProfileSpecServlet`(`acquiredDate`), `ProfileProjectServlet`(`startDate`/`endDate`), `ProfileServlet`(`desiredJobId`), `ProfileSkillServlet`(`userSkillId`) 등에서 `LocalDate.parse()`/`Long.valueOf()`가 잘못된 형식의 입력에 대해 각각 `DateTimeParseException`/`NumberFormatException`을 던지는데, 이를 잡는 catch 블록이 없어 그대로 컨테이너까지 전파되어 500 에러(스택트레이스 노출)로 이어졌다.
- **왜 문제인가**: `<input type="date">`는 정상적인 브라우저 사용에서는 항상 `yyyy-MM-dd` 형식을 보내지만, 폼을 거치지 않고 직접 요청을 보내면 임의의 문자열이 들어올 수 있다. 이런 경우에도 사용자에게 스택트레이스가 그대로 노출되는 건 정보 노출이자 나쁜 사용자 경험이다.
- **어떻게 고쳤나**: 4개 서블릿(`ProfileSpecServlet`, `ProfileProjectServlet`, `ProfileServlet`, `ProfileSkillServlet`) 전부 `NumberFormatException`/`DateTimeParseException`을 catch해 `HttpServletResponse.SC_BAD_REQUEST`(400)로 응답하도록 통일했다. 동시에 `title`/`rawInput`처럼 필수 텍스트 필드의 공백 여부도 서버에서 한 번 더 검증하도록 추가했다(HTML `required`를 우회하는 직접 요청 대비).

### 2-5. USER_SKILLS 기술명 중복 등록 가능

- **문제**: `sql/01_schema.sql`의 `USER_SKILLS`에는 `UNIQUE(user_id, skill_id)` 제약이 있지만, 1주차에는 임베딩 매칭 배치가 없어 `skill_id`가 항상 NULL로 들어간다. MySQL은 UNIQUE 제약에서 NULL을 서로 다른 값으로 취급하므로, 이 제약이 사실상 무력화되어 같은 `raw_input`(예: "Python")을 여러 번 추가해도 막히지 않았다.
- **어떻게 고쳤나**: 스키마를 건드리지 않고(`claude.md`의 "스키마 임의 변경 금지" 원칙 유지) `UserSkillDao`에 `existsActiveRawInput()`을 추가해 `raw_input`을 대소문자·공백 무시하고 비교하는 애플리케이션 레벨 중복 체크를 넣었다. `ProfileService.addSkill()`/`updateSkill()`에서 insert/update 전에 이 체크를 거치고, 중복이면 `ProfileService.DuplicateSkillException`을 던져 `ProfileSkillServlet`이 409 Conflict로 응답한다. (완전한 동시성 방어는 아니고 check-then-insert 방식이라 미세한 레이스는 남아있지만, 계정 무결성과 달리 데이터 품질 문제라 이 정도로 충분하다고 판단.)

### 2-6. 회원 탈퇴 기능 미완성

- **문제**: `UserDao.softDelete()`는 이미 구현돼 있었는데, 이걸 호출하는 서블릿이 어디에도 없어서 죽은 코드로 남아 있었다.
- **어떻게 고쳤나**: `UserService.withdraw(userId, rawPassword)`를 추가해 비밀번호 재확인 후 `softDelete()`를 호출하도록 하고, 새 서블릿 `AccountServlet`(`/profile/withdraw`, `SessionFilter` 보호 대상)을 만들어 연결했다. `profile.jsp` 하단에 비밀번호 입력 + 브라우저 `confirm()` 확인창이 있는 탈퇴 폼을 추가했다.

### 2-7. 스펙/프로젝트/기술스택 수정(Update) 기능 누락

- **문제**: `USER_SPECS`, `USER_PROJECTS`, `USER_SKILLS` 전부 Create/Read/Delete는 있었는데 Update가 없었다 — "CRUD"라고 부르기엔 한 글자가 비어 있었다.
- **어떻게 고쳤나**: `UserSpecDao`/`UserProjectDao`/`UserSkillDao`에 각각 `update()` 메서드를 추가했다(기존 `delete()`와 동일하게 `WHERE id = ? AND user_id = ?` 조건으로 본인 소유만 갱신). `ProfileService`에 `updateSpec`/`updateProject`/`updateSkill`을 추가하고, 세 서블릿의 `doPost()`에 `action=update` 분기를 넣었다. `profile.jsp`에는 각 항목마다 `<details>` 태그(순수 HTML, JS 불필요) 안에 "수정" 폼을 넣어 클릭하면 펼쳐지는 인라인 수정 UI를 구현했다.
  - 기술스택 수정 시에는 원문(`raw_input`)이 바뀌면 기존 `skill_id`/`similarity_score`(임베딩 매칭 결과)가 더 이상 유효하지 않으므로 NULL로 초기화하도록 `UserSkillDao.update()`에서 처리한다. 다음 매칭 배치 때 다시 채워진다.
