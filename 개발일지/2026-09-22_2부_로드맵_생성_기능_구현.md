# 2부 — 로드맵 생성 기능 구현 (FR-32 · 33 · 36)

날짜: 2026-09-22
관련 커밋: `4eb0e68`

## 1. 개요

팀 역할 분담에서 ②번(로드맵 생성)을 맡아 `RoadmapService`/`RoadmapServlet`/`roadmap.jsp`를 새로 구현했다. 격차 분석(①번, 다른 담당자 기능)이 아직 없는 상태에서 어떻게 결합도를 낮춰 먼저 개발할 수 있었는지, 우선순위를 어떻게 점수화했는지, 그리고 실제로 검증하다 잡은 버그 2건을 정리한다.

## 2. ①번(격차 분석) 의존성을 어떻게 풀었나

격차 분석 담당자의 Service/Controller가 아직 없다. `RoadmapService`는 그쪽 Service를 기다리지 않고 `GapAnalysisDao`/`GapAnalysisItemDao`(이미 완성된 조회 전용 DAO)를 직접 읽기만 하도록 설계했다. DB 테이블 자체가 접점이 되는 구조라, ①번이 나중에 Service를 만들어도 로드맵 쪽 코드는 손댈 필요가 없다. 테스트·데모 데이터는 이 DAO들로 직접 넣어 "격차 분석이 이미 끝나 있다"는 상황을 흉내 냈다.

## 3. 우선순위 점수 설계

처음엔 "①자격증 → ②프로젝트 → ③스킬" 순서만 고정하려 했는데, 팀 논의 중 "부족한 항목 안에서도 뭐가 더 시급한지 순위를 매겨야 한다"는 요구가 나왔다. 스키마에 이미 있는 값으로 아래 공식에 합의했다.

| 요소 | 근거 데이터 | 배점 |
|---|---|---|
| 필수 여부 | `JOB_REQUIRED_SKILL.importance` | REQUIRED +2, PREFERRED +1, 정보 없으면 0 |
| 단계 유형 기본 순서 | FR-32의 ①자격증→②프로젝트→③스킬 | 자격증·프로젝트는 점수 경쟁에 넣지 않고 항상 1·2번 고정 (커버리지를 정량화할 매핑 테이블이 없어서) |

즉 SKILL 단계들끼리는 점수 내림차순으로 정렬되고, CERT·PROJECT는 위치가 고정이다.

## 4. 실제 생성 흐름

`RoadmapService.generate(userId)`:

1. 사용자의 최신 `GAP_ANALYSIS` 조회
2. `GAP_ANALYSIS_ITEM` 중 `status=MISSING`만 골라 위 점수로 정렬
3. `CERT` 단계: 목표 직무 카테고리에 맞고 사용자가 이미 안 가진 자격증 중 난이도 최저 1개 (`CertificationDao.findByJobCategory` 신설)
4. `PROJECT` 단계: 상위 3개 부족 기술을 언급하는 안내문 1개
5. `SKILL` 단계: 부족 기술 하나하나, 점수 순
6. 각 단계 `reason`(FR-33)은 규칙 기반 템플릿 문구로 채움 — LLM 벤더가 아직 미확정이라(`db-design.md` 남은 과제), 나중에 `util.ExternalApiClient`로 교체할 수 있는 자리만 만들어둠

필요해서 새로 추가한 DAO 메서드: `JobDao.findById`, `SkillDao.findById`, `CertificationDao.findByJobCategory`.

## 5. 검증하다 잡은 버그

### 5-1. 같은 격차분석으로 두 번 생성하면 500 에러

`ROADMAP.gap_analysis_id`가 `UNIQUE`(격차분석 1건 : 로드맵 1건, 1:1)인데, "생성" 버튼을 두 번 누르는 것처럼 같은 분석으로 `generate()`를 또 호출하면 제약 위반(`SQLIntegrityConstraintViolationException`)이 그대로 터졌다. 테스트를 작성하는 과정에서 발견했다.

**수정**: `RoadmapDao.findByGapAnalysisId` 신설. `generate()` 맨 앞에서 "이미 이 분석의 로드맵이 있는지" 먼저 확인해서, 있으면 새로 만들지 않고 대표(`is_primary`)로만 지정하고 그대로 반환하도록 바꿨다 — 중복 클릭이 나도 안전하다.

### 5-2. 부족한 기술이 많으면 끝없이 늘어남

"데이터 엔지니어처럼 요구 기술이 많은 직무면 SKILL 단계가 몇 개까지 나올 수 있냐"는 질문을 받고 확인해보니, 원래 코드는 상한이 없어서 부족한 기술 개수만큼 그대로 다 나오는 구조였다. `db-design.md`에 이미 이런 우려가 적혀 있었다 — *"한 번에 전 구간을 다 생성하면 신규 사용자에게 수십 단계가 쏟아져 오히려 이탈하므로, 현재 tier + 다음 tier까지만 노출"*.

**수정**: 상위 5개(`MAX_ENTRY_SKILL_STEPS`)까지만 `tier=ENTRY`로 노출하고, 나머지는 버리지 않고 `tier=CORE`로 저장해서 "다음 단계 미리보기"로 남긴다. `roadmap.jsp`도 ENTRY/CORE 두 섹션으로 나눠 렌더링하도록 수정 — CORE 쪽은 완료 체크 버튼 없이 회색 텍스트로만 보여준다.

## 6. 검증

- `RoadmapServiceTest` 7개: 격차분석 없을 때 예외, CERT→PROJECT→SKILL 순서·점수 정렬, 완료 체크 반영, 다른 사용자 id로는 완료 체크 안 됨, 재분석(새 격차분석) 시 버전 증가 및 이전 로드맵 대표 해제, 같은 분석으로 중복 생성 방지, 부족 기술 5개 초과 시 ENTRY/CORE 분리
- Tomcat 실배포 후 curl로 회원가입 → (격차분석 데이터 직접 시뮬레이션) → 로드맵 생성 → 화면에 순서·점수 정렬 반영 확인 → 완료 체크 반영 확인까지 HTTP 레벨로 검증
- 첫 검증 때는 `mvn test`만 돌리고 `mvn package`를 안 해서 실행 중인 Tomcat이 옛날 코드로 응답하는 해프닝이 있었다 — `target/spec-odyssey`(exploded WAR)는 `package` 단계에서만 갱신되고 `test` 단계에선 갱신되지 않는다는 걸 다시 확인
- 전체 테스트 49개 통과
- 데모 계정 2개를 만들어 브라우저에서 직접 확인 가능하게 해둠: `demo_roadmap`(간단한 5단계 예시), `demo_many_skills`(7개 부족 → 5개 ENTRY + 2개 CORE 미리보기로 갈리는 예시)
