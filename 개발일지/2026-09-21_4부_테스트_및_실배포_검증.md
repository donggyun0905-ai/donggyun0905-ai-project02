# 4부 — 테스트 인프라 도입 및 실배포 검증

날짜: 2026-09-21
관련 커밋: `118bc47`

## 1. 개요

3부(ERD 전체 스캐폴딩)에서 만든 DTO·DAO 56개는 만들어만 두고 한 번도 실행해본 적이 없었다. "뼈대만 만들어두고 검증 안 하면 의미 없다"는 문제의식으로, JUnit 5를 도입해 DAO 36개(1주차 5개 + 3부 신규 31개) 전부에 실제 DB 통합테스트를 붙이고, 로컬 MySQL·Tomcat에 직접 배포해 HTTP 레벨까지 검증했다.

## 2. JUnit 5 도입 및 DAO 통합테스트

- `pom.xml`에 `org.junit.jupiter:junit-jupiter`(test scope)와 `maven-surefire-plugin` 3.2.5를 추가했다. 기존 의존성은 건드리지 않았다.
- `src/test/java/com/specodyssey/dao/`에 DAO당 테스트 클래스 1개씩 총 36개 + 공용 헬퍼 `TestFixtures.java`(마스터 테이블처럼 DAO에 insert가 없는 경우를 위한 raw insert/hard delete)를 작성했다.
- 목(mock)을 쓰지 않고 실제 DB에 대고 insert → 조회로 값 검증, C/D 유형은 update·delete까지 확인하는 방식이다. FK가 있는 테이블은 `@BeforeEach`/`@BeforeAll`에서 부모 행(USERS, JOB 등)을 실제로 먼저 만들어 테스트했다.
- 결과: `mvn test` 기준 **36/36 통과**.

## 3. 검증 환경 구축 — Docker에서 로컬 MySQL로 전환

- 처음에는 Docker로 MySQL 8.0 컨테이너를 띄우려 했다. Docker Desktop을 실행했지만 2분 넘게 daemon이 뜨지 않았고, `docker info`가 `500 Internal Server Error`를 반환하는 상태로 멈췄다. `wsl --status`가 exit code 50으로 응답 없이 실패하는 것으로 보아 WSL2 백엔드 쪽 문제로 판단, Docker 경로를 포기했다.
- 대안으로 로컬에 이미 설치돼 있던 **MySQL 8.4**(Windows 서비스 `MySQL84`, 이미 실행 중)를 발견해 그쪽으로 전환했다. 운영 DB와 분리하기 위해 **`spec_odyssey_test`라는 별도 테스트 전용 DB**를 새로 만들어 사용했다.
- MySQL 접속을 위한 root 비밀번호는 사용자가 직접 알려줬고, 이후 모든 DB 작업(스키마 적용, 테스트 실행, curl 스모크 테스트)에 `DB_URL`/`DB_USER`/`DB_PASSWORD` 환경변수로만 전달했다(소스에 하드코딩 없음, `DBUtil`의 기존 설계와 동일한 방식).

## 4. SQL 3개 파일 실제 적용 검증

`01_schema.sql` → `02_seed.sql` → `03_schema_extended.sql` 순서로 `spec_odyssey_test`에 실행했다. 결과:

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 테이블 수 | 36개 | `information_schema.tables` 기준, 문서(`db-design.md`)와 일치 |
| FK 제약 수 | 44개 | 1주차분 6개 + 3부 신규 38개 |
| UNIQUE 제약 수 | 21개 | `db-design.md` "복합 UNIQUE 제약" 표와 이름까지 전부 일치 |
| JOB 시드 행 | 18개 | README에 적힌 숫자와 일치 |
| CERTIFICATION 시드 행 | 37개 | 〃 |

세 파일 모두 에러 없이 적용됐고(exit 0), 사전에 정적으로 검증해둔 FK 생성 순서(참조 테이블이 먼저 만들어지는지)가 실제 MySQL에서도 문제없이 통했다.

## 5. FK·UNIQUE 제약이 실제로 동작하는지 직접 데이터로 확인

스키마가 적용됐다고 제약이 진짜 작동하는지는 별개 문제라, 손으로 데이터를 넣어 검증했다.

- **FK RESTRICT 테스트**: `USERS.desired_job_id`가 참조 중인 `JOB` row를 삭제 시도 → `ERROR 1451: Cannot delete or update a parent row: a foreign key constraint fails` 로 정상 차단됨을 확인.
- **UNIQUE 제약 테스트**: 이미 존재하는 `login_id`로 중복 INSERT 시도 → `ERROR 1062: Duplicate entry ... for key 'users.uk_users_login_id'` 로 차단됨을 확인. 이는 2부에서 코드로 방어해둔 회원가입 TOCTOU 레이스 컨디션이 DB 레벨에서도 최종 방어선으로 작동한다는 것을 실증한 것이다.
- 테스트에 사용한 행은 확인 직후 바로 삭제해 DB를 원상태로 되돌렸다.

또한 사용자가 DB 구조를 직접 눈으로 보고 싶다고 해서, 로컬에 설치돼 있던 **HeidiSQL**을 실행해 `spec_odyssey_test`에 연결하는 방법을 안내했다.

## 6. Tomcat 실배포로 HTTP 레벨 검증

컴파일(`mvn package`)이 통과한다고 실제로 동작한다는 보장은 없다는 판단 하에(특히 JSP는 배포 시점에만 컴파일되므로 `mvn package`로는 문법 오류가 안 잡힌다), 로컬에 설치돼 있던 **Apache Tomcat 11.0.25**(`C:\Jsp\apache-tomcat-11.0.25`)에 빌드한 WAR을 실제로 배포해 curl로 흐름을 검증했다.

검증한 시나리오와 결과:

| 시나리오 | 결과 |
| --- | --- |
| 회원가입 → 로그인 → `/profile` 접근 → 로그아웃 | 302 → 302 → 200 → 302, 전부 정상 |
| 비로그인 상태에서 `/profile` 접근 | 302로 `/login` 리다이렉트 |
| 로그인 상태에서 존재하지 않는 경로 접근 | 404 (에러 페이지 정상 동작) |
| 로그아웃 후 다시 `/profile` 접근 | 다시 302로 `/login` 리다이렉트 (재보호 확인) |
| 프로필 스펙 추가(CRUD) | 정상 반영, 목록에 즉시 표시 |

### 해프닝: 500 에러의 정체는 콘솔 인코딩 문제

검증 도중 회원가입 POST가 500 에러를 냈다. `<error-page>`가 이미 예외를 삼키고 있어 원인이 안 보였고, Tomcat 로그 어디에도 스택트레이스가 남지 않아 처음에는 원인 파악에 시간이 걸렸다. `error.jsp`에 스택트레이스를 임시로 출력하도록 바꿔서 재현한 결과:

```
org.apache.tomcat.util.http.InvalidParameterException: 문자 디코딩이 실패했습니다.
Caused by: java.nio.charset.MalformedInputException: Input length = 1
```

원인은 **애플리케이션 버그가 아니라 테스트 방식 문제**였다. Windows 콘솔 코드페이지가 949(EUC-KR)로 설정돼 있어(`chcp` 확인), Git Bash에서 curl.exe(네이티브 Windows 바이너리)로 한글 인자(`major=컴공` 등)를 넘길 때 인코딩이 깨진 채 전달된 것이다. 한글을 UTF-8 percent-encoding으로 직접 지정해서 재시도하니 정상적으로 302(성공)가 나왔다. 이후 검증은 전부 percent-encoding 또는 ASCII 값으로 진행했다. 임시로 추가했던 스택트레이스 출력 코드는 원인 확인 후 바로 제거해 `error.jsp`를 원래의 깨끗한 상태로 되돌렸다.

## 7. 정리

각 검증 단계(JUnit 실행, curl 스모크 테스트) 후에는 테스트 DB에 남은 데이터를 직접 삭제해 매번 깨끗한 상태로 되돌렸고, 마지막에는 Tomcat에 배포했던 WAR과 컨텍스트도 제거해 원래 Tomcat 설치 상태로 복구했다. 운영 DB(`spec_odyssey`)는 이번 검증 과정에서 전혀 건드리지 않았다.
