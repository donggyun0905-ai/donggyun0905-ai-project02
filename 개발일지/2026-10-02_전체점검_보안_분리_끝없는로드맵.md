## 1. 보안·품질 (전체 점검 결과를 순서대로 처리)
| 항목 | 처리 |
| --- | --- |
| 업로드 형식 검사가 곳곳에 따로 있고 로드맵 제출은 차단 목록(exe 등)만 확인 | **허용 목록을 `FileStorageUtil` 한 곳**으로 통일(pdf·doc·docx·hwp·hwpx·ppt·pptx·txt·md·png·jpg·jpeg·gif·zip). 서류 보관함·로드맵 제출·공유가 모두 이걸 쓴다 |

| CSRF 방어 없음 | **세션 CSRF 토큰** — 모든 POST 폼(59개)에 hidden `_csrf`, fetch는 `X-CSRF-Token` 헤더. `SecurityHeadersFilter`가 검증(+Origin/Referer 확인, 보안 헤더). 새 폼에서 빠뜨리면 `CsrfJspCoverageTest`가 잡는다 |
| 로그인 무한 시도 | 같은 아이디+IP 5회 실패 시 5분 잠금 |
| 세션 쿠키 | HttpOnly + SameSite=Lax |
| 커넥션 풀 없음(호출마다 새 연결) | `DBUtil`에 JDK만 쓰는 간단한 풀. 원격 DB에서 효과가 크다. 팀이 허가받으면 HikariCP로 교체 예정 |
| `[TEST] 파일 없이 통과` 버튼 | **제거**. 서버도 `complete`+`completed=true`를 거절한다(완료는 증빙 제출로만). 프로필에서 직접 추가한 스킬·자격증의 자동 완료는 서비스가 따로 처리하므로 그대로다 |
| 프로필에서 프로젝트를 수정하면 저장소·배포·회고가 지워지던 문제(4-4 작업 때 생김) | 수정 폼에 저장소·배포·기타 링크를 넣고, 폼에 없는 회고는 기존 값을 유지 |

## 2. 구조 정리 (동작이 달라지지 않게 — 아래 방식으로 확인)
- `RoadmapService`(1,034줄) → 공개 창구 + `RoadmapGenerator`(생성) · `RoadmapCompletionService`(완료·프로필 반영) · `RoadmapSubmissionService`(제출 완료) · `RoadmapReviewService`(복습) · `RoadmapUpkeepService`(유지·성장) · `RoadmapProgressCalculator`/`RoadmapProgress`/`TierProgress`(진행도). 공개 메서드 시그니처는 그대로.
- `RoadmapServlet` → `RoadmapSubmissionForm`(제출 폼 읽기) · `TierCelebration`(등급 환영) 분리.
- `roadmap.jsp`(532줄)·`profile.jsp`(429줄) → 조각(`.jspf`, 정적 include)으로 분리.
- **확인 방법**: ① 옮긴 코드를 줄 단위로 대조(바뀐 줄은 접근 제한자·위임 호출뿐) ② jspf는 조각을 되돌려 붙이면 원본과 **바이트 단위로 같음** ③ 같은 계정의 11개 화면을 분리 전/후 렌더링해 비교 — 토큰만 지우면 **동일**(공백만 다른 곳 제외) ④ Tomcat 10.1·11 모두 ⑤ 전체 테스트.
- DAO 39개의 `SELECT *`를 매퍼가 읽는 컬럼 목록(`COLUMNS`)으로 교체. 컬럼을 추가하면 **`COLUMNS`와 `mapRow`를 같이 고쳐야 한다**.
- 복습 생성 검사는 세션당 하루 한 번(`ReviewCheckGate`).
- 늘어나는 목록: 서류·공유 링크·D-day는 10개씩 쪽 이동(`Pager`), 로드맵은 끝낸 단계를 최근 12개만 보이고 나머지는 "이전 완료 기록 N개 더 보기".
- 컨트롤러 테스트 추가(가짜 요청/응답 도우미 `FakeWeb`): 로그인·가입·접근 필터·서류 보관함·내려받기·제출 폼·프로필 프로젝트·비밀번호·로드맵 라우팅.

## 8. 비밀번호 찾기 (복구 코드 방식) · 로그아웃 POST 전환

### 왜 이 방식인가 (선택지 비교)
| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 이메일로 재설정 링크 | 가장 흔한 방식 | 메일 발송 수단(SMTP·외부 서비스)과 라이브러리가 필요하고, **이메일이 선택 입력이라 이메일 없는 계정은 구할 수 없다** | 보류 |
| 보안 질문 | 구현이 쉽다 | 답이 추측·검색으로 알려지기 쉬워 오히려 위험 | 안 씀 |
| **복구 코드** (채택) | 외부 서비스·메일이 필요 없고, 이메일 없는 계정도 쓸 수 있다. GitHub 2단계 인증 복구 코드와 같은 방식 | 사용자가 코드를 보관해야 한다 | **채택** |
메일 발송 수단이 정해지면(Gmail SMTP 앱 비밀번호, 학교 메일 서버, 외부 메일 API 등) 이메일 재설정을 **추가**할 수 있다. 지금 구조(`UserService.resetPasswordWithRecoveryCode`)를 그대로 두고 토큰 발급 경로만 더하면 된다.

### 동작
- 가입 직후 16자 복구 코드(예 `K7M2-QX9R-…`, 헷갈리는 0/O/1/I 제외, 80비트)를 **화면에 한 번만** 보여 준다(`/recovery-code`). 새로고침하면 사라지고 캐시되지 않는다.
- 서버에는 **원문이 없다** — 비밀번호와 같은 방식(PBKDF2)의 해시만 `USERS.recovery_code_hash`에 둔다(새 컬럼, `sql/16_alter_users_recovery_code.sql`).
- 로그인 화면 "비밀번호를 잊으셨나요?" → `/password-reset`: 아이디 + 복구 코드 + 새 비밀번호. 대소문자·하이픈·공백은 무시한다.
- 성공하면 비밀번호가 바뀌고 **쓴 코드는 무효**, 새 코드가 한 번 보인다(코드는 한 번만 쓸 수 있다).
- 틀린 이유(없는 아이디 / 코드 없는 계정 / 틀린 코드 / 형식 오류)는 **같은 메시지**로만 알려 계정 존재 여부를 노출하지 않고, 어느 경우든 같은 횟수의 해시 계산을 해 응답 시간으로도 짐작하지 못하게 했다.
- 같은 (아이디, IP)에서 5번 틀리면 5분간 잠금(로그인과 같은 방식) — 코드 무작위 대입 방지.
- **이전에 가입한 계정**은 코드가 없다(NULL). 로그인한 뒤 내 프로필(지원자·면접관 모두)의 "복구 코드 발급"에서 현재 비밀번호를 확인하고 발급받는다. 재발급하면 이전 코드는 무효.
- 코드를 잃어버렸고 로그인도 못 하면 사용자가 직접 해결할 방법은 없다(운영 담당자 문의 안내 문구를 화면에 둠). 필요하면 운영자가 DB에서 비밀번호를 재설정하는 절차를 따로 정해야 한다.

### 로그아웃을 POST로
- 예전엔 `GET /logout` 링크라 다른 사이트의 `<img src=".../logout">` 하나로 사용자를 몰래 로그아웃시킬 수 있었다.
- 이제 메뉴의 로그아웃은 CSRF 토큰이 든 POST 폼(버튼을 링크처럼 보이게 스타일)이고, `GET /logout`은 아무것도 바꾸지 않고 로그인 화면으로만 보낸다.

### 배포 시 주의
- 공유 DB에 `sql/16_alter_users_recovery_code.sql`을 먼저 적용해야 한다(USERS를 읽는 모든 화면이 새 컬럼을 읽는다 — **적용 전에 배포하면 로그인을 포함한 모든 화면이 깨진다**). `sql/15`도 함께.
- 문서: `db-design.md`(USERS 컬럼, 47개 테이블 · FK 71 · 컬럼 324), ERD 뷰어, PDF(32쪽), DAO 가이드, md 사본 갱신.
- 테스트: 복구 코드 형식·해시 저장·한 번만 쓰기·같은 오류 메시지·잠금·세션 전달·프로필 재발급·로그아웃 POST (총 436개 통과). 실제 서버(Tomcat 10.1·11)에서 가입→코드 확인→재설정→새 비밀번호 로그인→로그아웃까지 확인.
