## 8. 비밀번호 찾기 (복구 코드 방식) · 로그아웃 POST 전환

### 왜 이 방식인가 (선택지 비교)
| 방식 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| 이메일로 재설정 링크 | 가장 흔한 방식 | 메일 발송 수단(SMTP·외부 서비스)과 라이브러리가 필요하고, **이메일이 선택 입력이라 이메일 없는 계정은 구할 수 없다** | 보류 |
| 보안 질문 | 구현이 쉽다 | 답이 추측·검색으로 알려지기 쉬워 오히려 위험 | 안 씀 |
| **복구 코드** (채택) | 외부 서비스·메일이 필요 없고, 이메일 없는 계정도 쓸 수 있다. GitHub 2단계 인증 복구 코드와 같은 방식 | 사용자가 코드를 보관해야 한다 | **채택** |
메일 발송 수단이 정해지면(Gmail SMTP 앱 비밀번호, 학교 메일 서버, 외부 메일 API 등) 이메일 재설정을 **추가**할 수 있다. 지금 구조(`UserService.resetPasswordWithRecoveryCode`)를 그대로 두고 토큰 발급 경로만 더하면 된다.

### 동작
- 가입 직후 16자 복구 코드(예 `K7M2-QX9R-…`, 헷갈리는 0/O/1/I 제외, 80비트)를 **화면에 한 번만** 보여 준다(`/recovery-code`). 새로고침하면 사라지고 캐시되지 않는다.
- 서버에는 **원문이 없다** — 비밀번호와 같은 방식(PBKDF2)의 해시만 `USERS.recovery_code_hash`에 둔다(새 컬럼, `sql/16_alter_users_recovery_code.sql`).
- 로그인 화면 "비밀번호를 잊으셨나요?" → `/password-reset`: 아이디 + 복구 코드 + 새 비밀번호. 대소문자·하이픈·공백은 무시한다.
- 성공하면 비밀번호가 바뀌고 **쓴 코드는 무효**, 새 코드가 한 번 보인다(코드는 한 번만 쓸 수 있다).
- 틀린 이유(없는 아이디 / 코드 없는 계정 / 틀린 코드 / 형식 오류)는 **같은 메시지**로만 알려 계정 존재 여부를 노출하지 않고, 어느 경우든 같은 횟수의 해시 계산을 해 응답 시간으로도 짐작하지 못하게 했다.
- 같은 (아이디, IP)에서 5번 틀리면 5분간 잠금(로그인과 같은 방식) — 코드 무작위 대입 방지.
- **이전에 가입한 계정**은 코드가 없다(NULL). 로그인한 뒤 내 프로필(지원자·면접관 모두)의 "복구 코드 발급"에서 현재 비밀번호를 확인하고 발급받는다. 재발급하면 이전 코드는 무효.
- 코드를 잃어버렸고 로그인도 못 하면 사용자가 직접 해결할 방법은 없다(운영 담당자 문의 안내 문구를 화면에 둠). 필요하면 운영자가 DB에서 비밀번호를 재설정하는 절차를 따로 정해야 한다.

### 로그아웃을 POST로
- 예전엔 `GET /logout` 링크라 다른 사이트의 `<img src=".../logout">` 하나로 사용자를 몰래 로그아웃시킬 수 있었다.
- 이제 메뉴의 로그아웃은 CSRF 토큰이 든 POST 폼(버튼을 링크처럼 보이게 스타일)이고, `GET /logout`은 아무것도 바꾸지 않고 로그인 화면으로만 보낸다.

### 배포 시 주의
- 공유 DB에 `sql/16_alter_users_recovery_code.sql`을 먼저 적용해야 한다(USERS를 읽는 모든 화면이 새 컬럼을 읽는다 — **적용 전에 배포하면 로그인을 포함한 모든 화면이 깨진다**). `sql/15`도 함께.
- 문서: `db-design.md`(USERS 컬럼, 47개 테이블 · FK 71 · 컬럼 324), ERD 뷰어, PDF(32쪽), DAO 가이드, md 사본 갱신.
- 테스트: 복구 코드 형식·해시 저장·한 번만 쓰기·같은 오류 메시지·잠금·세션 전달·프로필 재발급·로그아웃 POST (총 436개 통과). 실제 서버(Tomcat 10.1·11)에서 가입→코드 확인→재설정→새 비밀번호 로그인→로그아웃까지 확인.

## 9. HikariCP 도입 (강사님 허가 후)
- 직접 만든 간단한 풀을 **HikariCP 5.1.0**으로 교체했다(`DBUtil`). DAO·서비스 코드는 그대로다 — `DBUtil.getConnection()`을 try-with-resources로 쓰는 방식이 같다. 로그는 slf4j-jdk14로 java.util.logging(Tomcat 로그)에 합쳐 나온다.
- 설정: 최대 10 / 최소 유휴 2 / 연결 대기 10초 / 유휴 5분 / 최대 수명 25분 / 2분마다 keepalive. **환경변수 `DB_POOL_SIZE`로 최대 크기 조정**(`.env.example`에 설명).
- 주의 두 가지
  1. 트랜잭션(`TransactionUtil`) 안에서 DAO를 또 부르는 코드가 많아 한 요청이 연결을 2개 쓴다. 동시 사용자가 늘면 풀이 작을 때 서로 기다리다 10초 뒤 실패할 수 있으니 그때는 `DB_POOL_SIZE`를 키운다.
  2. 공유 DB를 팀원 여럿이 쓰므로 (사람 수 × 최대 크기)가 DB `max_connections`(기본 151)를 넘지 않게 한다.
- 종료 처리: `DbPoolShutdownListener`가 웹앱이 내려갈 때 풀과 MySQL 드라이버 정리 스레드를 닫는다. 내려가는 중에는 풀을 다시 만들지 않는다(종료 직전 스케줄러가 DB를 부르면 풀이 되살아나던 문제를 확인하고 막음).
- 확인: 전체 테스트 438개, Tomcat 10.1·11에서 32단계 시나리오, **DB를 재시작해도 다음 요청부터 정상**(죽은 연결을 풀이 알아서 교체), 동시 20요청 모두 200.
- 남은 경고(이전부터 있던 것): 종료 때 `trend-collector`·`work24-collector` 스케줄러 스레드가 외부 API 호출 중이라 바로 못 멈춘다는 Tomcat 경고. 기능에는 영향이 없다.

현재 직무·기술 수와 상관없이 모두 같은 값이다: 단계 완료 100점, 복습 주기 30/60/90/120일, 프로젝트 업데이트 90일·글 업데이트 150일·트렌딩 30일, 라운드 5개 기술, 열린 단계 상한 등(`RoadmapReviewService`·`RoadmapUpkeepService`·`RoadmapGenerator`).

### 실제로 어긋나는 곳 (DB를 확인한 숫자)
- 점수 공급이 **기술 수에 비례**한다. 기술 하나의 사다리(입문→전문가)가 400점이고, 시드 직무의 요구 기술은 10~13개 → 완주 4,000~5,200점. 등급 기준(`LEVEL_TIER`)은 500 / 1,500 / 3,000 / 5,000으로 직무와 무관한 절대값이라, **요구 기술이 많은 직무는 최고 등급에 쉽게 닿고 적은 직무는 못 닿는다.**
- 복습 주기가 **기술의 성격**(바뀌는 속도)과 **사용자의 기억**을 보지 않는다. SQL 기초와 프런트 프레임워크가 같은 취급이다.

### 방법
| | 내용 | 쓰는 데이터 | 스키마 |
| --- | --- | --- | --- |
| A. 점수 정규화 | 직무 사다리 **총점을 목표값으로 고정**하고 단계 점수를 나눠 준다. 단계 점수 = 목표 × 가중치 / 가중치 합 (가중치 = 요구 중요도 REQUIRED 2·PREFERRED 1 × 티어 가중 입문 1·핵심 2·심화 2·전문가 3). 예: 목표 4,000이면 사다리 완주 = "취뽀 임박", 최고 등급은 복습·업데이트 같은 유지·성장 점수로 | `JOB_REQUIRED_SKILL.importance` | 없음 (새로 생기는 단계부터 적용, 이미 받은 점수는 그대로) |
| B. 기술 성격별 복습 주기 | `SKILL.category`별 기본 주기 표(언어·CS 기초는 길게, 프레임워크·도구는 짧게) + `JOB_SKILL_TREND.mention_ratio`의 최근 증감이 큰 기술은 더 짧게 | `SKILL.category`, `JOB_SKILL_TREND` | 없음 (표는 D에 두면 편함) |
| C. 개인화 간격 (SM-2식) | 복습을 끝낼 때 "기억 났어요 / 조금 / 거의 못 했어요" 3택 → 다음 주기 ×2 / ×1.3 / ×0.5. 기술 상수 대신 **사용자별로 알아서 조정**. 평가는 `review_status`에 저장 | 사용자의 복습 기록 | 없음 |
| D. 상수를 코드 밖으로 | `SCORING_RULE`(키, 값, 설명, 직무별 덮어쓰기 `job_id`) 테이블을 두고 관리 화면(임시 관리자 화면이 이미 있음)에서 수정. 서비스는 캐시해서 읽는다. 재배포 없이 "팀 확인 필요 값"을 바로 바꿀 수 있다 | — | 테이블 1개 |
| E. 실제 데이터로 보정 | 단계 완료 소요일·복습 평가 분포를 쌓아 중앙값으로 기본값을 갱신. **사용자가 쌓여야 의미가 있어** 지금은 기록만 남기는 준비 | 이벤트 로그 | 로그 컬럼/테이블 |
| F. 라운드 크기 | 기술 5개 고정 대신 부족 기술 수에 비례(예: `min(5, max(3, ceil(부족 수 × 0.4)))`) | 격차 분석 결과 | 없음 |

### 권장 순서
1. **A (점수 정규화)** — 가장 큰 불공정(직무별 등급 속도)을 푼다. 2. **D (설정 테이블)** — 이후 모든 튜닝이 재배포 없이 가능해진다. 3. **C (개인화 간격)** — "상수 문제"를 사용자 단위로 해소. 4. B(카테고리·트렌드 가중) → 5. E(데이터 보정) → F.
A·D를 먼저 하면 나머지는 D의 설정 행으로 얹을 수 있다.

## 11. 점수 정규화(A) + 설정 테이블(D) 구현
요청: 일일 문제 풀이 점수는 상수로 두고, 등급은 시간이 걸려 차근히 오르게, 신기술이 직무에 추가되는 것도 반영.

- **기술 단계 점수**(`StepPointCalculator`) = 사다리 총점 `LADDER_BUDGET`(2,500) × 이 단계 가중치 ÷ 사다리 가중치 합. 중요도(필수 2·우대 1) × 티어(입문 1·핵심 2·심화 2·전문가 3). 기술 11~13개인 시드 직무에서 입문 단계 약 15~30점, 전문가 단계 약 45~90점이고 최소 5점. 이전엔 모든 단계가 100점이라 기술 수가 많으면 최고 등급까지 사다리만으로 닿았다.
- **차근히 오르는 이유**: 사다리를 끝까지 해도 2,500점이라 "실전러(1,500)"를 지나 "취뽀 임박(3,000)"에 못 미친다. 그 위는 일일 문제(하루 3문제×15~30점), 복습(40→30→…), 프로젝트·글 업데이트, 트렌딩 학습으로 시간을 들여야 한다. 자격증·프로젝트 단계는 사다리 밖이라 고정 100점.
- **신기술**: 단가는 사용자가 그 직무로 **처음 로드맵을 만든 시각 이전에 있던 기술**(`JOB_REQUIRED_SKILL.created_at`)로만 정한다. 트렌드 수집이 나중에 기술을 추가하면 그 기술의 단계는 같은 단가로 점수를 **더 받고**, 이미 있던 단계의 점수는 변하지 않는다(테스트로 확인).
- **일일 문제 점수**는 처음엔 상수로 뒀다가 §12에서 같은 규칙 테이블로 옮겼다(값은 그대로).
- **설정 테이블 `SCORING_RULE`**(`sql/17_schema_scoring_rule.sql`, 03·04에도 반영): 사다리 총점·가중치·최소 점수·고정 점수·라운드 기술 수·복습/유지 주기와 점수·감쇠 25개. `ScoringRules`가 1분 캐시로 읽고, **행이 없거나 테이블이 아직 없어도 코드 기본값으로 동작**한다. 0 이하 값은 기본값으로 대체(0으로 나누기·복습 폭주 방지).
- 한도 안 정한 것: 관리 화면(지금은 DB에서 직접 수정), 직무별 덮어쓰기, 복습 후 3택 평가(C)·카테고리별 주기(B).
- 확인: 전체 테스트 445개 통과(새 테스트 7개: 기술 수 6~20개에서도 사다리 총점이 목표±반올림 오차, 단계·중요도 순서, 신기술이 기존 점수를 안 깎음, 최소 점수, 규칙 변경 반영/0·음수 무시). 테이블이 없는 DB에서도 로드맵 테스트 통과.
- 배포: 공유 DB에 `sql/17_schema_scoring_rule.sql`을 실행(없어도 기본값으로 동작). 기존 사용자의 이미 받은 점수는 그대로고, 새로 완료하는 기술 단계부터 새 점수가 적용된다.

- `origin/donghyeon`의 스펙 아카이브(상위 티어 팁 게시판: 글쓰기·댓글·하트·북마크·사진/유튜브 첨부)를 합쳤다. 텍스트 충돌은 없었다.
- **합치며 고친 것**
  1. 새 게시판 폼 7개에 **CSRF 토큰이 없어서** 글쓰기·댓글·하트·삭제가 전부 403이 날 상황 → 토큰 추가(`CsrfJspCoverageTest`가 잡아냄).
