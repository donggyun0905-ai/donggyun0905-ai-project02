# 1부 — IntelliJ 개발환경 세팅 + Git 협업 트러블슈팅

날짜: 2026-09-22

## 1. 개요

오늘은 크게 두 갈래로 나뉜다. 하나는 IntelliJ에서 Tomcat을 실제로 눌러서 실행할 수 있게 세팅하는 과정에서 만난 문제들, 다른 하나는 팀원들이 push를 못 하겠다고 해서 원인을 추적한 과정이다. 둘 다 "기능"은 아니지만, 여기서 걸린 문제들이 앞으로 팀원 전원이 겪을 수 있는 것들이라 기록해둔다.

## 2. IntelliJ에서 Tomcat 원클릭 실행 세팅

### 2-1. Maven 프로젝트로 import가 안 되어 있었다

`Run` → `Edit Configurations` → `Tomcat Server` → `Deployment` 탭에서 war 아티팩트를 추가하려는데 목록에 아무것도 안 뜨고 "External Source"만 보이는 문제가 있었다. `.idea/Project02.iml`을 열어보니 `type="JAVA_MODULE"`로 된 빈 모듈이었다 — `pom.xml`이 있는데도 Maven 프로젝트로 한 번도 import가 안 된 상태였던 것. 프로젝트 창에서 `pom.xml` 우클릭 → `Add as Maven Project`로 해결. import가 끝나면 `war` 패키징을 보고 Web 파셋과 war exploded 아티팩트가 자동으로 생긴다(아티팩트 이름은 `artifactId`인 `spec-odyssey`를 따라가지, 폴더명 `Project02`가 아니다).

### 2-2. DB_URL에 눈에 안 보이는 공백/개행이 섞여 들어감

Tomcat 실행 설정의 `Environment variables`에 `DB_URL`을 입력했는데 "No suitable driver found for  jdbc:mysql://..." 에러가 났다. 메시지에 공백이 두 칸 있는 걸 보고 URL 앞에 공백이 붙었을 거라 의심했고, `.idea/workspace.xml`을 직접 열어 확인하니 실제로 값 맨 앞에 스페이스 한 칸, 맨 뒤에 개행문자(`&#10;`)가 들어가 있었다. 안내 텍스트를 복붙하는 과정에서 앞뒤 공백까지 같이 복사된 것으로 보인다. 값을 다시 정확히 입력해서 해결.

이 문제는 팀원 사이에서도 반복됐다 — "복붙하면서 역슬래시가 자꾸 들어가서 안 됐다"는 얘기를 나중에 다시 들었다. IntelliJ의 환경변수 입력창(GUI 다이얼로그)을 거치는 방식 자체가 복붙 사고에 취약하다는 뜻이라, 결국 `.env` 파일 방식으로 바꾸게 된 계기가 됐다(3절 참고).

### 2-3. DB 자체가 없었음

`DB_URL` 오타를 고친 뒤에도 `Unknown database 'spec_odyssey_dev'` 에러가 났다. 내가 임의로 `spec_odyssey_dev`라는 이름으로 DB를 만들라고 안내했었는데, 실제로 만든 적이 없어서 난 에러였다. `CREATE DATABASE` + `01_schema.sql` → `02_seed.sql` → `03_schema_extended.sql` 순서로 적용해서 해결.

이후 "우리 팀 DB는 `spec_odyssey_dev`가 아니라 `spec_odyssey_test`"라는 정정을 받아서, `DB_URL`을 `spec_odyssey_test`로 다시 바꿨다. `spec_odyssey_test`는 어제 자동테스트용으로 이미 만들어둔 DB라 스키마가 이미 맞는 상태였다.

## 3. `.env` 파일 방식 도입

IntelliJ 환경변수 다이얼로그의 복붙 사고가 반복되는 걸 보고, `DBUtil`이 환경변수 대신(또는 그보다 우선해서) `src/main/resources/.env` 파일을 읽도록 바꿨다.

- 우선순위: `.env` 파일이 있으면 그 값을 쓰고, 없으면 기존처럼 환경변수(`System.getenv`)로 대체.
- `.env.example` 템플릿을 커밋(`DB_URL`/`DB_USER`/`DB_PASSWORD` 키만 있고 값은 비어있음).
- 실제 `.env`는 `.gitignore`의 `*.env` 규칙에 이미 걸려 있어 커밋되지 않는다.
- 검증: 환경변수를 전부 지운 상태에서 `mvn test` 실행 → 42개 전부 통과 (`.env`만으로 DB 연결이 되는지 확인).

이러면 팀원들은 GUI 다이얼로그에 값을 입력할 필요 없이, 텍스트 파일 하나 복사해서 값만 채우면 되므로 복붙 사고 가능성이 훨씬 줄어든다.

## 4. GitHub 협업자 push 문제

### 4-1. 증상

팀원들이 브랜치든 main이든 push가 안 되고, GitHub가 "Pull Request로만 가능하다"고 안내한다는 문의를 받았다.

### 4-2. 1차 추정 — Collaborator 미승인

저장소가 Public인 상태에서 초대(Collaborator)를 보냈어도 상대가 **수락**하기 전까지는 실제 쓰기 권한이 없다. 이 상태에서 push를 시도하면 GitHub는 정확히 "권한이 없으니 포크해서 PR을 올리라"는 취지로 안내한다.

사용자가 GitHub `Settings → Collaborators and teams` 화면 스크린샷(`캡처.PNG`)을 공유해줘서 확인해보니:

| 이름 | 상태 |
|---|---|
| 로킹 | 협력자(수락됨) |
| 모스헤드5 | 협력자(수락됨) |
| 강다인 | 초대 대기 중 |
| 조영준(`youngjun0723`) | 초대 대기 중 |

강다인·조영준 두 명이 초대를 아직 수락하지 않은 상태였다.

### 4-3. 그런데 수락된 사람도 안 된다는 정정

로킹·모스헤드5는 이미 수락된 협력자인데도 push가 안 된다는 추가 정정을 받았다. 이 경우 남은 가능성은 두 가지였다:

1. Collaborator 초대 시 권한 레벨을 Write가 아니라 Read로 잘못 지정했을 가능성
2. GitHub 브랜치 보호 규칙(Branch protection rule)이 걸려 있어 전원이 직접 push를 못 하고 PR을 거쳐야만 하는 상태일 가능성(에러 메시지 "Changes must be made through a pull request"가 이 경우와 정확히 일치)

두 가지 다 API 인증 없이는 확인이 안 되는 설정이라 사용자에게 직접 GitHub 화면을 확인해달라고 요청한 상태였는데, 결과적으로는 **네트워크 문제**였던 것으로 마무리됐다(해프닝). 다만 확인 과정에서 다룬 두 가지 원인(권한 레벨, 브랜치 보호 규칙)은 앞으로 비슷한 증상이 다시 나오면 먼저 볼 지점으로 기록해둔다.

## 5. 브랜치 동기화 — 팀원 브랜치가 옛날 지점에 멈춰 있었음

브랜치 상태를 다시 확인해보니:

- `main`, `donggyun0905`: 오늘까지의 전체 작업(`7a67080`)까지 반영됨
- `donghyeon`: 이미 스스로 `main` 위에서 시작해서 커밋 1개(`index.jsp`의 `h1` 텍스트를 영문으로 수정)를 얹어둔 상태 — 문제 없음
- `seongwon`, `youngjun`, `kangdain`: 여전히 어제 초반 지점(`d847fec`)에 멈춰 있었음 — 오늘 만든 DAO 36개, `TransactionUtil`, `RoadmapService` 등을 하나도 못 받은 상태

세 브랜치를 `git push origin main:refs/heads/<branch>` 명령으로 `main`과 동일한 지점까지 fast-forward 시켰다. 이 명령이 처음에는 "Git Destructive" 안전장치에 걸려 자동 실행이 막혔고, 사용자가 직접 실행하거나 명시적으로 재요청한 뒤에 진행할 수 있었다. 최종적으로 5개 브랜치(`main`, `donggyun0905`, `seongwon`, `youngjun`, `kangdain`)가 전부 `7a67080` 기준으로 맞춰졌다.
