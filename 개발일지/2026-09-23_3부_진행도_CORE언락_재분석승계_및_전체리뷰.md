# 3부 — 진행도·CORE 언락·재분석 승계 + 전체 리뷰

날짜: 2026-09-23
관련 커밋: `9c72a95`

## 1. 개요

"남은 거 정리해줘" 요청에 답하면서 나온 4가지를 사용자와 하나씩 확인하며 처리했다. 그 다음 "자격증 말고 프로젝트·스킬도 겹칠 수 있지 않냐"는 지적을 계기로 로드맵·게이미피케이션 관련 코드 전체를 다시 훑는 리뷰를 했고, 거기서 진짜 버그를 몇 개 더 잡았다.

## 2. 진행도(%) — "현재 티어 기준"으로 결정

`ROADMAP.target_level`이 기본 `EXPERT`로 고정돼 있고 `db-design.md`에 "길이 계속 연장되는 구조"라고 적혀 있어서, "전체 대비 %"는 분모가 계속 바뀌어 의미가 없다. 새로 목표를 정하게 하는 기능을 따로 만들지, 지금 구조로 계산할지 물어봤고 후자로 결정 — `RoadmapService.computeProgress(steps)`가 ENTRY 단계 완료/전체 개수로 %를 낸다. 새 UI/입력 없이 기존 값만으로 계산되는 쪽이라 스코프가 작았다.

## 3. ENTRY 완료 → CORE 단계 언락

CORE는 지금까지 "다음 단계 미리보기"로만 회색으로 보여주고 완료 체크 버튼이 아예 없었다. ENTRY를 다 끝내면 CORE도 ENTRY와 똑같이 완료 체크 가능한 형태로 바뀌도록 `roadmap.jsp`를 고쳤다. 확인해보니 CERT·PROJECT는 항상 `tier=ENTRY`로만 생성되고 CORE엔 SKILL만 들어가는 구조라, "PROJECT 파일 업로드 폼이 CORE에도 뜨나" 같은 걱정 없이 단순하게 처리할 수 있었다.

서버 쪽은 이미 전에 "CORE 단계를 서버에서 막지 말자"(사용자가 지적한 "다른 길에서 이걸 먼저 하고 싶어서 먼저 했을 때도 있다"는 이유)고 정해뒀던 터라 손댈 게 없었고, 순수하게 화면(JSP) 쪽만 고치면 됐다.

## 4. 재분석 시 완료 단계 승계

재분석으로 새 로드맵 버전이 생길 때, 이전에 완료했던 스킬이 미완료로 초기화되는 문제가 있었다("딴 걸 또 딸 순 없으니" 고쳐야 한다고 확인받음). `generate()`에서 SKILL 단계를 새로 넣을 때마다 `countCompletedByUserAndSkill`로 이전 완료 이력이 있는지 확인해서, 있으면 새 단계도 바로 완료 상태로 넣는다 — 단, **점수는 다시 안 준다**(`completeStep`을 거치지 않고 `is_completed=true`로 바로 insert하므로 `scoreService.award`가 호출되지 않는다).

CERT는 `findSuggestedCertification`이 이미 보유한 자격증을 애초에 후보에서 제외하기 때문에 별도 승계 로직이 필요 없었다(재확인만 하고 코드 변경 없음).

## 5. 프로필에서 직접 추가해도 로드맵이 인식하게 — CERT, 그리고 SKILL

로드맵의 "완료하기"를 거치지 않고 사용자가 프로필에서 직접 자격증을 추가하면 로드맵의 해당 CERT 단계가 계속 미완료로 남는 문제가 있었다. `RoadmapService.syncCertAddedFromProfile(userId, certTitle)`을 만들어 `ProfileSpecServlet`에서 CERT 스펙 추가 시 호출하도록 연결했다 — 일치하는 미완료 CERT 단계를 찾아 `completeStep`을 그대로 태운다.

여기서 사용자가 "자격증 말고 프로젝트나 스킬도 겹칠 수 있지 않냐"고 지적했는데, 정확했다. 같은 문제가 SKILL에도 있었고, 오히려 SKILL 쪽이 더 까다로웠다:

- 1주차 설계상 프로필에서 수동 입력한 기술은 `skill_id`가 항상 `NULL`이다(2주차 임베딩 매칭 배치 전이라 `UserSkillDao` 자체에 이미 이런 주석이 있었다).
- CERT와 같은 방식으로 그냥 `syncSkillAddedFromProfile`을 만들면, 사용자가 수동으로 "React"를 적어둔 상태에서 로드맵의 React 단계를 완료 처리할 때 `USER_SKILLS`에 **같은 기술이 두 줄**(하나는 `skill_id=NULL`, 하나는 `skill_id`가 채워진 새 행)로 남는 진짜 버그가 생긴다.
- **수정**: `syncSkill`이 `skill_id`로 못 찾으면, 같은 이름의 수동 입력 행(`skill_id IS NULL`)이 있는지 한 번 더 찾아서(`UserSkillDao.findByUserIdAndRawInput`), 있으면 새로 만들지 않고 그 행에 `skill_id`를 채워 넣는(`attachSkillId`) 쪽으로 병합한다.
- 이 로직을 테스트하다가 병합 버그를 하나 더 발견했다 — 기존 행의 숙련도가 미입력(`null`)이고 새로 계산한 값이 `BEGINNER`(둘 다 랭크 0)면, `>` 비교라서 `null`이 그대로 남는 문제였다. `>=`로 바꿔서 동점일 땐 항상 새로 계산한(항상 `null`이 아닌) 값을 쓰도록 고쳤다.

PROJECT는 같은 방식으로 못 고친다는 것도 이번에 명확히 정리했다 — CERT/SKILL은 `certification_id`/`skill_id`로 동일성을 판단할 수 있는데, PROJECT 단계는 애초에 특정 실체를 가리키지 않는 범용 제안이라 매칭 근거가 없다. 억지로 이름 매칭 같은 걸 붙이면 엉뚱한 프로젝트가 자동 완료되는 오작동이 더 클 것 같아 전용 완료 플로우(파일 첨부 필수)로만 완료하게 두기로 했다.

## 6. 전체 리뷰에서 추가로 잡은 버그

### 6-1. PROJECT 완료 시 고아 파일

`completeProjectStep`이 이미 완료된 단계에 재제출되거나 소유자가 아니면 조용히 아무 것도 안 하는데, 서블릿은 그 전에 이미 디스크에 파일을 다 저장해놓은 상태였다. DB에 참조가 하나도 없는 파일이 디스크에 영원히 남는 문제였다.

**수정**: `completeProjectStep`이 `boolean`(실제로 반영됐는지)을 반환하도록 바꾸고, 서블릿이 `false`거나 `SQLException`이 나면 방금 저장한 파일을 지우도록 고쳤다.

### 6-2. `syncSkill`의 방어 누락

`skillDao.findById(skillId)`가 `null`을 반환할 수 있는 경우(SKILL 마스터가 삭제된 예외 상황)에 대한 null 체크가 없어서 NPE 위험이 있었다. 방어 코드 추가.
