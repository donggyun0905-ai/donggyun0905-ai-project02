## 3. 기술 선수관계 그래프 — 위상 정렬 + DFS (`37917e7`)

### 문제

로드맵 순서를 "필수냐 우대냐"와 티어로만 정했다. 그래서 Spring이 Java보다 먼저, Docker가 Linux보다
먼저 나오는 순서가 만들어질 수 있었다. "왜 이 순서냐"에 답할 근거가 없었다.

### 선택

`SKILL_PREREQUISITE(skill_id, prereq_skill_id)`에 "A를 하기 전에 B"를 담고 방향 그래프로 본다.
로드맵 생성 때 **Kahn 알고리즘**으로 줄 세우고, 관리자가 관계를 추가할 때 **DFS**로 순환을 막는다.

### 설계에서 지킨 두 가지

**① 원래 순위를 필요한 만큼만 흔든다.** 선수관계는 "이것보다 먼저"만 말하고 전체 순서를 말하지 않는다.
그래서 큐에서 꺼낼 때 항상 "지금 꺼낼 수 있는 것 중 격차 분석 순위가 가장 앞선 것"을 고른다.

```java
while (!ready.isEmpty()) {
    ready.sort((a, b) -> Integer.compare(rank.get(a), rank.get(b)));
    Long next = ready.remove(0);
    sorted.add(next);
    for (Long waiting : unlocks.get(next)) {
        if (inDegree.merge(waiting, -1, Integer::sum) == 0) {
            ready.add(waiting);
        }
    }
}
```

관계없는 기술은 자기 자리를 지킨다. `[Spring, SQL, Java]`에 "Spring 전에 Java"가 있으면
`[SQL, Java, Spring]`이 된다 — SQL이 원래 Java보다 앞이었으니 그대로 앞에 남는다.

**② 순환이 있어도 로드맵 생성이 멈추지 않는다.** 관리자 화면이 막지만 DB를 직접 고치면 생길 수 있다.
그때 생성이 실패하면 안 되므로 정렬하지 못한 기술은 원래 순서로 뒤에 붙인다(FR-111과 같은 태도).

**라운드 밖 기술은 끌어오지 않는다.** 그러면 이번 라운드 구성이 통째로 바뀌고, 그 기술은 다음 라운드에
어차피 들어온다.

### 순환 검사를 재귀로 안 쓴 이유

관계가 길게 이어지면 스택이 넘칠 수 있어 명시적 스택으로 썼다. 그리고 **기존 데이터에 이미 순환이
있어도 멈추지 않는다**(visited로 끊는다) — 관리자가 망가진 데이터 위에서 다른 관계를 추가할 수 있어야 한다.

```java
// skill → prereq 관계를 넣으면 순환이 생기는지. 간선이 skill → (그 선수들) 방향이므로
// prereq에서 출발해 skill에 닿으면 순환이다.
Deque<Long> stack = new ArrayDeque<>();
stack.push(prereqSkillId);
while (!stack.isEmpty()) {
    Long current = stack.pop();
    if (!visited.add(current)) continue;      // 이미 본 곳 — 기존 순환에 빠지지 않는다
    if (current.equals(skillId)) return true;
    for (Long next : prereqs.getOrDefault(current, Set.of())) {
        if (!visited.contains(next)) stack.push(next);
    }
}
```

### DB 제약에서 막힌 것

`CHECK (skill_id <> prereq_skill_id)`도 걸려고 했는데 MySQL이 거부했다 —
`ERROR 3823: Column 'skill_id' cannot be used in a check constraint: needed in a foreign key constraint
referential action`. `ON UPDATE CASCADE`가 걸린 컬럼은 CHECK에 쓸 수 없다. 프로젝트 FK 관례를 깨지
않기로 하고, 자기 참조는 DFS가 잡는 **가장 짧은 순환**으로 코드에서 막았다.

### 시드

`sql/35`로 19개를 넣었다: Java→Spring→Spring Boot, Linux→Docker→Kubernetes,
JavaScript→React·Vue·Node·TS, Python→Pandas·NumPy·Django·Flask·TF·PyTorch, SQL→MySQL·Redis,
AWS→Terraform, Git→Jenkins, Linux→Nginx.

**애매한 것은 일부러 안 넣었다.** "React 전에 TypeScript" 같은 것은 취향이 섞여 "왜 이 순서냐"에
답할 수 없게 된다. 이름으로 찾는 `INNER JOIN`이라 시드에 없는 기술(JPA·Spark)은 그 줄만 조용히 건너뛴다.

## 4. 간격 반복 복습 — SM-2 (`e992f3d`)

### 문제

복습 주기가 티어로만 고정이었다(입문 30일 · 핵심 60 · 심화 90 · 전문가 120). 같은 사람이 쉬운 기술과
어려운 기술을 같은 주기로 복습했다.

### 선택

복습을 낼 때 "얼마나 기억났나요?"를 받아 Anki가 쓰는 SM-2로 기술마다 다음 복습일을 계산한다.
자기 평가 네 가지 → SM-2 품질 q: 거의 잊었다(2) · 어려웠다(3) · 보통(4) · 쉬웠다(5).

```
EF' = EF + (0.1 - (5-q) × (0.08 + (5-q) × 0.02))
q=5 → +0.1 / q=4 → 변화 없음 / q=3 → -0.14 / q=2 → -0.32
```

### 원래 SM-2와 다르게 한 곳

**첫 간격을 1일·6일이 아니라 티어 기본 주기로 쓴다.** 원래 공식은 매일 카드를 보는 플래시카드용이다.
여기서 복습은 "기술 하나를 다시 정리해 글로 내는" 일이라 하루 뒤에 또 하라고 하면 쓸 수 없다.
팀이 정한 티어 주기를 출발점으로 두고 두 번째부터 EF로 늘린다 — 덕분에 기존 동작과도 이어진다.
"거의 잊었다"는 7일로 당긴다(1일은 글로 내는 복습에 너무 짧다).

### 원래 공식에 없는 상한을 둔 이유

SM-2에는 EF 상한이 없다. 그러면 "쉬웠다"를 몇 번 누르는 것만으로 간격이 몇 년이 된다. EF를 2.8로,
간격 자체를 1년으로 끊었다 — 1년을 넘기면 사실상 다시 안 보게 된다.

### 트랜잭션 경계

일정 갱신을 점수 적립과 **같은 트랜잭션** 안에서 한다. 점수는 들어갔는데 다음 일정이 안 잡히면
그 기술이 영원히 돌아오지 않는다.

자기 평가는 기본값 "보통"이고 값이 이상해도 보통으로 본다 — 평가 때문에 복습 제출이 막히면 안 된다.
`completeReview`는 두 인자 버전을 남겨 뒀다(보통으로 동작).

## 5. D-day까지 무엇을 할지 — 0/1 배낭 (`cbb7dcb`)

### 문제

D-day 화면은 "며칠 남았다"만 보여 줬다. 남은 기간에 무엇부터 하면 좋은지는 사용자가 직접 골라야 했다.

### 선택

남은 일수 = **용량**, 단계 소요 일수 = **무게**, 그 단계로 받는 점수(`StepPointCalculator`) = **가치**.
한 단계는 쪼갤 수 없고(절반 완료가 없다) 한 번만 담을 수 있어 **0/1 배낭**이 맞다.

### 왜 그리디가 아니라 DP인가

점수/일수(밀도)가 높은 것부터 담는 그리디는 **밀도 1등을 담고 남은 칸에 아무것도 안 들어가는** 경우에
무너진다. 후보가 (6일 100점)·(4일 60점)·(3일 55점)일 때 남은 기간이 **6일**이면 그리디는 밀도 1등인
3일 55점을 담고 남은 3일을 버려 **55점**에서 멈추지만, DP는 6일 100점 하나로 **100점**을 찾는다.
용량이 작을수록 그 확률이 커진다. 이 반례를 테스트에 박아 뒀다.

> 문서를 쓰다 내 설명의 오류를 잡았다. 처음에 "7일에서 그리디는 100점"이라고 썼는데, 7일에서는
> 밀도 그리디도 3일+4일로 115점을 낸다 — 반례가 아니다. `docs/algorithms.html`의 데모를 만들어
> 용량별로 두 방식을 같이 계산해 보고서야 알았다. 실제 반례는 용량 6일이고, 그 사례를 테스트에 추가했다.

```java
// best[i][d] = 앞의 i개만 쓰고 용량 d일 때의 최대 점수
for (int i = 1; i <= n; i++) {
    int weight = items.get(i - 1).effortDays();
    int value = items.get(i - 1).points();
    for (int d = 0; d <= capacity; d++) {
        int without = best[i - 1][d];
        best[i][d] = d < weight ? without : Math.max(without, best[i - 1][d - weight] + value);
    }
}
```

### 전제 — 잠긴 단계는 후보에서 뺀다

로드맵은 앞 티어를 끝내야 다음이 열리는 계단식 잠금이다. 잠긴 단계를 추천하면 **"할 수 없는 일"을
알려 주는 셈**이다. 복습처럼 사다리에 없는 티어는 언제든 할 수 있다.

### 소요 일수는 추정이라 규칙으로 뺐다

`ScoringRules`(=`SCORING_RULE` 테이블)에 `EFFORT_DAYS_*`로 뒀다. 관리자가 조정할 수 있고 코드 기본값도
있다. 입문 3일 · 핵심 7 · 심화 5 · 전문가 4 · 자격증 21(접수·시험 일정) · 프로젝트 10 · 복습 1.

### 표가 커지지 않게 둔 상한 둘

계획 기간 1년(넘는 D-day에 계획은 의미가 없다), 후보 60개(로드맵이 길면 미완료가 수백 개 — 점수
밀도 높은 것부터 자르므로 좋은 후보는 남는다).

## 6. 하이브리드 기술명 매칭 — RRF (`54bced3`)

### 문제

기존 매칭은 "정확 일치 → 접두·부분 → 편집거리(0.75) → 임베딩(0.75)"을 차례로 시도하고 각 단계가 자기
임계값을 못 넘으면 거기서 끝이다. 그래서 **두 신호가 모두 "조금 비슷하다"고 말하는 입력**을 놓쳤다.

### 왜 점수를 더하지 않고 RRF인가

편집거리 유사도와 코사인 유사도는 **분포가 다르다**. 그대로 더하면 한쪽이 항상 이기고, 정규화하려면
각 분포를 알아야 한다. RRF는 점수가 아니라 **순위**만 쓴다.

```
score(d) = Σ 1/(k + rank_i(d)),  k = 60
```

척도가 다른 신호를 정규화 없이 합칠 수 있는 것이 장점이다. k=60은 정보 검색의 관례값 — 작으면 1등에
너무 쏠리고 크면 순위 차이가 뭉개진다.

### 가장 중요했던 것 — 기존 동작을 바꾸지 않는다

종속(`EmbeddingMatcher` → `FuzzyNameMatcher`)이 뭐라도 찾으면 그대로 돌려주고, **못 찾았을 때만** RRF가
돈다. 없던 결과만 더하고 있던 결과는 안 건드린다. 사전(`SKILL_ALIAS`) 일치가 먼저 잡던
"자바 백엔드 → Java" 같은 동작도 그대로다. 기존 매칭 테스트가 하나도 깨지지 않은 것이 그 증거다.

### 받아들이는 조건 — "합의"

RRF 1등이 **두 순위에서 모두 상위 3등 안**에 있어야 받는다. 한쪽만 좋아하는 후보가 바로 알려진
오탐이다 — `EmbeddingMatcher` 주석에 적혀 있는 실측값이 그 근거다.

| 쌍 | 코사인 | 뜻 |
| --- | --- | --- |
| Java ↔ JavaScript (다른 기술) | 0.805 | 임베딩만 보면 1등인데 글자로는 전혀 아니다 |
| 자바 ↔ Java (같은 기술) | 0.680 | 오히려 더 낮다 |
| "웹 서버 구축 기술" ↔ "백엔드 서버 개발 능력" | 0.783 | 진짜 비슷한 문장이 오탐 쌍보다 낮다 |

두 신호가 같이 가리킬 때만 받으면 이 종류를 막는다. 그래서 각 신호의 개별 바닥은 종속보다 낮춰도
된다(글자 0.45 · 의미 0.60) — **합의가 확신을 대신한다**.

### 글자 유사도는 둘 중 높은 쪽

편집거리만 쓰면 앞에 글자가 붙은 쌍("myspringboot" vs "springboot")에 약하고, 2-gram Dice만 쓰면 짧은
이름의 오타에 약하다. 둘을 계산해 높은 쪽을 쓴다.

### 화면에 남기는 점수

RRF 내부 값은 0.03 같은 수라 사용자가 보는 "유사도"로 쓸 수 없고, `SKILL.similarity_score`는
`DECIMAL(5,4)`라 0~1이어야 한다. 그래서 두 신호의 평균을 남긴다.

### 한계를 코드에 적었다

표기 체계가 아예 다른 입력("리액트" vs "React.js")은 글자 순위가 전혀 못 잡아 합의가 성립하지 않는다.
그건 `SKILL_ALIAS` 사전이 맡는 영역이고, 억지로 받으면 오탐이 늘어난다. 임베딩 모델이 없는 PC에서는
합의할 두 번째 신호가 없어 이 단계를 조용히 건너뛴다.

## 7. 함께 익힌 기술 추천 — 자카드 + 동시 출현 (`e7e4c1d`)

### 선택

"같은 직무를 목표로 한 사람들이 내가 가진 기술 다음에 많이 익힌 기술"을 대시보드에 보여 준다.
`JOB_REQUIRED_SKILL`은 "직무가 요구하는 것"이고 이쪽은 "비슷한 사람들이 실제로 고른 것"이라 **서로 다른 정보**다.

### 왜 단순 빈도가 아니라 자카드로 가중하나

인기 기술은 아무 상관 없는 사람도 갖고 있다. 나와 기술 구성이 비슷한 사람(자카드가 높은 사람)이
가진 기술에 더 무게를 주면 "나와 비슷한 길을 걷는 사람들의 다음 걸음"에 가까워진다.

```
자카드 = |교집합| / |합집합|
```

합집합으로 나누기 때문에 **기술을 아주 많이 등록한 사람이 교집합만으로 1등이 되는 것**도 막힌다
(테스트로 고정했다). 겹치는 기술이 하나도 없는 사람은 "비슷한 길"이 아니라 아예 제외한다.

### 개인정보

집계만 내보낸다. 누가 가졌는지는 돌려주지 않고 화면에는 "N명 중 M명"만 나간다. **표본이 모자라면
아무것도 보여 주지 않는다** — 또래 3명 미만이거나 그 기술을 가진 사람이 2명 미만이면 추천하지 않는다.
2~3명으로 "많이 익혔다"고 말하면 틀린 말이고, 사람이 적을 때는 추천 자체가 특정 개인의 프로필을
드러낼 수 있다. 데이터 인사이트의 또래 비교와 같은 태도다.

조회에서 빼는 대상: 본인 · 논리 삭제 · 탈퇴 신청 · 테스트 계정(`is_test`) · `skill_id IS NULL`.
**제외가 실제로 걸리는지 DB 테스트로 확인했다** — SQL 컬럼 이름 오타는 런타임에만 드러난다.

동점일 때 순서를 `skillId`로 고정했다 — 호출마다 추천 순서가 바뀌면 사용자가 혼란스럽다.

## 8. 급상승 기술 감지 — EWMA + z-score (`d8de80c`)

### 문제

트렌드가 "이번 달 언급 비율 높은 순"이면 원래 항상 높은 기술(Java처럼 늘 30%대)이 늘 1등이라
"요즘 뜨는 기술"을 알 수 없다. 알고 싶은 것은 절대값이 아니라 **평소보다 얼마나 튀었는지**다.

### 왜 단순 평균이 아니라 EWMA인가

단순 평균은 1년 전 값과 지난달 값을 같게 본다. 채용 시장은 최근이 더 중요해서 최근에 큰 가중을 주는
EWMA가 "평소"에 가깝다.

```
mean_t = α·x_t + (1-α)·mean_(t-1)
var_t  = α·(x_t - mean_(t-1))² + (1-α)·var_(t-1)
z = (이번 달 - 과거 기준선) / 과거 표준편차
```

**이번 달 값은 기준선에 넣지 않는다** — 넣으면 자기 자신 때문에 기준선이 올라가 z가 작아진다
(테스트로 고정했다).

### 배지를 아껴 붙이려고 조건 넷

| 조건 | 이유 |
| --- | --- |
| z ≥ 2.0 | 정규분포라면 상위 약 2% |
| 이번 달 비율 ≥ 1% | 0.1%가 0.4%가 되는 것도 z는 크지만 공고 몇 건 차이다 |
| 과거 3달 이상 | 수집을 막 시작했으면(2026-09) "평소"를 모른다 |
| 표준편차 바닥 0.2 | 완전히 평평했던 기술은 작은 변화에 z가 무한대로 튄다 |

그리고 **위로 튄 것만** 본다 — 아래로 떨어진 달도 z의 절댓값은 크다.

α=0.4는 쌓인 달이 많지 않아 과거에 눌리지 않게 잡은 값이고, 더 크면 기준선이 지난달 하나에 휘둘린다.
빠진 달(null)은 0건으로 보고 계산을 멈추지 않는다.

## 9. 토큰 버킷 + 서킷 브레이커 (`c09c59a`)

### 문제

지금까지는 **실패한 뒤에 기다렸다.** Groq 한도를 넘으면 429를 받고 재시도 정책이 20·40·60초를 기다리고,
깃허브 403이나 고용24 장애에서는 사용자마다·요청마다 같은 실패를 반복하며 타임아웃만큼 멈췄다.
두 장치는 **보내기 전에** 막아서 FR-111·112가 말하는 "캐시·안내 문구로 대체"가 즉시 일어나게 한다.

### 토큰 버킷

토큰을 일정 속도로 채우고 호출마다 하나 쓴다. 창(window)을 끊어 세는 방식과 달리 창이 바뀌는 순간
두 배가 몰리지 않고, 평소에 안 쓰면 그만큼 몰아 쓸 수 있다.

시계가 뒤로 가도(시간 동기화) 토큰을 깎지 않는다 — 음수가 되면 영원히 막힌다.

적용: Groq 분당 30회, 한꺼번에 10개까지(화면 하나가 추천 이유를 여러 개 만든다).

### 서킷 브레이커

```
CLOSED ──연속 실패 누적──▶ OPEN ──시간 경과──▶ HALF_OPEN ──성공──▶ CLOSED
                            ▲                      │
                            └──────실패────────────┘
```

**반만 열어 한 번 떠보는 단계가 필요한 이유**: 바로 CLOSED로 돌리면 아직 죽어 있는 상대에게 모든
요청이 동시에 몰려 또 한꺼번에 실패한다.

| 대상 | 임계값 | 차단 | 비고 |
| --- | --- | --- | --- |
| Groq | 연속 5회 | 1분 | 형식 오류(422)는 실패로 세지 않는다 — 상대는 살아 있고 우리 프롬프트 문제다 |
| 트렌드 수집 | 연속 3회 | 10분 | **출처별로 하나씩**(깃허브·HN·dev.to·Lobsters·GeekNews) |
| 고용24 | 연속 3회 | 5분 | 응답은 왔지만 API가 오류 코드를 준 경우(키 만료·한도)도 실패로 센다 |

트렌드를 출처별로 나눈 이유: 깃허브가 403을 주는 동안 다른 출처 수집까지 멈추면 안 되고, 반대로
깃허브에만 같은 실패를 매번 반복하며 타임아웃만큼 기다릴 이유도 없다. 끊긴 출처는 그 회차에서 조용히
건너뛴다. `source(name, fetcher)`가 모든 출처를 감싸는 한 지점이어서 거기 한 곳만 고쳤다.

### 설계를 한 번 되돌렸다

처음에 호출 한도를 `static`으로 뒀더니 **테스트 수백 개가 같은 버킷을 비워** 뒤쪽 `GroqLlmClientTest`가
429로 깨졌다. 운영은 JVM 전체 공유가 맞지만(한도는 API 키 단위) 인스턴스 필드로 바꿔 기본값만 공유
객체로 두고 테스트가 자기 것을 끼우게 했다. 설정을 바꾼 사본(`withSettings`·`withRetryPolicy`)도
같은 한도·서킷을 이어 쓴다 — 같은 API 키라 따로 세면 안 된다.

### 시간을 주입받게 만든 이유

`sleep` 없이 테스트하려면 시간을 앞으로 돌려야 한다. 테스트가 느려지면 1,016개가 같이 느려진다.
`AppClock`은 시뮬레이션용 날짜 기반이라 밀리초 단위에는 맞지 않아 `LongSupplier`를 따로 받는다.

## 10. 스펙 아카이브 검색 — MySQL FULLTEXT(ngram) (`1874c4e`)

### 먼저 "되는지" 확인했다

사용자가 "키워드 위주 하이브리드 검색이 되는지 보고 된다면 적용"이라고 했으므로 실측부터 했다.
공유 DB: **MySQL 9.7.2 · ngram 플러그인 ACTIVE · `ngram_token_size = 2`**.

| 검색어 | 결과 |
| --- | --- |
| `스프링` | 스프링 부트 · 스프링 프레임워크 ✅ |
| `프링` (중간 글자) | 둘 다 ✅ — **ngram이라 부분 일치가 된다** |
| `Spring` (영문) | Spring Boot ✅ |
| `스프링 부트` (자연어 모드) | 점수순 — 부트 1.06, 프레임워크 0.46 ✅ |
| `자` (한 글자) | 0건 ❌ — token_size가 2라 인덱스에 토큰이 없다 |

`EXPLAIN`으로 `Full-text index search on TECH_ARTICLE using ft_tech_article_text`까지 확인했다.

### 왜 LIKE가 아닌가

`LIKE '%키워드%'`는 앞에 와일드카드가 있어 인덱스를 전혀 타지 못하고, 본문이 `TEXT`라 글이 쌓일수록
전수 조회가 된다. 그리고 기본 FULLTEXT 파서는 공백으로 단어를 잘라 한국어에서 "프링"으로 "스프링 부트"를
못 찾는다 — **ngram 파서가 필요한 이유가 이것이다.**

### 한 글자만 LIKE 폴백

인덱스를 못 타지만 "검색은 되는데 한 글자만 안 된다"가 더 이상하다. `token_size`를 1로 낮추는 선택도
있었지만 인덱스가 급격히 커지고 흔한 글자가 전부 걸려 느려진다.

### 사용자 입력을 검색식으로

낱말마다 `+`와 따옴표를 붙여 "모두 포함"으로 만들고, 입력에 든 연산자(`+ - * ~ < > ( ) " @`)는 전부
지운다 — 안 지우면 "C++"의 `+`가 연산자로 해석돼 구문 오류나 엉뚱한 결과가 된다. `#`은 연산자가
아니라 남긴다("C#"은 실제 기술명이다). "C++"처럼 연산자를 지우면 한 글자가 되는 입력은 자연히
LIKE 폴백이 받는다.

### 관리자 회원 검색에는 넣지 않았다

`USERS`는 쓰기가 잦은 표라 FULLTEXT 인덱스의 유지 비용이 붙는다. 관리자 검색은 호출이 드물고 대상
행도 적어 LIKE로 충분하다 — **가장 바쁜 표에 인덱스를 더할 이유가 없다.**

## 14. 오늘의 교훈

**알고리즘은 "쓰려고" 넣으면 티가 난다.** 8개 전부 이미 있는 화면의 아쉬운 점에서 출발했고, 그래서
각각 "왜 이게 필요한가"에 한 줄로 답할 수 있다. 발표에서 설명할 수 있는 이유도 거기에 있다 —
