## 2. 항목 0 — 완료 체크 후 로드맵 화면이 맨 위로 튕기는 문제 (`03674de`)

**문제**: 로드맵 단계를 완료 체크하면 폼 제출로 페이지가 새로고침되면서 `.journey-track-scroll`

페이지 로드 시 복원하는 스크립트를 추가했다. `document.addEventListener('submit', ..., true)`로
아무 폼이 제출되기 직전에 현재 스크롤 위치를 저장한다 — capture 단계라 어떤 완료 버튼을
눌러도 놓치지 않는다.

## 5. 항목 2 — JOB_SKILL_TREND을 LLM 없이 채우기 (`dea0f92`)

**배경**: `JOB_SKILL_TREND`(직무별 기술 언급 시계열)를 원래 LLM으로 채울 계획이었는데, 토큰
비용이 문제였다. 대신 이미 수집돼 있던 `JOB_POSTING.tech_stack`(917건, 700건이 tech_stack
있음, 4개월치)을 직접 집계하는 방식으로 바꾸기로 했다(팀 동의).

**구현**: `JobSkillTrendService.refreshAll()` — 공고를 `(job_id, period_ym)`로 묶고, 각 공고의
`tech_stack`을 콤마로 쪼개 `SkillMatcher`(정확 일치→별칭→편집거리)로 기술명을 SKILL에 매칭,
기술별 언급 공고 수·비율을 계산해 `JOB_SKILL_TREND`에 upsert한다.

**성능 버그 발견 및 수정**: 처음 만들고 실제 917건에 대고 돌렸더니 8분 넘게 끝나지 않았다.
원인은 `FuzzyNameMatcher`가 매칭 실패한 토큰마다 원격 DB의 SKILL·SKILL_ALIAS **전체 테이블을
매번 다시 긁어오는** 구조였던 것 — 같은 토큰("Java" 등)이 공고 수백 건에 반복 등장하는데
매번 새로 원격 조회를 하니 왕복 지연이 누적됐다. 배치 안에서 토큰별 매칭 결과를 캐싱하도록
고치자 정상적으로 끝났고, 실제로 690건이 정확한 값(예: 백엔드 개발자 Java 40.23%, AWS 37.89%)
으로 집계되는 걸 실제 DB 쿼리로 확인했다.

## 6. 항목 1 — SPEC_SCORE_HISTORY 실제 연결 (`f8cddd1`, `2be1111`)

DAO/DTO만 있고 아무도 호출하지 않던 테이블이었다. `db-design.md` 설계 판단을 다시 확인해보니
이 테이블은 애초에 "뭘 했는지"를 저장하는 게 아니라 **완성도 점수(숫자)의 시계열 스냅샷**
전용으로 설계돼 있었다 — 다른 테이블을 참조하는 FK가 없다.

**구현**: `SpecScoreService` 신설.
- `completeness_score`(0~100) = 목표 직무 격차 분석 충족률(`GapAnalysisDto.matchRate`) 40점 +
  스펙 총량(자격증 최대 5개×4점=20, 프로젝트 최대 5개×4점=20, 기술 최대 20개×1점=20) 60점.
  목표 직무가 없으면 40점 몫을 스펙 총량 쪽으로 재배분(60→100).
- `SpecScoreScheduler`: `TrendScheduler`와 같은 패턴으로 매일 00:00 전체 사용자 스냅샷(멱등).
- `DashboardServlet`: 접속 시 오늘 스냅샷 없으면 기록 + 완성도 게이지 표시.
- `InsightsServlet`/`insights.jsp`: "또래 비교" 카드를 실제 데이터로 교체, 비교 데이터 없으면
  안내 문구로 대체.

**보류한 것**: 또래 비교용 시연 데이터(`is_seed=TRUE`)는 `SPEC_SCORE_HISTORY.user_id`가
`NOT NULL` FK라서 가짜 `USERS` 계정도 같이 만들어야 하는 문제가 있어 이번엔 넣지 않기로
했다. 실사용자끼리만 비교하고, 없으면 안내만 보여준다. 이유와 나중에 풀 방법 3가지는
`docs/future-expansion.md` 3번 항목에 적어뒀다.

**헷갈리기 쉬운 부분 — 별도로 기록**: `SPEC_SCORE_HISTORY` 연결과 "면접관에게 실제로 뭘
했는지 보여주는 것"(FR-81 이력 타임라인)은 다른 기능이다. 후자는 `interviewer-view.jsp`의
"이력 타임라인"·"성장 잠재력" 섹션인데, **아직도 100% 하드코딩된 가짜 예시 데이터**다.
실제로 연결하려면 `ShareViewServlet`의 진짜 토큰→사용자 검증부터 먼저 만들어야 한다(지금은
`"demo"` 문자열 하나만 유효 취급). 이것도 `docs/future-expansion.md` 4번 항목에 적어뒀다.

## 7. 항목 2-1 — JOB_SKILL_TREND 수동 재집계용 임시 관리자 화면 (`388f5d1`)

"일단 임시로 정해서 만들어줘 보면서 수정하게"라는 지시대로, 정식 관리자 권한 체계 없이
로그인만 하면 접근 가능한 임시 화면을 만들었다: `/admin/job-skill-trend`.

- GET: 현재 적재 현황(전체 행 수·집계된 월 수·최신 집계월) + 최신월 상위 15건 표시.
- POST: `JobSkillTrendService.refreshAll()`을 수동으로 실행하고 결과 건수를 배너로 보여준다.
- **실제 배포로 검증**: 로컬 Tomcat 10.1.60에 WAR를 배포하고 회원가입→로그인→curl로 GET/POST를
  직접 호출해 확인했다 — GET에서 기존 690건이 보이고, POST로 다시 690건이 정상 갱신됐다.
  테스트 계정은 확인 직후 공유 DB에서 삭제했다.
- 정식 배포 전에 접근 제한(관리자 권한 구분)을 다시 검토해야 한다고 코드 주석에 남겨뒀다.

**후속 — 접근 제한 추가 (`88ea4e4`)**: "테스트 용도인데 admin 아이디로 로그인하면 들어가게
하는 건 어때?"라는 제안을 받아, 로그인만 하면 누구나 들어가던 걸 `ADMIN_LOGIN_ID`(.env, 기본값
`"admin"`)와 세션 로그인 아이디가 일치할 때만 통과하도록 좁혔다. `USERS`에 role 컬럼을 추가하는
정식 권한 체계는 스키마 변경이라 지금은 안 하기로 함.

**검증 중 발견한 것**: 처음 재배포해서 확인하려는데 로컬 Tomcat이 응답은 하는데 `/spec-odyssey/`
전체가 404였다 — 원인은 내가 띄운 `C:\Tomcat\apache-tomcat-10.1.60` 인스턴스가 아니라
**IntelliJ가 별도 catalina.base로 관리하는 Tomcat이 이미 8080 포트를 쓰고 있었던 것**(아마
내가 앞서 shutdown한 뒤 사용자가 IntelliJ에서 따로 띄운 것으로 추정). 포트 충돌로 내 새 배포가
반영되지 않는 상태라, 남의 세션을 건드릴 수 있어 일단 중단하고 확인을 요청했다. 사용자가 그
Tomcat을 끈 뒤 재배포해서 정상 검증했다 — 일반 계정 GET → 403, `admin` 계정 GET → 200(690건
정상 표시). 두 테스트 계정 모두 확인 후 공유 DB에서 삭제, 로컬 Tomcat도 내리고 배포 파일 정리.
