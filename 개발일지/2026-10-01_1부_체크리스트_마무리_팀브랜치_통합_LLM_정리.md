# 체크리스트 3·4·10 마무리, 팀 브랜치 4개 통합, LLM 테스트 성능 문제 해결

날짜: 2026-10-01
관련 요구사항: FR-46·71·81~86·91·92·101·102·111

## 1. 개요

전날(09/30) 정리한 12개 체크리스트 중 남아있던 3번(ERD 재검토로 나온 미구현 테이블)을 끝까지
처리했고, 4번(CERT 증빙서류 검증 방법)을 결론 냈다. 그 직후 팀원 4명(seongwon·donghyeon·
youngjun·kangdain)이 거의 같은 시간대에 같은 기능을 독립적으로 구현해서 main에 올린 걸
발견해, 충돌 4건을 정리해서 내 브랜치와 main에 합쳤다. 마지막으로 테스트가 매번 실제 Groq를
불러 1시간 넘게 걸리고 Groq 무료 한도를 갉아먹던 문제를 공용 LLM 클라이언트로 바꿔서 해결했다.

## 2. 3번 — ERD 감사로 찾은 미구현 테이블 8개 전부 연결

`grep`으로 전체 테이블과 그 테이블을 쓰는 DAO 호출처 수를 대조하는 식으로 감사했다
(`grep -h "^CREATE TABLE" sql/*.sql`로 테이블 목록 뽑고, 각 DAO를 `new`하는 곳이 0건인
테이블을 찾음). "DAO만 있고 아무도 안 쓰는" 테이블 8개가 나왔고, 담당자들이 이미 다른
작업으로 넘어갔다고 해서 전부 직접 구현했다.

- **SHARE_LINK·SHARE_LINK_VIEW_LOG**(FR-85·86) — 공유 링크 발급·목록·중단·삭제.
  `SecureRandom` 256비트 → Base64URL 토큰.
- **면접관 뷰**(FR-81·85, NFR-9) — 토큰으로 지원자 이력(전공·자격증·프로젝트·기술스택) 조회,
  로그인 없는 "ownerless" 접근이라 세션 대신 토큰 활성·만료 여부로 권한을 확인.
- **면접관 비교/장바구니**(FR-82·83) — `EvaluationSessionDao` 등 이미 있던 DAO 스캐폴딩 위에
  실제 로직(후보 담기·기준 가중치·적합도 계산) 연결. 쿠키의 `session_token`으로 소유를
  대신 증명(계정 없는 면접관용).
- **CERT_SCHEDULE → D-day 자동 생성**(FR-71) — 로드맵이 추천한 자격증에 가까운 시험 회차가
  있으면 자동으로 D-day 알림을 만듦. **4절에서 다시 나오지만, 이건 나중에 되돌렸다.**
- **AI_USAGE_LOG**(FR-101·102, 명세서 [선택] 최하위 우선순위) — 자기기입 CRUD만 구현,
  "활용 스타일 프로파일링"(자동 분류)은 범위 밖으로 남김.
- **JOB_BENCHMARK_SPEC**(FR-46) — 실제 합격자 데이터가 없어 Groq LLM이 "이 직무는 보통 이런
  단계를 밟는다"를 ENTRY~EXPERT 4단계로 생성, 한 번 생성하면 캐싱해서 재사용(On-demand+캐싱,
  TD-2 설계 원칙).

커밋: `c08653d`, `b05a427`, `d1aaf0c`, `0643a32`, `b922d4b`

## 3. 4번 — CERT 증빙서류, 아무 파일이나 넣어도 통과되는 문제

코드를 보니 이건 버그가 아니라 팀이 이미 "별도 자동 판정 규칙 없이 서류 첨부 자체를 증빙으로
신뢰한다"고 결정해둔 설계였다(PROJECT·CORE/ADVANCED SKILL 단계도 같은 트레이드오프). 사용자에게
세 가지 선택지(① 양심에 맡기고 유지 ② 파일 형식·용량 같은 가벼운 체크 추가 ③ 관리자 승인
큐 도입)를 물었고, **① 유지 + 제출 전 "이 문서는 면접관에게 노출됩니다" 확인창 추가**로
결론 났다. 다만 그 안내가 거짓말이 안 되려면 실제로 보여줘야 해서, 면접관 뷰(2절의
`ShareDocumentServlet`)에 CERT 증빙 서류를 실제로 열어볼 수 있는 링크까지 같이 만들었다.

## 4. 팀 브랜치 4개 통합 — 같은 기능을 서로 모르고 각자 구현한 문제

### 4-1. seongwon — 공유 링크·D-day (main에 PR로 먼저 올라감)

seongwon이 2절의 공유 링크·면접관 뷰·D-day를 **나와 완전히 독립적으로, 거의 같은 시간에**
구현해서 main에 PR #9로 먼저 합쳤다. 확인해보니:

- `ShareLinkService` 클래스명까지 똑같은데 내용이 다름 — 자동 병합이 안 되는 수준.
- D-day는 seongwon이 먼저 만들었다가(FR-71), **"자격증 시험 일정은 기관마다 출처가 달라
  자동 수집이 신뢰하기 어렵다"**는 이유로 바로 다음 커밋에서 자동 등록 자체를 걷어내고
  사용자가 직접 추가하는 방식으로 팀 결정을 확정해버렸다 — 내가 막 만든 자동 생성 기능과
  정반대 결론.

사용자 확인 후 처리 방침: **D-day 자동 생성은 완전히 제거**(`DdayAutoGenerationService`·
연결 코드·placeholder 시드 데이터 전부 삭제, `496347a`). **공유 링크/면접관 뷰는 seongwon
쪽을 채택**하고 내 `ShareLinkService`·`InterviewerViewService`는 버렸다. 다만 seongwon
쪽엔 없던 내 것 두 가지(면접관 비교/장바구니, CERT 증빙서류 노출)는 seongwon의
`ShareViewService`/`ShareViewDto` 구조 위로 그대로 옮겨 붙였다(`ShareViewDto.TimelineItem`에
`documentId` 필드 추가, `ShareDocumentServlet` 신설). `git merge origin/main --no-commit`으로
받은 뒤 겹친 파일 8개를 `git checkout --theirs`로 seongwon 쪽을 선택하는 식으로 정리했다
(`011ea21`).

### 4-2. donghyeon — 자소서·이력서 첨삭 (FR-91·92·112)

`git merge origin/donghyeon`은 충돌 없이 깨끗하게 들어왔다. `GroqLlmClient`(LlmClient 실제
구현체)·`ResumeFeedbackService`(날조 차단, 본문에 없는 수치·기술명은 `[수치]`/`[사용한 기술]`
로 치환)·1:1 비교 화면. 무관한 `helloworld.html`(리트코드 검색용 로컬 스크래치 파일로 보임)은
이번 머지에서 빼고 받았다(`d120e70`).

### 4-3. youngjun — SkillCatalog 매칭 캐시 + LLM 결과 캐싱

`EmbeddingMatcher`·`FuzzyNameMatcher`·`EmbeddingBackfillService`를 매번 DB 전체를 긁는 대신
메모리 캐시(`SkillCatalog`)로 바꾼 부분은 그대로 받았다(매칭 규칙·임계값 0.75는 안 바뀜).
`CachingLlmClient`(LLM 응답 7일 캐싱, 실패 시 직전 성공 결과로 대체, FR-111·112)도 추가로
받았다 — `LlmClient` 인터페이스에만 의존해서 어떤 구현체를 넣어도 동작한다.

**충돌**: donghyeon도 같은 날 `GroqLlmClient`를 독자적으로 구현해서, 두 사람의 같은 이름
클래스가 겹쳤다. 처음엔 donghyeon 쪽(이미 ResumeFeedbackService가 실제로 쓰고 있었음)을
남겼다가(`0ffdc10`), 이후 사용자 지시로 **youngjun 쪽으로 재교체**했다 — `LlmRetryPolicy`로
재시도 규칙을 분리해뒀고 로컬 가짜 서버로 재시도·실패 경로를 꼼꼼히 테스트해둔 쪽이 더
탄탄하다고 판단. donghyeon 쪽에만 있던 기능(자소서 첨삭이 트렌드 수집과 Groq 무료 한도를
안 나눠 쓰게 하는 **기능별 모델 분리**)은 잃지 않게
`GroqLlmClient.fromConfig(modelConfigKey, defaultModel)` 오버로드로 옮겨 붙였다(`abb33a5`).
이건 내 브랜치 안에서의 임시 선택이고, youngjun이 main에 PR을 올릴 때 같은 충돌이 다시 날
거라 최종 선택은 팀이 그때 한 번 더 정해야 한다.

## 6. Groq 호출이 한꺼번에 몰리는 문제 — 공용 쓰로틀

전체 테스트를 한 번에 돌리면 `ProjectIdeaService`·`TrendLlmService`·`JobBenchmarkSpecService`가
전부 같은 Groq 엔드포인트로 몰려서 429(요청 제한)가 났다. 호출부마다 막는 대신
`ExternalApiClient.send()`에서 Groq 엔드포인트로 가는 요청만 동시 1건 + 최소 1.5초 간격으로
묶는 공용 세마포어를 추가했다(`88ce8c0`).

## 7. ProjectIdeaService를 GroqLlmClient로 전환 — 테스트 1시간 → 3분

팀원(youngjun)이 "`RoadmapServiceTest`가 매번 실제 Groq를 불러서 429가 나면 20·40·60초씩
기다리고, 전체 테스트가 1시간 넘게 걸리고 Groq 한도도 같이 소모된다"고 알려줬다. 또
"`RoadmapServiceTest`(4건)·`GapAnalysisServiceTest`(가끔 1건)가 tearDown에서 SKILL을 지울 때
FK 오류가 난다"는 제보도 같이 왔다.

- `ProjectIdeaService`가 직접 돌리던 HTTP 재시도 로직을 걷어내고 공용
  `LlmClient`(`GroqLlmClient`+`LlmRetryPolicy`)에 맡겼다. 생성자로 `LlmClient`를 주입할 수
  있게 열어서 테스트가 `StubLlmClient`로 바꿔 끼울 수 있게 했다. `RoadmapService`도
  `ProjectIdeaService`를 주입하는 생성자를 추가.
- `RoadmapServiceTest`·`GapAnalysisServiceTest`가 `StubLlmClient`를 쓰도록 바꿨다.
- **FK 오류 직접 조사**: 의심됐던 테스트 메서드 4개를 전부 열어서 확인했는데, finally에서
  정리가 다 제대로 되고 있었다 — 테스트 코드 자체엔 정리 누락이 없었다. 원인은 몇 분씩
  블로킹하던 실제 Groq 재시도 호출 쪽으로 보인다(정확한 메커니즘까지는 특정 못 했지만,
  LLM을 스텁으로 바꾸자 완전히 사라졌고 두 번 반복 실행해도 재현 안 됨).
- `ProjectIdeaServiceTest` 신설 — 검증·길이제한 로직을 `StubLlmClient`로 직접 테스트.

결과: 전체 테스트 스위트가 **1시간 넘던 게 2분 49초**로 줄었다(`2b3678d`).
