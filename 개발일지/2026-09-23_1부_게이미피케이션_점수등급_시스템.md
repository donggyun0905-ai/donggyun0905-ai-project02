# 1부 — 게이미피케이션(점수·등급) 시스템 구축

날짜: 2026-09-23
관련 커밋: `9c72a95`

## 1. 개요

원래 팀 역할 분담(①격차분석·②로드맵·③직무발굴)에는 없던 작업이다. 사용자가 가지고 있던 나침반 로고 이미지 하나를 5단계 등급 배지로 쓰고 싶다고 해서, 점수·등급 체계 전체를 새로 설계하게 됐다. "차례대로 하자"는 원칙에 따라 다음 순서로 진행했다: ①등급 이름/구간 확정 → ②로고 이미지 준비 → ③시드 데이터 적용 → ④점수 적립 로직 설계(같이 검토) → ⑤화면 표시.

## 2. LEVEL_TIER 5단계 확정 및 시드

`requirements.md`의 TD-5(b) 추천안을 그대로 채택했다(팀 확정, 별도 협의 없이 초안 그대로 진행).

| 등급 | 점수 구간 | 타이틀 | 문제 난이도 매핑 |
|---|---|---|---|
| 비기너 | 0~499 | 뉴비 항해사 | 0~1 |
| 취준생 | 500~1499 | 견습 항해사 | 1~2 |
| 실전러 | 1500~2999 | 정식 항해사 | 2~3 |
| 취뽀 임박 | 3000~4999 | 선장 | 3~4 |
| 취뽀 | 5000~ | 전설의 선장 | 4~5 |

`problem_level_min/max`는 지금 당장 쓰이는 곳은 없지만, FR-52("문제 난이도를 사용자 현재 수준에 맞춰 조정")를 담당할 사람이 그대로 가져다 쓸 수 있게 스키마에 이미 있던 값을 살렸다.

"비기너는 0,1로"라는 지시가 점수 구간을 말하는 건지 문제 난이도를 말하는 건지 헷갈려서, 추측 대신 `AskUserQuestion`으로 확인했다 — 문제 난이도(`problem_level_min/max`) 쪽이 맞았다. 점수 구간을 잘못 넣었으면 등급 전체가 틀어질 뻔했다.

`sql/04_seed_extended.sql`로 적용, `spec_odyssey_test` DB에 5행(id 18~22) 확인.

## 3. 로고 이미지 5분할

사용자가 준 이미지(`T.png`, 1880×406, 나무→청동→은→금→틸골드 순서의 나침반 5개가 나란히)를 PowerShell `System.Drawing`으로 잘라 `tier-1-beginner.png` ~ `tier-5-legend.png`로 분리했다. 처음엔 `WEB-INF/views/common/image/`에 있어서 서블릿 스펙상 직접 URL 접근이 안 되는 위치였다 — `src/main/webapp/image/`로 옮겨야 한다고 안내했고, 사용자가 직접 옮겼다.

## 4. ScoreService — 범용 구조로 설계

TD-5 스코어링은 신호 종류가 5개다(ROADMAP +100, QUIZ +10~30, PROBLEM +5, DOCUMENT +30, SELF_CHECK +0~50). 지금 당장은 ROADMAP만 쓰지만, 나머지를 만들 담당자도 그대로 재사용할 수 있도록 `signal_type`을 파라미터로 받는 구조로 만들었다.

- `award(userId, signalType, refId, points)` — 단독 호출용, 자체 트랜잭션.
- `awardWithinTransaction(conn, ...)` — 다른 서비스(RoadmapService)의 트랜잭션에 끼워 넣을 때. "단계 완료 처리"와 "점수 적립"이 한 트랜잭션이어야 부분 반영(점수만 들어가고 완료 표시는 안 되는 등)을 막을 수 있다.
- `SCORE_LOG`에 `UNIQUE(user_id, signal_type, ref_id)`가 있어서, 같은 이벤트로 두 번 호출해도(중복 클릭 등) `ScoreLogDao.existsByUserSignalRef`로 먼저 확인하고 조용히 무시한다.
- 점수는 상한 없이 계속 쌓이는 게임식 설계라 **완료 취소해도 깎지 않는다** — `SCORE_LOG`가 append-only인 이유이기도 하다.

## 5. `RoadmapService.completeStep`에 연동

로드맵 단계 완료(FR-36)와 점수 적립을 한 트랜잭션으로 묶었다. 완료 취소해도 이미 받은 점수는 유지되고, 같은 단계를 다시 완료 처리해도(중복 클릭) 중복 적립되지 않는다.

## 6. 검증 중 잡은 버그 — 소유자 아닌 완료 요청에도 점수 적립 시도

`RoadmapStepDao.updateCompleted`는 `WHERE rs.id=? AND r.user_id=?`로 소유자를 확인하는데, 원래 반환값이 `void`였다. 그래서 `completeStep`은 실제로 행이 갱신됐는지 모른 채 무조건 점수를 적립하려고 시도했다 — 다른 사용자 id로 완료 체크를 시도하면 DB엔 아무 변화가 없는데도 `scoreService.awardWithinTransaction`이 존재하지 않는 `user_id`로 `SCORE_LOG`에 insert를 시도해서 `SQLIntegrityConstraintViolationException`(FK 위반)이 터졌다. 기존에 있던 "다른 사용자 id로는 완료체크가 안된다" 테스트가 이걸 잡아냈다.

**수정**: `updateCompleted`가 `int`(영향받은 행 수)를 반환하도록 바꾸고, `completeStep`은 그 값이 0보다 클 때만 점수를 적립하도록 고쳤다.
