## 1. 개요

10/11에 임시 터널로 시연 가능성은 확인했다. 오늘은 실제로 띄우는 날이다.

## 2. 한 일 — 전부 설정

### 2-1. cloudflared 설치

```powershell
winget install --id Cloudflare.cloudflared
```

`2026.10.0`, `C:\Program Files (x86)\cloudflared\cloudflared.exe`.
설치 직후 기존 터미널에서는 `cloudflared` 를 못 찾는다 — PATH가 갱신되기 전이라
**새 PowerShell 창**을 열어야 한다.

### 2-2. RemoteIpValve — 넣을 곳이 두 군데였다

10/11 일지에는 "`conf\server.xml` 에 한 줄"이라고 적었는데, 실제로 돌고 있는 톰캣을
들여다보니 그렇게 간단하지 않았다.

```
catalina.home = C:\Jsp\apache-tomcat-11.0.25
catalina.base = C:\Users\...\JetBrains\IntelliJIdea2026.2\tomcat\50cb1b62-...
```

**톰캣이 실제로 읽는 `server.xml` 은 `CATALINA_BASE/conf` 쪽이다.**
IntelliJ는 실행 설정마다 자기 전용 base 디렉터리를 따로 만든다 — 이 PC에만 14개가 있었다.
그래서 `CATALINA_HOME` 쪽만 고치면 적용되지 않을 수 있다.

IntelliJ가 다음 실행 때 base의 `server.xml` 을 다시 만들 가능성이 있어서 **양쪽 다** 넣었다.
둘 중 어느 쪽이 쓰이든 걸리게 하려는 것이다. 각각 백업을 먼저 떴다.

```xml
<Valve className="org.apache.catalina.valves.RemoteIpValve"
       remoteIpHeader="X-Forwarded-For"
       protocolHeader="X-Forwarded-Proto"
       protocolHeaderHttpsValue="https" />
```

재시작 뒤 확인한 결과 **base의 밸브가 살아남았다.** IntelliJ가 덮어쓰지 않았다.

### 2-3. 컨텍스트 경로를 `/` 로

IntelliJ > Run > Edit Configurations > Tomcat > **Deployment** 탭 > Application context → `/`

바꾸기 전에는 `conf\Catalina\localhost\spec_odyssey.xml` 에 `path="/spec_odyssey"` 로
배포돼서 공개 주소 뒤에 그걸 붙여야만 열렸다. 바꾼 뒤 `ROOT.xml` 로 바뀌고 `/` 가 200이 된다.

## 3. 밸브가 "진짜로" 동작하는지 어떻게 확인했나

터널을 띄우기 전에 로컬에서 확인하고 싶었다. cloudflared가 보내는 헤더를 직접 흉내 내서
같은 주소로 두 번 요청하고 **응답의 `Set-Cookie` 를 비교**했다.

| 요청 | `Set-Cookie` |
| --- | --- |
| 헤더 없이 (평소 로컬) | `JSESSIONID=…; Path=/; HttpOnly; SameSite=Lax` |
| `X-Forwarded-Proto: https` 를 붙여서 | `JSESSIONID=…; Path=/; **Secure**; HttpOnly; SameSite=Lax` |

톰캣은 `request.isSecure()` 가 true일 때만 세션 쿠키에 `Secure` 를 붙인다.
`Secure` 가 붙었다는 건 밸브가 scheme을 https로 바로잡았다는 뜻이고, 같은 값으로
`getScheme()` · `getServerPort()` 도 바뀐다 — 즉 `ShareLinksServlet.shareBaseUrl()` 이
`https://…/share/…` 를 만든다는 것이 간접적으로 증명된다.

**리다이렉트 `Location` 으로는 확인할 수 없었다.** 서블릿 6.0부터 상대 경로를 그대로
보낼 수 있어서 `/login` 만 돌아온다. 쿠키가 더 정확한 신호다.

터널을 띄운 뒤 공개 주소로 다시 확인했을 때도 `Secure` 가 붙어 있었다.

## 4. 코드를 넣었다가 되돌린 기록

`META-INF/context.xml`(WAR 안)에 밸브를 넣으면 PC마다 `server.xml` 을 고칠 필요가
없어진다고 판단해서 커밋 `df5a2e0` 을 만들었다. 테스트도 5개 붙였다.

되돌린 이유는 **발표 전날이기 때문**이다. 기술적으로 맞는 변경이라도, 이미 검증이 끝난
동작에 새 변수를 넣는 건 그날 할 일이 아니다. `git revert --no-edit df5a2e0` 으로
되돌렸고(push된 커밋이라 reset이 아니라 revert), 테스트 1,060개 통과를 확인한 뒤 push했다.

되돌린 뒤 `git diff origin/main HEAD` 가 비어 있는 것으로 **파일 내용이 완전히 원복됐음**을
확인했다. 커밋 기록만 남고 코드는 한 글자도 바뀌지 않았다.

발표가 끝나면 다시 검토할 만한 변경이다. 그때는 `server.xml` 을 PC마다 고치는 일이 없어진다.

## 5. `clean` 으로 서비스를 두 번 끊었다 — 가장 큰 교훈

### 5-1. 1차 — revert 검증하다가

되돌린 게 맞는지 보려고 `mvn clean test` 를 돌렸다. 그런데 톰캣이 바라보는 배포 경로가
`C:\Project02\target\spec-odyssey` 였다. `clean` 이 `target/` 을 통째로 지우면서
**배포본이 사라졌고 사이트 전체가 404가 됐다.**

`./mvnw package -DskipTests` 로 복구했다. 12초 걸렸다.

### 5-2. 2차 — 잔재 파일을 없애려다가

머지 뒤 배포본을 확인해 보니 이런 게 있었다.

```
Only in target/spec-odyssey/WEB-INF/classes/.../service: ResumeFeedbackService$DocType.class
```

`d701f71` 이 없앤 옛날 클래스인데 배포본에 남아 있었다. IntelliJ는 **바뀐 파일은
덮어쓰지만 없어진 파일은 지우지 않는다.** 그래서 깨끗하게 다시 만들려고
`mvn clean package` 를 돌렸는데 — **톰캣이 켜져 있었다.**

```
Failed to delete C:\Project02\target\spec-odyssey\WEB-INF\lib\mysql-connector-j-8.4.0.jar
```

톰캣이 그 jar를 열어 두고 있어서 지울 수 없었다. 문제는 **clean이 거기서 멈추기 전에
이미 `WEB-INF/views` 와 `web.xml` 을 지운 뒤**였다는 것이다. 반쯤 지워진 상태로 실패했고
사이트는 다시 404가 됐다.

마침 그때 톰캣을 멈춘 덕에 jar 잠금이 풀렸고, 그제서야 `clean package` 가 제대로 돌았다.

### 5-3. 규칙

> **`clean` 은 톰캣을 끈 상태에서만 돌린다.**

켜져 있으면 두 가지가 동시에 터진다.
- **파일 잠금** — 실행 중인 톰캣이 jar를 잡고 있어 삭제가 실패한다
- **반쯤 지워진 상태** — clean은 실패해도 되돌려 주지 않는다. 지운 데까지는 지워진 채로 끝난다

결과를 보고 나서 복구하는 것보다, 끄고 돌리는 게 훨씬 싸다.

## 6. `mvn clean` 이 뭔가 — 빌드 생애주기

처음 보는 명령이라 정리해 둔다.

### 6-1. `target/` 폴더

Maven은 빌드 결과를 전부 `target/` 아래에 모은다. **소스가 아니라 산출물**이다.

```
target/
├── classes/              .java 를 컴파일한 .class
├── test-classes/         테스트 컴파일 결과
├── spec-odyssey/         WAR 를 펼쳐 놓은 모습 ← 톰캣이 이걸 바라본다
├── spec-odyssey.war      압축한 배포 파일
└── surefire-reports/     테스트 결과 리포트
```

`target/` 은 `.gitignore` 에 있다. 소스만 있으면 언제든 다시 만들 수 있기 때문이다.

### 6-2. 생애주기(lifecycle)와 단계(phase)

Maven 명령은 "단계 이름"이다. 어떤 단계를 부르면 **그 앞 단계가 전부 먼저 실행된다.**

```
validate → compile → test → package → verify → install → deploy
```

- `mvn compile` — 컴파일만 (`target/classes`)
- `mvn test` — 컴파일 + 테스트 실행
- `mvn package` — 위 전부 + WAR 만들기 (`target/spec-odyssey`, `.war`)

그래서 `mvn package -DskipTests` 는 "테스트는 건너뛰고 WAR까지 만들어라"가 된다.

### 6-3. `clean` 은 그 줄에 속하지 않는다

`clean` 은 **별도의 생애주기**다. 하는 일은 하나, **`target/` 폴더를 통째로 삭제**한다.

그래서 `mvn clean package` 는 "지우고 → 처음부터 다시 만들어라"다.
`clean` 없이 `package` 만 하면 **있던 파일 위에 덮어쓴다.**

### 6-4. 그럼 언제 `clean` 이 필요한가

덮어쓰기만으로는 **없어진 파일이 안 지워진다.** 5-2의 `ResumeFeedbackService$DocType.class`
가 정확히 그 경우다. 소스에서는 사라졌는데 `target/` 에는 남는다.

보통은 죽은 파일이라 무해하다. 하지만 이런 때 문제가 된다.
- 지워진 클래스를 아직 참조하는 코드가 어딘가 남아 "되긴 되는데" 상태가 된다
- 옛 리소스 파일이 새 것보다 먼저 읽혀 수정이 반영되지 않는다
- "내 PC에서는 되는데"의 흔한 원인이 된다

그래서 **발표·배포 직전처럼 결과가 정확해야 할 때**는 `clean` 을 한 번 쓴다.
평소 개발 중에는 필요 없다 — 느리기만 하다.

### 6-5. 우리 프로젝트에서의 주의

| 하려는 것 | 명령 | 톰캣 |
| --- | --- | --- |
| 코드 고치고 확인 | IntelliJ Run (자동 빌드) | 켜도 됨 |
| 테스트만 | `.\mvnw test` | 켜도 됨 |
| 배포본 갱신 | `.\mvnw package -DskipTests` | 켜도 됨 (무중단) |
| **깨끗하게 새로** | `.\mvnw clean package -DskipTests` | **반드시 끄고** |

`mvnw` 는 Maven 자체를 저장소에 포함시킨 실행기다. 팀원이 Maven을 따로 설치하지
않아도, 그리고 **모두 같은 Maven 버전**으로 빌드하게 해 준다. `mvn` 대신 쓰면 된다.

      `Select-String RemoteIpValve "$env:LOCALAPPDATA\JetBrains\...\conf\server.xml"`
- [ ] 공유 링크 주소에 `:8080` 이 안 붙는지
- [ ] 절전 끄기 `powercfg /change standby-timeout-ac 0`
- [ ] 세션 30분 — 시연 직전에 다시 로그인
- [ ] 끝나면 cloudflared 창 닫기 (켜져 있는 동안 누구나 들어온다)

알아두면 좋은 한계 (전부 설정·운영으로 해결, 코드 변경 불필요):

- **100MB** — 클라우드플레어 무료 플랜이 요청 본문을 자른다. 캐릭터 설치 파일 한도는
  200MB라, 넘으면 터널 말고 `http://localhost:8080/admin/companion` 으로 직접 올린다
- **100초** — 가장자리가 100초에서 524를 돌려준다. LLM을 기다리는 화면이 여기에 가까워질 수 있다
- **스케줄러 중복** — `@WebListener` 6개가 톰캣마다 돈다. 같은 공유 DB를 보는 인스턴스가
  여럿이면 같은 일을 여러 번 한다. 시연 중에는 한 대만 띄우는 게 안전하다
