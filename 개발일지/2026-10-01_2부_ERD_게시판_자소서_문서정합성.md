# ERD 대폭 수정(기술 글 게시판·프로젝트 문서), 자소서 선택 업로드, ERD 문서 3종 정합성 검증

날짜: 2026-10-01
관련 요구사항: FR-14·24·81~86 · 개발일지 4-3(EXPERT 증빙 공개)·4-4(프로젝트 완료 시 받는 것)

## 1. 개요

"로드맵 - 생각정리 및 업데이트" 문서의 4-3(EXPERT 증빙을 블로그처럼 공개)을 팀 회의에서 댓글·북마크·하트·조회수가
붙는 진짜 게시판으로 넓히기로 해서 ERD를 크게 고쳤다. 같이 나온 "이력서·자소서를 내 프로필에 선택으로 올리고, 면접관이
한눈에 볼 수 있게 하자"는 의견도 반영했다. 작업하다가 **문서에는 '반영 완료'로 적혀 있는데 실제로는 없는 것**과
**ERD 문서 3종(SQL·db-design.md·ERD 뷰어)이 서로 어긋나 있는 것**을 발견해서 같이 바로잡았다.

## 2. 먼저 확인한 것 — "ERD 뷰어·db-design 반영 완료"가 실제로는 아니었다

생각정리 문서 4-3-1·4-4에 "TECH_ARTICLE(신설)까지 ERD 뷰어에 반영하고 검증했다(테이블 37개→39개)"고 적혀 있었다.
저장소를 `grep`으로 대조해 보니 아래는 **SQL·db-design.md·뷰어·코드 어디에도 없었다.**

| 문서에 "확정/반영 완료"로 적힌 것 | 실제 |
| --- | --- |
| TECH_ARTICLE (4-3-1) | 없음 |
| PROJECT_TECH_NOTE, PROJECT_DOCUMENT_ITEM (4-4) | 없음 |
| USER_PROJECTS.repo_url·deploy_url·retrospective (4-4) | 없음 |

반대로 `ROADMAP_STEP`의 증빙 컬럼, `JOB.requirement_version` 등은 SQL과 db-design.md에는 있었지만 **ERD 뷰어에는 빠져 있었다.**
(뷰어 상단에는 "35개 테이블"이 남아 있었고, 실제 DB는 38개였다.) 이번에 전부 현재 상태로 맞췄다.

## 3. 스키마 변경 (테이블 38개 → 46개)

**신설 8개** — 게시판 6개 + 프로젝트 문서 2개. 상세 설계 판단은 `docs/db-design.md`에 있다.

- `TECH_ARTICLE` — 개발일지 컬럼 목록을 그대로 지키고 `source_type`, `hidden_reason`·`hidden_at`,
  `like_count`·`comment_count`·`bookmark_count`만 더했다. `roadmap_step_id`는 UNIQUE(EXPERT 단계 하나에 글 하나).
- `TECH_ARTICLE_COMMENT`(대댓글 한 단계, 자기참조) · `_LIKE` · `_BOOKMARK` — 하트·북마크는 복합 UNIQUE
  `(article_id, user_id)`이고 취소는 `is_deleted`로 하며 다시 누르면 같은 행을 되살린다(물리 삭제 금지 + UNIQUE 충돌 방지).
- `TECH_ARTICLE_VIEW_LOG` — "사용자 1명 × 글 1개 × 하루 1회"만 조회수에 반영하려고 `(article_id, viewer_user_id, viewed_date)` UNIQUE.
- `TECH_ARTICLE_REPORT` — 자동 게시 + 사후 관리(4-3)에서 "문제 글을 누가 찾느냐"를 신고로 푼다.
- `PROJECT_TECH_NOTE`, `PROJECT_DOCUMENT_ITEM` — 4-4에서 확정했던 것을 이제야 반영.

**컬럼 추가** — `USERS.cover_letter_document_id`, `SHARE_LINK.scope_cover_letter`, `USER_PROJECTS`의 `repo_url`·`deploy_url`·`retrospective`.

**내가 문서에 없던 판단을 추가한 곳** (회의에서 뒤집어도 된다): `PROJECT_TECH_NOTE (project_id, skill_id)` UNIQUE,
`TECH_ARTICLE.source_type`(자유 글 허용 여부는 아직 안 정함), `*_count` 집계 컬럼, 신고 테이블, 조회 이력 테이블.

SQL은 신규 DB용(`01`·`03`)과 기존 DB용 마이그레이션(`12`·`13`·`14`)을 같은 DDL에서 만들었다.

## 4. 자소서 — 이력서와 같은 구조로 구현

- 내 프로필에서 이력서·자소서를 **선택**으로 올림(PDF·doc·docx·hwp·hwpx, 10MB). 바꾸면 이전 파일 삭제.
- 공유 링크마다 "자소서 파일" 공개 범위를 따로 고름(기본 비공개, NFR-4).
- 면접관은 한 카드("이력서 · 자소서")에서 한눈에 보고 내려받는다. 비교표에도 자소서 행을 추가했다.
- `ResumeService`를 이력서·자소서 공용으로 일반화했다(`Kind`로 컬럼만 가름). `ProfileResumeServlet`은 URL 두 개
  (`/profile/resume`, `/profile/cover-letter`)를 한 서블릿이 받는다.
- 프로필·공유 설정 화면에 "이력서·자소서를 올려 두면 면접관이 한눈에 볼 수 있어 편해요" 안내 문구를 넣었다.

## 5. ERD 문서 3종 정합성 검증 (이번에 만든 방법)

손으로 맞추다 어긋난 게 이번 문제의 뿌리라서, **실제 DB(`information_schema`)를 기준으로 세 문서를 기계적으로 대조**했다.

1. 신규 DB 경로(`01`+`03`+`09`)와 마이그레이션 경로(기존 DB + `12`~`14`)로 각각 DB를 만들어 컬럼·FK·인덱스를 비교 → **46개 테이블, FK 70개, 인덱스까지 일치**.
2. 그 DB와 `db-design.md`를 테이블·컬럼 단위로 대조 → 유일한 불일치는 `DOCUMENTS.uploaded_at`(문서에만 있고 DB에는 만든 적 없는 컬럼. 업로드 시각은 공통 컬럼 `created_at`)이라 문서에서 지웠다.
3. DB와 ERD 뷰어를 대조 → 뷰어에 빠져 있던 컬럼 18개(새 테이블·새 컬럼 포함)와 관계 24개를 보강. 뷰어 상단 숫자는 이제 데이터에서 직접 센다.
4. Chromium으로 뷰어를 열어 JS 오류 0건, 카드 46개, 관계선 68개, 카드 겹침 0건 확인.

## 8. 같은 날 이어서 한 것 — ERD PDF와 DAO 가이드

**ERD PDF 새로 만듦** (`docs/스펙_오디세이_DB_설계_및_ERD.pdf`, 31쪽·책갈피 64개)
- 예전 PDF(2026-09-21판, 36개 테이블)는 그대로 두면 `db-design.md`와 어긋나서, 기준 문서인 `db-design.md`를 그대로 인쇄한 판으로 교체했다. 이전 판은 git 이력에 남아 있다.
- 첫 장에 이번 개정 요약, 전체 ERD 그림(A3 가로), 영역별 ERD 3장((A) 핵심 여정 · (B) 확장 · (C) 게시판·프로젝트 문서), 테이블 정의 46개, 복합 UNIQUE 요약, 회의에서 정할 것.
- 영역별 ERD는 처음엔 mermaid로 그렸는데 글자가 너무 작아 읽을 수 없어서, ERD 뷰어의 카드를 영역별로 다시 배치한 그림으로 바꿨다.
- 만들다 알게 된 점: Chromium PDF에서 큰 이미지를 `display:block`으로 두면 제목과 이미지가 서로 다른 쪽으로 갈라진다(이미지를 인라인으로 두면 해결). 그리고 `db-design.md`의 `*_count`가 마크다운 강조로 읽혀 글자가 깨져서 백틱으로 감쌌다(GitHub에서도 같은 문제였다).

**DAO 가이드 갱신** (`docs/spec-odyssey-dao-guide.html`)
- 09-21 이후 코드가 많이 바뀌어 있었다 — 가이드는 DAO 36개·메서드 109개인데 소스는 DAO 40개·메서드 178개(`JobPostingDao`·`SkillAliasDao`·`MissionDao`·`TrendCollectDao` 누락, 35개 DAO의 메서드 목록이 달랐다).
- 가이드가 "소스에서 자동 추출"한 데이터라, 같은 규칙으로 현재 소스에서 다시 추출했다(시그니처, 반환, 트랜잭션 겸용/전용, void 수정·삭제, DTO 필드, 호출하는 곳). 기존 109개 메서드의 설명은 그대로 보존했고, 새 69개는 코드 주석을 설명으로 썼다.
- 소스와 가이드의 DAO별 메서드 이름이 전부 일치하는 것을 별도 방식으로 교차 확인했다.
- 서술 절 중 사실이 바뀐 곳만 고쳤다: ① void 수정·삭제 27개→35개와 `RoadmapStepDao.updateCompleted`가 이미 `int`로 바뀐 점, ④ LLM은 `GroqLlmClient`가 타임아웃·재시도를 처리, 점수 요약 행 생성 방식 결정됨, 테스트 실행 환경(리눅스는 `lower_case_table_names=1`, DB 시간대 +09:00), 구현이 끝난 기능 현황. 게시판·프로젝트 문서 테이블은 DAO가 아직 없다는 인수 항목을 추가했다.
- 서술 절 나머지(공용 뼈대 사용법 등)는 09-21 기준 그대로다. 숫자·사실이 바뀐 곳만 고쳤기 때문에, 전체를 다시 읽고 다듬는 일은 따로 필요하다.
- 서명이 긴 메서드가 설명 열을 눌러 행이 너무 높아지던 것을 CSS로 고쳤다.

## 9. 아직 안 한 것

- 게시판의 DAO·서비스·화면(팀 회의 후). 스키마와 문서만 선점했다.
- 프로젝트 문서 체크리스트·기술 활용 설명서·회고의 입력 화면과 완료 판정(4-4). 마찬가지로 스키마만.
- `요구사항 명세서` PDF와 `로드맵 - 생각정리 및 업데이트` PDF는 원본 편집 파일이 없어 손대지 않았다. 게시판·자소서는 아직 요구사항(FR)에 번호가 없다.
