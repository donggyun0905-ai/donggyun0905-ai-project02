## 2. 어드민 패널 (`f1625f2`)

관리자 판정을 `AdminAccess.isAdmin()` 한 곳에서 `user_type = 'ADMIN'`으로 바꿨다. `user_type`은 면접관 계정(TD-4) 때
이미 `VARCHAR(15)` 자유 값으로 열어 둔 컬럼이라 **마이그레이션이 필요 없었다** — `db-design.md`의 "회의에서 정할 것"에
이 방향으로 이미 정리돼 있었다. 아이디만 맞으면 관리자가 되던 예전 방식은 가입이 열린 서버에서 누구나 선점할 수 있었다.

| 화면 | 하는 일 |
| --- | --- |
| `/admin/articles` | 신고된 기술 아티클 보기 · 사유를 남기고 내리기/복구. 내리면 그 글의 열린 신고를 전부 처리 완료로 닫는다 |
| `/admin/users` | 아이디·이름·이메일 검색 · 프로필 수정 · 비밀번호 재설정 · 탈퇴 처리/유예 취소 |
| `/admin/roadmap` | 로그인 아이디로 회원 로드맵 단계를 찾아 완료/취소/삭제 |
| `/admin/reference` | JOB · SKILL · CERTIFICATION · SKILL_ALIAS · JOB_REQUIRED_SKILL 추가·수정 |

판단해서 **일부러 안 한 것**:
- 로드맵 단계 완료를 토글해도 **점수는 건드리지 않는다**. 점수는 append-only(SCORE_LOG) 설계라 관리자가 토글할 때마다
  적립·회수하면 중복 적립이나 음수가 생긴다. 화면에도 그렇게 적었다.
- 기준 데이터 수정에서 **임베딩 필드는 건드리지 않는다**(`SkillDao.update`). 이름만 바꾸고 벡터를 그대로 두면 매칭이
  어긋나지만, 벡터를 지우면 매칭이 아예 멈춘다 — 재생성 흐름이 생길 때까지 손대지 않는 쪽이 안전하다.
- 기준 데이터 범위는 49개 테이블 전체가 아니라 **기준·참조 데이터 5개로 한정**했다(사용자 결정).

`RoleFilter`에 ADMIN 분기를 넣어 관리자는 `/admin/` 밖으로 가면 `/admin`으로 돌아오고, 지원자·면접관은 `/admin/`에
못 들어간다. 좌우 위젯·알림·설문 제한도 관리자에게는 붙지 않는다.

## 3. 화면당 중복 DB 조회 제거 (`e827d40`)

"화면당 15회"를 세어 보니 **절반 가까이가 순수 중복**이었다. 원인은 필터와 서블릿이 같은 데이터를 서로 모르고 각자 읽는 구조.

**① 로드맵 (요청 범위 캐시)** — `/roadmap`·`/dashboard`에서 `getPrimaryRoadmap` + `getSteps` + `computeProgress`가
요청마다 **두 번씩** 돌았다(`SideWidgetFilter` → `GlanceService`가 한 번, 서블릿이 또 한 번). `getSteps`가 그중 제일 무겁다.
새 `RoadmapRequestCache`가 요청 속성에 담아 한 번만 읽는다.
화면을 그리는 동안에는 단계가 바뀌지 않으니 요청 범위에서는 낡을 수 없고, 복습·관리 단계를 실제로 덧붙이는 경로
(세션당 하루 한 번)에서는 `invalidate()`로 버린다.

**② 등급 구간 (애플리케이션 캐시 60초)** — `LEVEL_TIER` 전체 조회가 한 화면에 **최대 6번**이었다.
헤더 배지에서 2번(`getTierForScore` + `getTierLogoPath`), 위젯에서 2번, 대시보드 등급 카드에서 2~3번.
시드로만 관리되고 앱에서 쓰는 화면이 아예 없는 마스터성 데이터라, 이미 있던 `ScoringRules`와 **똑같은 방식**으로
`LevelTiers`에 캐시했다. DAO는 그대로 매번 DB를 읽게 둬서 `LevelTierDaoTest`(insert 직후 findAll 확인)가 그대로 통과한다.

남겨 둔 것: 사용자별 가변 데이터(`USER_SCORE_SUMMARY` 요청당 3번, `DDAY_ALERT` 2번). 요청 범위로 묶으려면
`SessionFilter`까지 건드려야 해서 따로 하는 게 안전하다.

## 4. Tomcat 11에서만 터지던 인사이트 500 (`15d37c3`)

"또래 비교에서 에러 페이지가 뜬다"는 제보. **서비스 계층을 실계정 7개로 직접 돌려 봤는데 전부 정상**이었다 —
그래서 JSP의 EL 해석만 문제라고 특정했다.

원인은 10/5에 겪은 것과 같은 종류다. `insights.jsp`가 `${peer.comparable}`로 읽는데 `PeerView` record에는
`isComparable()`만 있었다. **Tomcat 11의 `RecordELResolver`는 record에서 `isX()`/`getX()`를 안 찾고 `x()`만 찾는다** —
그래서 Tomcat 11(나)에서만 `PropertyNotFoundException`으로 화면 전체가 죽고, 10.1(팀원들)에서는 정상으로 보였다.

`comparable()`을 추가하고, 재발을 막으려고 **main의 모든 record를 전수 조사**했다. JSP가 읽는 파생 접근자 8개 중
누락은 이거 하나였고 나머지는 이미 두 형태가 다 있었다. `RecordElAccessTest`의 점검 대상에 `InsightViewDto`의 record
8개를 넣고 `comparable`은 두 형태를 직접 단정하게 했다.

> kangdain은 record **구성요소**에는 `getX()`를 다 넣어 팀 규칙을 지켰다. 놓친 건 구성요소가 아닌 **계산 값** 하나뿐이다.

## 5. 체크리스트 0~11번

**1·2·3번 — 가입 화면 (`32ff687`)**
아이디 칸을 벗어나면 서버에 물어보고 안 되는 아이디면 칸 아래에 빨간 글씨로 이유를 띄운다(다음 단계로도 못 넘어간다).
비밀번호 확인은 입력하는 동안 바로 일치 여부를 보여 준다.
확인 엔드포인트는 **가입 화면과 같은 공개 경로**(`/register?checkLoginId=…`)에 뒀다 — `SessionFilter`의 공개 경로 목록은
보안 경계라 리뷰어 2명 규칙이 있어서 건드리지 않았다.

3번("탈퇴한 아이디를 못 쓴다")은 **코드 문제가 아니었다.** 검사 로직을 공유 DB의 탈퇴 계정 13개에 그대로 돌려 보니
**전부 재가입 가능 상태**였다. 막히는 경우는 유예 30일 중일 때뿐이고, 그건 탈퇴 취소로 아이디를 돌려주기 위한 의도된 동작이다.
대신 "이미 사용 중"이라는 안내가 왜 막혔는지 알려 주지 않던 문제를 고쳤다 — 살아 있는 계정인지, 유예 중인 계정이 잡고
있는지를 구분하고 후자는 며칠 뒤에 쓸 수 있는지까지 알려 준다. 화면 안내와 가입 실패 문구가 같은 판단(`checkLoginId`)을
쓰게 모으고, 두 문구가 같은지 테스트로 단정했다.

**4번 — 탈퇴 취소에 복구 코드 (`1e9d4cd`)**
비밀번호만 맞으면 버튼 한 번으로 계정이 되살아나서, 비밀번호가 새어 나간 계정을 남이 되살려 기록을 다 볼 수 있었다.
복구 코드를 받아 둔 계정은 그 코드까지 맞아야 되살린다.
**폴백이 필요했다** — 복구 코드 발급 전에 만들어진 계정은 받을 코드가 없어서, 요구하면 유예가 끝날 때까지 복구할 길이
아예 없어진다. 공유 DB의 활성 계정 23개 중 15개가 이 경우였다(팀원 계정 포함). 그 계정은 비밀번호 확인만으로 되살리고
화면에도 어느 쪽인지 적어 준다.
유예 만료는 코드를 다시 받아도 소용없으므로 `WithdrawalGraceExpiredException`으로 분리했다(전에는 둘 다 같은 예외라
만료인데도 코드 재입력 화면이 떴다).

**5·11번 — 레이아웃 (`9f2b7dc`)**
첨삭 화면은 좌우 위젯이 안 붙는데 본문이 `.wide`의 1140px에 묶여 있었다. `mainFull`/`main.full`(1800px)을 추가했다.
이 화면은 `SideWidgetFilter` 대상이 아니고 `#trend-sidebar`도 비어 있어(`:empty` → `display:none`) 폭이 실제로 비어 있다.
위젯 스크롤바는 기본 회색 막대가 종이색 배경과 겉돌았는데, "지나온 길"(`.journey-track-scroll`)에서 이미 쓰는
모양·토큰(`--gold`)으로 맞췄다 — 새 색을 만들지 않았다.

**6·7·8번 — 로드맵 (`cfbe5a8`)**
7번의 원인이 분명했다. `RoadmapRefreshPlan`의 클래스 주석에는 *"그대로인 단계는 서로의 순서도 바꾸지 않고, 새 단계는
같은 티어의 맨 뒤에 붙인다"*고 적혀 있는데 `orderedSlots`가 그렇게 하지 않았다 — 티어 안에서 종류별로 다시 모으고
새 자격증·프로젝트를 기존 기술 **앞**에 끼워 넣어서 이미 걸어온 길의 번호가 전부 밀렸다. 문서화된 규칙대로 고쳤다.

6번에는 함정이 있었다. 새 입문 단계가 생기면 **티어 잠금 규칙상 이미 열린 핵심·심화가 다시 잠긴다** — 그래서 코드에
"예전부터 부족했던 기술은 일부러 안 넣는다"는 제약이 있었다. 사용자 결정으로 잠금을 완화했다: 한 번 열린 티어는
나중에 앞 티어에 단계가 덧붙어도 다시 잠기지 않는다. 앞 티어를 다 끝냈는지 볼 때 **이 티어보다 나중에 만들어진 단계는
빼고 본다**(단계 id가 만든 순서라 스키마 변경이 필요 없다). 한 라운드로 통째로 만든 로드맵에서는 예전과 똑같이 동작하고,
원래 있던 앞 단계를 완료 취소하면 그대로 다시 잠긴다 — 테스트 4개로 단정했다.

`appendNextRound`가 아직 담지 않은 부족 기술을 한 라운드만큼 각 티어 맨 뒤에 이어 붙인다. **LLM은 부르지 않는다**
(사용자 결정) — 프로젝트 단계 아이디어가 LLM을 쓰므로 기술 단계만 넣고, 프로젝트는 "바뀐 부분만 다시 만들기"가 맡는다.
화면은 길 끝 표식이 보이면 `action=extend`를 부르고, 새 화면을 받아 **길 부분만 갈아 끼워** 스크롤 위치를 유지한다
(새로고침이 없어 깜빡이지 않는다). 길 그림(`_path.jspf`)은 갈아 끼운 뒤 다시 그려야 해서 `window.journeyPathInit()`으로
노출했다 — 다시 그릴 때 이전 SVG가 쌓이지 않게 지우고, resize는 예전처럼 `draw()`만 불러 빛이 처음부터 다시 달리지 않게 했다.

**9번 — 이미 되어 있었다.** `RoadmapGenerator.findSuggestedCommonCertification`이 공통 자격증을 한 칸 따로 배치하고,

**0번 — 데이터 인사이트는 기능 자체가 바뀌었다.** 전에는 4개 카드 중 2개("취업시장 트렌드", "약점 히트맵")가
하드코딩된 HTML이었고, 지금은 전부 목표 직무 기준 실데이터다. 히트맵 열 축도 바뀌었다: `입문/핵심/심화/전문가`(로드맵 티어)
→ `기초/중급/심화`(`required_level`). **같은 화면에 "심화"가 두 뜻으로 쓰여** 헷갈리니 열 이름이나 설명을 손보는 게 좋다.

사용자 결정대로 **kangdain의 계산 + youngjun의 모델 공유**로 합쳤다.
kangdain 것을 쓰는 이유는 주석에 실측이 남아 있다 — 전공마다 유사도 범위가 달라서 절대 문턱(youngjun: 0.40) 하나로는
자를 수 없다(국문 0.33과 수학 0.36이 붙어 있다). 같은 사람 안에서 계열끼리 상대 비교하고 차이 신뢰도 × 절대 신뢰도를
곱해 약한 신호를 서서히 줄인다.
youngjun에서 가져온 것은 임베딩 모델 공유다. kangdain 주석에 "남의 파일을 안 건드리려고 따로 로드했고, 공유하도록
바뀌면 합치면 된다"고 적혀 있었다 — **모델 하나가 약 440MB라** 중복 로드를 남길 수 없다.
`EmbeddingMatcher.embedder()`를 공개로 바꿔 연결했다(동작 변화 없음).

**③ `countNewQuestions` 소실** — kangdain 브랜치가 그 기능 이전 main 기반이라 `JobDiscoveryService`를 그대로 take하면
설문 문항 변경 안내가 사라진다. HEAD를 바탕으로 FR-38 호출부만 kangdain API로 바꿨다.

**④ SQL 번호 충돌 2건** — seongwon의 알림이 내 `21_alter_users_withdraw_requested_at`과 21로 겹쳤고(알림을 24로 옮김),
donghyeon의 시뮬레이션이 그 24와 또 겹쳤다(26·27로 옮김). `README`·`db-design.md`·`03_schema_extended.sql`의 참조도 맞췄다.
**25번은 비어 있다.**

알림 테이블과 시뮬레이션 마이그레이션은 공유 DB에 이미 적용돼 있어 실행할 것이 없었다(구조까지 확인).

## 7. 공유 DB를 오염시키던 테스트 정리 버그 (`24a4f95`, `15d37c3`)

전체 테스트에서 tearDown이 FK로 깨지는 걸 파보니 **공유 DB에 테스트 고아 행이 계속 쌓이고 있었다.** 원인 3개를 고쳤다.

1. **tearDown이 DAO `findByXxx`로 순회** — DAO는 `is_deleted = FALSE`만 돌려주니 서비스가 논리 삭제한
   `ROADMAP`·`ROADMAP_STEP`·`GAP_ANALYSIS`를 못 보고 그대로 남긴다. 그 행이 FK로 SKILL·USERS 하드 삭제를 막는다.
   `TestFixtures.findIdsByColumn`을 추가해 FK 컬럼으로 직접 지우게 했다.
2. **테스트 기술을 팀 공용 BACKEND 직무에 끼워 넣는다** — 그 사이에 분석을 돌린 다른 테스트 사용자의
   `GAP_ANALYSIS_ITEM`·`ROADMAP_STEP`도 그 기술을 물고 있다. 소유자와 무관하게 그 `skill_id`를 가리키는 행을 모두 끊는다.
3. **`SPEC_SCORE_HISTORY` 정리가 아예 없었다.** `SpecScoreScheduler`가 **웹앱이 뜨는 순간 전체 사용자**에게 스냅샷을
   남기므로, 누가 같은 공유 DB로 서버를 켜 두면 테스트가 방금 만든 사용자 몫까지 생긴다. `USERS` 삭제 바로 앞에서
   지워 그 레이스 창을 줄였다.

남아 있던 고아 행(테스트 계정 21개 + SKILL 44개)을 정리하고, 전체 테스트 뒤 고아 0을 확인했다.

> 3번은 운영에도 영향이 있다 — 팀원 5명이 각자 서버를 켜면 같은 날 스냅샷이 중복 시도된다(멱등 처리는 돼 있어 데이터는 안 깨진다).

## 8. 남은 일

- **`GroqRetryAfterClient`가 main에서 안 쓰인다.** youngjun의 `LlmRetryPolicy.BATCH`는 429에 20·40·60초 **고정** 대기인데,
  seongwon이 `retry-after` 헤더를 읽어 필요한 만큼만 기다리게 만든 걸 대체한 셈이다("몇 초면 풀릴 한도에도 수 분씩
  기다렸다"가 고치려던 문제). 지울지, retry-after를 `GroqLlmClient`에 넣을지 정해야 한다. 지금은 테스트만 남아 있다.
- **브라우저 확인**: 첨삭 화면 폭, 위젯 스크롤바, 그리고 특히 **로드맵 맨 밑 스크롤 자동 추가가 깜빡임 없이 되는지와
  갈아 끼운 뒤 길 그림(S자 곡선·흰 빛)이 제대로 다시 그려지는지.**
- **데이터 인사이트 히트맵 열 이름** — 같은 화면의 "심화"가 두 뜻(5절 0번).
- **`InsightsServlet`의 세션 NPE 위험** — `getSession(false)` 결과를 `try` 밖에서 바로 캐스팅한다. `SessionFilter`가
  막아 주니 지금은 안 터지지만 다른 서블릿은 모두 헬퍼로 처리한다.
- **`donghyeon`의 26번 마이그레이션**이 `aaa`·`bbb`·`ttt`·`test`·`test1`·`test1234`·`webtest` 등을 `is_test = TRUE`로
  표시했다. 이 계정들은 시뮬레이션 초기화로 **물리 삭제가 허용된다** — 실제로 쓰는 계정이 섞였으면 빼는 게 좋다.
- 저장소 루트의 `2d/ConsoleApp1`(C# 프로젝트)과 `.claude/worktrees/agent-ad80d744361b5de15`(예전 에이전트 worktree,
  커밋 `2b3678d`) 정리 여부.
