## 3. 설문 중복 정리 + 18문항 확장 (`e570574`)

**문제**: 공유 DB에 직무 발굴 설문이 24개 — 원본 12문항(id 108~119)과 문구까지 똑같은 복제본(id 120~131).
`05_seed_survey.sql`이 두 번 실행된 것이다. 이미 답한 9명은 복제본에도 응답이 있어서 추천 점수가 두 배로 잡히는 상태였다.

**정리**: 복제본 12문항과 거기 달린 응답 108개를 논리 삭제(물리 삭제 금지 규칙).

**재발 방지**: 시드를 `INSERT ... SELECT ... WHERE NOT EXISTS` 형태로 바꿔, 같은 문구의 살아 있는 문항이 있으면
건너뛰게 했다. 스키마를 건드리지 않는 방법이다. 공유 DB에 두 번 연속 실행해 18개 그대로인 것 확인.

**확장**: 계열당 2문항이면 계열 점수가 2~10점으로만 나와 동점이 잦아 계열마다 1문항씩 추가 → 6계열 × 3 = 18문항.
기존 문항처럼 기술 용어 없이 "하는 일"로 묻고, 같은 계열이 연달아 나오지 않게 섞었다. 점수는 계열별 평균이라 코드 변경은 없다.

**기존 응답자 9명**: 새 6문항에 임시로 3점(보통이다)을 넣었다 — 중간값이라 기존 추천이 한쪽으로 쏠리지 않는다.
설문을 다시 풀면 실제 값으로 바뀐다.

## 4. 회원 탈퇴 30일 유예 (`ecfc5ca`)

**배경**: 탈퇴 시 아이디를 `del_<id>_`로 바로 비우는 방식(10/2 커밋 `d20e456`)은 재가입은 되지만 탈퇴한 사람이
돌아올 길이 없었다. 복구 기능을 붙이면 그사이 다른 사람이 아이디를 가져가는 문제가 생긴다. 기존 "복구 코드"는 비밀번호
찾기용이라 탈퇴 계정(`is_deleted = TRUE`)에는 쓸 수 없었다.

**결정(팀 확인)**: 실무에서 많이 쓰는 유예 방식.
- `USERS.withdraw_requested_at` 추가(`sql/21_alter_users_withdraw_requested_at.sql`, 공유 DB 적용, `01_schema.sql` 반영).
- 탈퇴하면 `is_deleted = TRUE` + 신청 시각만 남기고 **아이디는 30일 동안 그대로 잡아 둔다** → 그사이 같은 아이디로
  가입하면 "이미 사용 중", 그래서 "아이디 중복" 상황 자체가 생기지 않는다.
- 30일 안에 같은 아이디·비밀번호로 로그인하면 "탈퇴 신청한 계정입니다" 화면(확정 날짜 표시) → "탈퇴 취소하고 계속 쓰기"로
  바로 로그인. 비밀번호가 틀리면 탈퇴 계정인지 알려주지 않는다. 취소 버튼은 방금 비밀번호를 확인한 세션에서 10분 안에만 유효.
- 유예 중에도 복구 코드로 비밀번호를 찾을 수 있다(계정은 탈퇴 상태 그대로, 다음 로그인에서 취소).
- 30일이 지나면 `WithdrawalPurgeScheduler`(매일 00:00, 기동 시 1회)가 아이디를 비우고 이름·나이·구분·이메일·복구 코드를
  지운다. 배치가 늦어도 가입 시 유예가 끝난 계정의 아이디는 그 자리에서 비워 준다.
- 탈퇴 경로가 `/login` 안에서 처리되도록 해 `SessionFilter` 공개 경로는 건드리지 않았다(변경 시 리뷰어 2명 규칙).
- `18_fix_withdrawn_login_id.sql`은 21 적용 뒤 다시 실행하면 유예 중인 아이디까지 비워 버려 파일에 경고를 달았다.
- 프로필의 탈퇴 안내 문구를 "30일 안에 다시 로그인하면 취소 가능"으로 바꿨다.

**검증**: `UserWithdrawTest` 7개(유예 중 가입 차단, 취소 후 로그인, 유예 만료 후 재가입, 정리 배치가 만료 계정만 처리,
긴 아이디 충돌 없음, 예전 방식 탈퇴 계정, 유예 중 복구 코드)를 새로 작성. 로컬 Tomcat에서 가입 → 탈퇴 → 같은 아이디 가입(막힘)
→ 로그인(취소 화면, 확정일 2026-11-02) → 탈퇴 취소 → 정상 로그인까지 실제로 확인. 전체 `mvnw test` 579개 통과.
테스트 계정은 정리 배치와 같은 방식으로 정리했다.
