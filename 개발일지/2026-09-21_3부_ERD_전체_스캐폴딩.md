# 전체 ERD 36개 테이블 스키마·DTO·DAO 스캐폴딩

날짜: 2026-09-21
범위: 1주차 8개 테이블 외 나머지 28개 테이블(2주차 이후 분)의 DDL·DTO·DAO를 미리 만들어둔 작업

## 1. 개요

`claude.md`에는 원래 "나머지 28개 테이블은 아직 만들지 않는다. 2주차 이후 범위"라는 문구가 있었다. 하지만 이 규칙이 팀이 합의한 게 아니라 임의로 들어간 것이라는 판단 하에, 2주차에 팀원들이 역할을 나눠 병렬로 작업을 시작하기 전에 전체 ERD(36개 테이블)의 스키마와 DTO/DAO 골격을 미리 갖춰두기로 했다. 그래야 2주차 담당자들이 "테이블이 아직 없다"는 이유로 서로를 기다리는 일 없이 바로 Service/Controller부터 시작할 수 있다.

단, Controller/Service/JSP 같은 실제 기능 로직은 전혀 만들지 않았다 — `claude.md`의 "요청하지 않은 기능 임의 추가 금지" 원칙에 따라, 이번 작업은 순수하게 데이터 접근 계층까지만이다.

## 2. DB 스키마 확장 — `sql/03_schema_extended.sql`

`sql/01_schema.sql`(1주차 8개 테이블)을 건드리지 않고 새 파일로 나머지 28개 테이블의 DDL을 추가했다.

- **FK 44개**: 1주차분 6개 + 신규 38개. 전부 `ON DELETE RESTRICT ON UPDATE CASCADE`로 1주차와 동일한 정책 유지.
- **복합 UNIQUE 21개**: `docs/db-design.md`의 "복합 UNIQUE 제약" 표에 나열된 것을 빠짐없이 반영 (예: `JOB_REQUIRED_SKILL(job_id, skill_id)`, `JOB_SKILL_TREND(job_id, skill_id, period_ym)`, `SCORE_LOG(user_id, signal_type, ref_id)` 등 — 재수집·재적립 시 중복 방지용).
- **테이블 생성 순서**: FK 의존성을 어기지 않도록 무의존 테이블(SURVEY_QUESTION, PROBLEM, TREND_TECH, LEVEL_TIER 등) → 1주차 테이블에만 의존하는 테이블(JOB_REQUIRED_SKILL, CERT_SCHEDULE 등) → 그 위에 얹히는 테이블(ROADMAP → ROADMAP_STEP, EVALUATION_SESSION → EVALUATION_SESSION_ITEM 등) 순으로 배치.

## 3. DTO/DAO 56개 — 테이블 성격별 4가지 유형(A/B/C/D)

DAO를 전부 똑같은 모양(add/edit/delete 풀세트)으로 만들면 안 된다고 판단했다. 테이블마다 실제로 누가 어떻게 쓰는지가 다르기 때문이다. 처음엔 "테이블만 만들고 DTO/DAO는 조회 전용 뼈대만" 하는 절충안도 검토했지만, 최종적으로는 아래처럼 역할별로 메서드 구성을 다르게 해서 DTO/DAO까지 전부 만들기로 했다.

| 유형 | 개수 | 성격 | DAO 메서드 구성 | 해당 테이블 |
| --- | --- | --- | --- | --- |
| A | 8 | 마스터/시스템 수집 데이터 — 사람이 화면에서 관리하지 않음 | `findAll`/`findByXxx` + `insert`만 | JOB_REQUIRED_SKILL, JOB_BENCHMARK_SPEC, SURVEY_QUESTION, PROBLEM, TREND_TECH, TREND_TECH_JOB, LEVEL_TIER, CERT_SCHEDULE |
| B | 8 | append-only 로그/스냅샷 — 한 번 쌓이면 끝, 수정·삭제 없음 | `insert` + 조회만 | GAP_ANALYSIS, GAP_ANALYSIS_ITEM, USER_SURVEY_ANSWER, SPEC_SCORE_HISTORY, JOB_SKILL_TREND, SCORE_LOG, SHARE_LINK_VIEW_LOG, EXTERNAL_API_CACHE |
| C | 5 | 시스템이 생성하고 사용자는 상태만 바꿈(체크/선택) | `insert` + 조회 + `update`(상태 변경 전용), delete 없음 | ROADMAP, ROADMAP_STEP, JOB_RECOMMENDATION, USER_DAILY_MISSION, USER_SCORE_SUMMARY |
| D | 7 | 사용자·면접관이 직접 소유·관리하는 리소스 | 완전한 CRUD(soft delete 포함) | SHARE_LINK, EVALUATION_SESSION, EVALUATION_SESSION_ITEM, EVALUATION_CRITERIA, DOCUMENTS, DDAY_ALERT, AI_USAGE_LOG |

A/B 유형에 update/delete를 안 만든 이유: 마스터 데이터는 사람이 화면에서 고치는 게 아니라 시드/배치로 채워지고, 로그성 데이터는 애초에 수정하면 데이터 정합성이 깨진다(예: `SCORE_LOG`를 수정할 수 있으면 점수를 조작할 수 있게 됨). 필요하지도 않은 메서드를 미리 만들어두면 2주차 담당자가 "이거 써도 되는 건가" 헷갈리기만 한다.

## 4. 설계상 특이 케이스

- **`USER_SCORE_SUMMARY.user_id`**: AUTO_INCREMENT PK가 아니라 `USERS.id`를 그대로 받는 PK이자 FK — 사용자 1명당 요약 행 1개(1:1)를 자동으로 보장하기 위한 구조. `UserScoreSummaryDao`는 이 특수성 때문에 `insert(dto)` 시 PK를 직접 지정해서 넣는다.
- **`EVALUATION_SESSION` 계열**: 면접관은 계정이 없다(FR-14). 그래서 `user_id` 기반 소유자 확인을 쓸 수 없고, 대신 `session_token`(추측 불가능한 랜덤 문자열)을 발급 증명으로 삼아 `EvaluationSessionDao`/`EvaluationSessionItemDao`가 토큰 기준으로 소유자를 확인한다.

## 5. 기존 5개 DAO와의 관계

`SKILL`, `CERTIFICATION`, `JOB_ALIAS`, `JOB`은 이미 이전 세션에서 조회 전용 뼈대(`findAll`/`findByName` 등)로 만들어져 있었다. 이번 작업은 그 패턴을 그대로 따라 나머지 28개 테이블까지 확장한 것이다. 최종적으로 `dto`/`dao` 패키지에 각각 36개 파일(1주차 5개 + 마스터 조회전용 3개 + 이번 28개)이 갖춰졌다.

## 6. 이번 커밋에 없는 것

- Controller/Service/JSP: 전혀 없음. 2주차 각 기능 담당자가 이 DAO/DTO 위에 붙인다.
- 테스트: 이 커밋에는 테스트가 포함되지 않았다. DAO 36개에 대한 JUnit 통합테스트는 바로 다음 작업(커밋 `118bc47`)에서 별도로 진행했다 — "4부" 개발일지 참고.
