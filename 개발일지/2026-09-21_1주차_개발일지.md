# 1주차 개발일지 — 회원/인증 + 프로필 CRUD

날짜: 2026-09-21
범위: `docs/requirements.md` 8절 진행 가이드 기준 **1주차 목표** (FR-11~13, FR-21~25) — 설계 확정(ERD) + 회원/인증 + 프로필 CRUD

## 1. 개요

스펙 오디세이(Spec Odyssey)는 단순 스펙 "진단"이 아니라 사용자가 나아갈 "길(여정)"을 제시하는 서비스로 기획됐다(핵심 정체성은 `docs/requirements.md` 참고). 전체 로드맵은 4주 계획 중 1주차이며, 이번 주 완료 범위는:

- 회원가입 / 로그인 / 로그아웃 (FR-11·12·13)
- 세션 기반 본인 데이터 접근 통제 (FR-13)
- 프로필 기본정보 + 보유 스펙 · 프로젝트 · 기술스택 CRUD (FR-21~25)

아직 AI 분석·격차 분석·로드맵·대시보드·일일 미션 등 2주차 이후 기능은 구현되지 않았다.

## 2. 아키텍처 구조

- **스택**: Java 17 · Servlet 6.0(Jakarta EE, Tomcat 10.1) · JSP · MySQL 8.0+ · Maven(war 패키징)
- **레이어링**: `controller`(Servlet) → `service`(비즈니스 로직) → `dao`(JDBC) → `dto`(순수 데이터 객체), View는 `WEB-INF/views/*.jsp`
- **인증**: 세션 기반. 로그인 성공 시 `HttpSession`에 `loginUser`(UserDto, 비밀번호 해시는 제거한 사본)를 저장. `SessionFilter`가 `/profile/*`, `/dashboard/*`를 가로채 미로그인 시 `/login`으로 리다이렉트.
- **비밀번호 저장**: 외부 라이브러리 없이 JDK 표준 API로 PBKDF2WithHmacSHA256(반복 12만회, salt 16byte)를 직접 구현(`PasswordUtil`). 저장 포맷은 `{iterations}:{saltBase64}:{hashBase64}`.
- **DB 커넥션**: `DBUtil`이 `DB_URL`/`DB_USER`/`DB_PASSWORD` 환경변수로만 접속 정보를 받는다. 세 값 중 하나라도 없으면 클래스 초기화 시점에 `ExceptionInInitializerError`로 즉시 실패 — 시크릿을 소스에 하드코딩하지 않기 위한 설계(NFR-3).
- **트랜잭션**: `ProfileService`가 스펙/프로젝트/스킬 추가·삭제 시 `USERS.profile_updated_at` 갱신을 같은 트랜잭션으로 묶는다(2주차 재분석 트리거 FR-37을 위한 사전 설계).
- **논리 삭제(Soft Delete)**: 모든 삭제는 `is_deleted = TRUE` UPDATE. 물리 삭제 없음.

## 3. DB 스키마 요약 (1주차 구현분 — 8개 테이블)

> 전체 설계(`docs/db-design.md`)는 36개 테이블을 정의하지만, 1주차 스키마(`sql/01_schema.sql`)는 회원/인증 + 프로필 CRUD에 필요한 8개만 만든다.

| 테이블 | 역할 | 주요 컬럼 |
| --- | --- | --- |
| `USERS` | 회원 계정 + 기본 프로필 | login_id(UK), password_hash, email, major, grade, interest_field, desired_job_id(FK→JOB), desired_job_status, profile_updated_at |
| `USER_SPECS` | 자격증·어학·수상 (1:N) | user_id(FK), spec_type, title, issuer, score, acquired_date |
| `USER_PROJECTS` | 프로젝트·경험 (1:N) | user_id(FK), title, description, tech_stack, start_date, end_date |
| `USER_SKILLS` | 보유 기술 스택 (1:N) | user_id(FK), skill_id(FK, 현재 항상 NULL), raw_input, similarity_score, proficiency |
| `SKILL` | 기술 마스터 (2주차 임베딩 매칭용, 현재는 빈 테이블) | skill_name(UK), category, embedding_vector |
| `JOB` | 직무 마스터 — 프로필의 희망직무 드롭다운에 사용 | job_name(UK), job_category, is_popular |
| `JOB_ALIAS` | 직무명 별칭 (2주차 On-demand 수집용, 현재 미사용) | job_id(FK), alias_name(UK) |
| `CERTIFICATION` | 자격증 마스터 (2주차 로드맵/D-day용, 현재 시드만 적재) | cert_name(UK), issuer, job_category, difficulty_level |

시드 데이터(`sql/02_seed.sql`): IT 직무 18개, IT 자격증 37개.

공통 규칙(모든 테이블): `created_at`/`updated_at`/`is_deleted` 컬럼, FK는 전부 `ON DELETE RESTRICT ON UPDATE CASCADE`(물리 연쇄 삭제 금지 방침과 일치), 문자셋 utf8mb4.

## 4. 구현된 기능 (엔드포인트 기준)

| 서블릿 | URL | 메서드 | 기능 |
| --- | --- | --- | --- |
| `RegisterServlet` | `/register` | GET/POST | 회원가입 폼 표시 · 처리 (아이디 중복 체크 → PBKDF2 해시 → INSERT) |
| `LoginServlet` | `/login` | GET/POST | 로그인 폼 표시 · 처리 (검증 성공 시 세션에 `loginUser` 저장, 실패 시 에러 메시지) |
| `LogoutServlet` | `/logout` | GET | 세션 무효화 후 `/login`으로 리다이렉트 |
| `SessionFilter` | `/profile/*`, `/dashboard/*` | (필터) | 미로그인 요청을 `/login`으로 차단 |
| `ProfileServlet` | `/profile` | GET/POST | 프로필(기본정보+스펙+프로젝트+스킬) 조회, 기본정보(전공·학년·관심분야·희망직무) 수정 |
| `ProfileSpecServlet` | `/profile/specs` | POST | 스펙(자격증/어학/수상) 추가·삭제 (`action=delete`) |
| `ProfileProjectServlet` | `/profile/projects` | POST | 프로젝트·경험 추가·삭제 |
| `ProfileSkillServlet` | `/profile/skills` | POST | 기술 스택 추가·삭제 (원문만 저장, 표준 스킬 매칭은 미구현) |

화면(JSP): `index.jsp`(랜딩), `WEB-INF/views/login.jsp`, `signup.jsp`, `profile.jsp`.

모든 삭제는 `WHERE id = ? AND user_id = ?` 조건으로 실행되어, 본인 소유가 아닌 레코드 id를 넘겨도 0행 갱신으로 조용히 무시된다 — 별도 권한 체크 로직 없이도 IDOR을 막는 방식.

## 6. 개선이 필요한 부분

- **회원가입 입력 검증 없음**: `RegisterServlet`이 `loginId`/`password`가 null이거나 빈 문자열이어도 그대로 `UserService.register()`에 넘긴다. 서버 사이드 필수값·길이·비밀번호 정책 검증이 없다.
- **아이디 중복 체크의 TOCTOU**: `existsByLoginId()` 확인 후 `insert()`를 별도 호출이라, 동시에 같은 아이디로 두 요청이 오면 둘 다 통과해 DB의 `UNIQUE(login_id)` 제약 위반 `SQLException`이 그대로 터진다. `RegisterServlet`은 이 예외를 `DuplicateLoginIdException`으로 못 잡고 500 에러로 흘려보낸다.
- **날짜 파싱 예외 미처리**: `ProfileSpecServlet`(`acquiredDate`), `ProfileProjectServlet`(`startDate`/`endDate`)에서 `LocalDate.parse()`가 형식이 잘못된 입력에 대해 `DateTimeParseException`을 던지는데 별도 catch가 없어 500 에러로 이어진다.
- **USER_SKILLS 중복 방지가 현재는 무력화됨**: `sql/01_schema.sql`의 `UNIQUE(user_id, skill_id)` 제약은 `skill_id`가 NULL일 때(현재 모든 입력이 그렇다) MySQL이 NULL을 서로 다른 값으로 취급해 제약이 걸리지 않는다. 즉 같은 `raw_input`을 여러 번 추가해도 막히지 않는다. 2주차 임베딩 매칭이 `skill_id`를 채우기 전까지는 애플리케이션 레벨에서 중복 체크가 필요할 수 있다.
- **CSRF 방어 없음**: `/profile/specs`, `/profile/projects`, `/profile/skills` 모두 세션 쿠키만으로 인증하는 순수 POST 폼이라 CSRF 토큰이 없다. 학습/과제 범위에서는 우선순위가 낮을 수 있으나 인지해 둘 필요는 있음.
- **테스트 코드 없음**: 단위/통합 테스트가 아직 없다.
- **web.xml은 최소 설정**: 서블릿은 전부 `@WebServlet` 애노테이션 기반이라 `web.xml`에는 welcome-file만 있다. 예외 발생 시 보여줄 에러 페이지(`<error-page>`) 설정도 아직 없어, 처리되지 않은 예외는 Tomcat 기본 스택트레이스 화면으로 노출된다.
