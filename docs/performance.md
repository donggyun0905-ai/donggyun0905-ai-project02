## 측정 방법

- **같은 코드, 같은 서버**: 같은 WAR를 로컬 Tomcat 10.1(8090)에 올렸다. 환경변수 `DB_POOL_DISABLED=true`만 켜고 끄며 비교했다.
  이 스위치는 풀 도입 전 방식대로 요청마다 `DriverManager`로 새 연결을 맺는다. 측정·장애 분리용이라 운영에서는 켜지 않는다(`DBUtil`).
- **DB**: 팀 공유 MySQL 8(원격). 연결 한 번에 TCP와 인증이 필요해서 비용이 크다. 풀이 효과를 보는 이유가 이것이다.
- **계정**: 실제 사용자와 비슷하게 꾸몄다. 희망 직무 백엔드 개발자, 보유 기술 4개, 격차 분석 1회, 로드맵 23단계.
- **반복**: 로그인한 뒤 두 화면을 번갈아 30번씩 요청했다. 처음 3번은 JSP 컴파일·캐시 워밍업이라 집계에서 뺐다.
  값은 브라우저 렌더링을 뺀 서버 응답 시간이다(HTML 전체를 받을 때까지).

다시 재려면 서버를 풀 켬/끔으로 각각 띄운 뒤 아래를 실행한다.

```bash
python scripts/measure_response.py http://localhost:8080 <아이디> <비밀번호> 30
```

## 남은 과제

- 풀을 켜도 대시보드는 1초가 넘는다. 화면 하나가 좌우 위젯까지 DB를 여러 번 부르고, 원격 DB라서 왕복 한 번이 수십 ms다.
  위젯 결과 캐시나 질의 묶기로 더 줄일 수 있다. 개발일지 10/5의 12번 항목과 같은 과제다.
