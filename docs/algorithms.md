## 1. 위상 정렬 (Kahn) + DFS 순환 검사

### 문제

로드맵 순서를 "필수냐 우대냐"와 티어로만 정했다. 그래서 **Spring이 Java보다 먼저** 나오는 순서가
만들어질 수 있었다. "왜 이 순서냐"에 답할 근거가 없었다.

### 왜 위상 정렬인가

"A를 하기 전에 B"는 **방향이 있는 그래프의 간선**이다. 이런 제약을 모두 지키는 일렬 순서를 찾는 것이
위상 정렬이고, 제약을 다 지키는 순서가 존재하려면 그래프에 **순환이 없어야(DAG)** 한다.

- *단순 정렬로는?* 선수관계는 전체 순서를 말하지 않는다. "Spring 전에 Java"는 SQL이 어디 들어갈지를
  말해 주지 않으므로 비교 함수를 만들 수 없다.
- *재귀로 하나씩 올리면?* 순환이 있으면 무한히 돈다. 순환 검사가 따로 필요하다.

### 동작 — Kahn 알고리즘

```
진입차수(indegree) = 그 노드가 기다려야 하는 선수 노드 수

1. 진입차수가 0인 노드를 전부 "준비 큐"에 넣는다
2. 큐에서 하나 꺼내 결과에 붙인다
3. 그 노드가 풀어 주는 노드들의 진입차수를 1 줄인다
4. 0이 된 노드를 큐에 넣는다
5. 큐가 빌 때까지 반복

결과 길이 < 노드 수  →  순환이 있다 (못 꺼낸 노드가 남는다)
```

**예시** — 입력 순위 `[Spring, SQL, Java]`, 간선 `Spring → Java`("Spring 전에 Java")

| 단계 | 진입차수 | 준비 큐 | 결과 |
| --- | --- | --- | --- |
| 시작 | Spring:1, SQL:0, Java:0 | SQL, Java | — |
| 1회 | | Java | SQL |
| 2회 | Spring:0 | Spring | SQL, Java |
| 3회 | | — | SQL, Java, Spring |

### 우리 코드에서 바꾼 것

**① 원래 순위를 최대한 유지한다.** 준비 큐에서 꺼낼 때 아무거나 꺼내면 매번 다른 순서가 나온다.
항상 "지금 꺼낼 수 있는 것 중 격차 분석 순위가 가장 앞선 것"을 꺼낸다. 위 예시에서 SQL이 Java보다
먼저 나온 것이 그 효과다 — 관계없는 기술은 자기 자리를 지킨다.

**② 순환이 있어도 멈추지 않는다.** 교과서는 "순환이면 오류"로 끝낸다. 우리는 정렬하지 못한 노드를
원래 순서로 뒤에 붙인다. 관리자 화면이 순환을 막지만 DB를 직접 고치면 생길 수 있고, 그때 로드맵
생성이 실패하면 안 된다(FR-111과 같은 태도).

**③ 라운드 밖 노드는 끌어오지 않는다.** 이번 라운드에 없는 선수 기술은 간선을 무시한다. 끌어오면
이번 라운드 구성이 통째로 바뀌고, 그 기술은 다음 라운드에 어차피 들어온다.

### 순환 검사는 DFS

관리자가 "A 전에 B"를 추가할 때, **B에서 간선을 따라가다 A에 닿으면** 순환이다.

```
wouldCreateCycle(A, B):
    A == B 이면 true          # 자기 자신이 가장 짧은 순환
    스택 = [B]
    visited = {}
    while 스택이 비지 않음:
        현재 = 스택.pop()
        현재를 visited에 넣지 못하면 continue   # 이미 본 곳
        현재 == A 이면 true
        현재의 선수들을 스택에 push
    return false
```

재귀가 아니라 **명시적 스택**을 쓴 이유: 관계가 길게 이어지면 스택이 넘칠 수 있다.
`visited`가 있는 이유: 기존 데이터에 이미 순환이 있어도 검사가 무한히 돌지 않아야 한다 — 망가진
데이터 위에서도 관리자가 다른 관계를 추가할 수 있어야 한다.

### 겪은 제약

`CHECK (skill_id <> prereq_skill_id)`를 걸려다 MySQL이 거부했다.

```
ERROR 3823 (HY000): Column 'skill_id' cannot be used in a check constraint
                    'ck_skill_prerequisite_not_self': needed in a foreign key
                    constraint 'fk_skill_prerequisite_skill' referential action
```

`ON UPDATE CASCADE`가 걸린 컬럼은 CHECK에 쓸 수 없다. FK 관례를 깨지 않고 자기 참조는 코드(DFS)에서 막았다.

```bash
mvn -o test -Dtest=SkillPrerequisiteDbTest        # DB 왕복 7개 (시드 그래프에 순환이 없는지도 본다)
```

## 2. 간격 반복 — SM-2

### 문제

복습 주기가 티어로만 고정이었다(입문 30일 · 핵심 60 · 심화 90 · 전문가 120). 같은 사람이 **쉬운 기술과
어려운 기술을 같은 주기로** 복습했다.

### 왜 SM-2인가

사람의 기억은 복습할수록 오래 간다(간격 효과). SM-2는 Anki·SuperMemo가 쓰는 공식으로, **사용자의
자기 평가**를 받아 항목마다 다음 간격을 늘리거나 줄인다. 공식이 짧아서 테스트하기도 쉽다.

- *고정 주기로는?* 사람마다·기술마다 잊는 속도가 다르다. 쉬운 것은 너무 자주, 어려운 것은 너무 늦게 나온다.
- *"틀린 것만 다시"로는?* 복습은 맞춤/틀림이 아니라 정도 문제다. 2단계(통과/실패)는 정보가 너무 적다.

### 동작

자기 평가 q(0~5)를 받아 **난이도 계수(EF, ease factor)**를 갱신하고, 그걸로 다음 간격을 곱한다.

```
EF' = EF + (0.1 - (5-q) × (0.08 + (5-q) × 0.02))

q=5 (쉬웠다)   → EF +0.10
q=4 (보통)     → EF  변화 없음
q=3 (어려웠다) → EF −0.14
q=2 (거의 잊음) → EF −0.32,  연속 기록 초기화

다음 간격 = 지난 간격 × EF'      (단, 첫 통과는 아래 참고)
```

**예시** — 입문 기술, EF 2.5에서 시작

| 복습 | 평가 | EF | 간격 |
| --- | --- | --- | --- |
| 1회 | 보통(q=4) | 2.50 | 30일 (티어 기본) |
| 2회 | 보통(q=4) | 2.50 | 30 × 2.5 = **75일** |
| 3회 | 어려움(q=3) | 2.36 | 75 × 2.36 = **177일** |
| 4회 | 거의 잊음(q=2) | 2.04 | **7일** (연속 기록 0으로) |

### 우리 코드에서 바꾼 것

**① 첫 간격을 1일·6일이 아니라 티어 기본 주기로 쓴다.** 원래 SM-2는 매일 카드를 보는 플래시카드용이라
I(1)=1일, I(2)=6일로 시작한다. 우리 복습은 **"기술 하나를 다시 정리해 글로 내는"** 일이라 하루 뒤에
또 하라고 하면 쓸 수 없다. 팀이 정한 티어 주기를 출발점으로 두고 두 번째부터 EF로 늘린다 —
덕분에 기존 동작과도 이어진다.

**② EF 상한 2.8을 추가했다.** 원래 공식에는 하한(1.3)만 있다. 상한이 없으면 "쉬웠다"를 몇 번 누르는
것만으로 간격이 몇 년이 된다.

**③ 못 외운 경우를 1일이 아니라 7일로 둔다.** 글로 내는 복습에 하루는 너무 짧다.

**④ 간격 자체를 1년으로 끊는다.** 넘기면 사실상 다시 안 보게 된다.

### 트랜잭션 경계

일정 갱신을 **점수 적립과 같은 트랜잭션** 안에서 한다. 점수는 들어갔는데 다음 일정이 안 잡히면
그 기술이 영원히 돌아오지 않는다.

### 직접 확인하기

```bash
mvn -o test -Dtest=SpacedRepetitionTest   # 공식 12개 (DB 없음)
```

관련 파일: `service/SpacedRepetition.java` · `service/RoadmapReviewService.java` ·
`dao/SkillReviewScheduleDao.java` · `sql/36_schema_skill_review_schedule.sql`

## 3. 0/1 배낭 문제 (동적 계획법)

### 문제

D-day 화면은 "며칠 남았다"만 보여 줬다. 남은 기간에 무엇부터 하면 좋은지는 사용자가 직접 골라야 했다.

### 왜 배낭 문제인가

문제를 이렇게 옮기면 그대로 배낭이 된다.

| 배낭 | 우리 문제 |
| --- | --- |
| 가방 용량 | D-day까지 남은 일수 |
| 물건 무게 | 그 단계를 끝내는 데 걸리는 일수 |
| 물건 가치 | 그 단계로 받는 점수 |

**0/1**인 이유: 한 단계는 쪼갤 수 없고(절반만 완료는 없다) 한 번만 담을 수 있다.
(쪼갤 수 있으면 분할 가능 배낭이고 그건 그리디로 최적이 나온다.)

### 왜 그리디가 아니라 DP인가

점수/일수(= 밀도)가 높은 것부터 담는 그리디는 **용량을 남긴다.**

```
후보: (6일 100점, 밀도 16.7) · (4일 60점, 밀도 15.0) · (3일 55점, 밀도 18.3)

남은 기간 6일
  그리디: 3일 55점(밀도 1등) → 남은 3일에 들어갈 것이 없다 → 55점
  DP    : 6일 100점 하나 → 100점                              ✅ 45점 차이

남은 기간 10일
  그리디: 3일 55점 → 6일 100점 → 남은 1일 → 155점
  DP    : 6일 + 4일 = 10일 → 160점                            ✅ 5점 차이

남은 기간 7일
  그리디: 3일 + 4일 = 115점
  DP    : 115점                                               (이 용량에서는 같다)
```

그리디는 **밀도 1등을 담고 남은 칸에 아무것도 안 들어가는** 경우에 무너진다. 용량이 작을수록 그
확률이 커진다(위에서 6일 때 45점 차이). DP는 "담지 않는 선택"도 표에 남기기 때문에 그걸 피한다.

> 주의: "점수가 높은 것부터" 담는 그리디는 또 다른 방식이고 실패하는 지점이 다르다. 위 7일 예시에서
> 그 그리디는 6일 100점을 담고 1일을 버려 100점에서 멈춘다. 어느 기준을 쓰든 **그리디는 0/1 배낭에서
> 최적을 보장하지 않는다** — 쪼갤 수 있는 분할 가능 배낭에서만 밀도 그리디가 최적이다.

`algorithms.html`의 3절에 **용량을 바꿔 표를 직접 채워 보는 데모**가 있다. 그리디 점수도 함께
보여 주므로 어느 용량에서 차이가 나는지 바로 확인할 수 있다.

### 동작

```
best[i][d] = 앞의 i개 물건만 쓰고 용량이 d일 때의 최대 가치

best[0][*] = 0
best[i][d] = max( best[i-1][d],                          # i번째를 안 담는다
                  best[i-1][d - w(i)] + v(i) )           # 담는다 (d >= w(i)일 때만)

답 = best[n][용량]
```

**무엇을 담았는지 되살리기** — 표를 거꾸로 따라간다.

```
d = 용량
for i = n ... 1:
    best[i][d] != best[i-1][d] 이면 i번째를 담은 것 → d -= w(i)
```

시간·공간 복잡도는 O(n × 용량). 1차원 배열로 줄일 수도 있지만, 되살리기가 필요해 2차원을 썼다.

### 우리 코드에서 바꾼 것

**① 잠긴 단계는 후보에서 뺀다.** 로드맵은 앞 티어를 끝내야 다음이 열리는 계단식 잠금이다. 잠긴 단계를
추천하면 **"할 수 없는 일"을 알려 주는 셈**이다. 복습처럼 사다리에 없는 티어는 언제든 할 수 있다.

**② 표 크기에 상한을 둘 곳이 두 군데다.**
- 계획 기간 1년 — 넘는 D-day에 계획은 의미가 없고 표만 커진다.
- 후보 60개 — 로드맵이 길면 미완료가 수백 개가 된다. **밀도 높은 것부터 자르므로** 좋은 후보는 남는다.
  (상한을 걸면 최적해를 놓칠 수 있다는 것은 인지하고 채택했다.)

**③ 무게를 규칙 테이블로 뺐다.** 소요 일수는 추정이라 `SCORING_RULE`의 `EFFORT_DAYS_*`로 둬서
관리자가 조정할 수 있다. 입문 3 · 핵심 7 · 심화 5 · 전문가 4 · 자격증 21 · 프로젝트 10 · 복습 1.

**④ 화면 순서는 짧게 끝나는 것부터.** DP가 고른 집합은 순서가 없다. "오늘 뭐부터"로 읽히게 정렬한다.

### 직접 확인하기

```bash
mvn -o test -Dtest=DdayPlannerTest       # 배낭 14개 (DB 없음)
mvn -o test -Dtest=DdayPlanServiceTest   # 후보 고르기(잠금) 4개
```

## 4. RRF — 순위 융합 (Reciprocal Rank Fusion)

### 문제

기술명 매칭은 "정확 일치 → 접두·부분 → 편집거리(0.75) → 임베딩(0.75)"을 **차례로** 시도하고 각 단계가
자기 임계값을 못 넘으면 거기서 끝이다. 그래서 **두 신호가 모두 "조금 비슷하다"고 말하는 입력**을 놓쳤다.

### 왜 점수를 더하지 않고 RRF인가

편집거리 유사도와 코사인 유사도는 **분포가 전혀 다르다.**

| 쌍 | 편집거리 유사도 | 코사인 |
| --- | --- | --- |
| 완전 무관한 두 기술 | 0.1~0.3 | **0.5~0.7** (문장 임베딩은 바닥이 높다) |
| 같은 기술, 표기 차이 | 0.6~0.9 | 0.68 |

그대로 더하면 코사인이 항상 이긴다. 정규화하려면 각 분포를 알아야 하는데, 입력에 따라 달라진다.

**RRF는 점수가 아니라 순위만 쓴다.**

```
score(d) = Σ  1 / (k + rank_i(d))         k = 60 (정보 검색 관례값)
          i∈목록
```

k가 작으면 1등에 너무 쏠리고, 크면 순위 차이가 뭉개진다. 척도가 다른 신호를 **정규화 없이** 합칠 수
있는 것이 이 방법의 핵심 장점이다.

### 동작 예시

```
글자 순위:  1. Spring   2. Spring Boot   3. SQL
의미 순위:  1. Java     2. Spring Boot   3. Kotlin

Spring       = 1/(60+1)                = 0.01639
Spring Boot  = 1/(60+2) + 1/(60+2)     = 0.03226   ← 양쪽에서 2등이지만 1등
Java         = 1/(60+1)                = 0.01639
```

**한쪽 1등보다 양쪽 2등이 이긴다** — 이게 RRF를 쓰는 이유다.

### 우리 코드에서 바꾼 것

**① 기존 동작을 전혀 바꾸지 않는다.** 종속(임베딩 → 편집거리)이 뭐라도 찾으면 그대로 돌려주고,
**못 찾았을 때만** RRF가 돈다. 없던 결과만 더하고 있던 결과는 안 건드린다. 기존 매칭 테스트가
하나도 깨지지 않은 것이 그 증거다.

**② "합의" 조건을 추가했다.** RRF 1등이 **두 순위에서 모두 상위 3등 안**에 있어야 받는다.
한쪽만 좋아하는 후보가 바로 알려진 오탐이다 — 코드에 적혀 있는 실측값이 근거다.

| 쌍 | 코사인 | 뜻 |
| --- | --- | --- |
| Java ↔ JavaScript (**다른 기술**) | 0.805 | 임베딩만 보면 1등인데 글자로는 전혀 아니다 |
| 자바 ↔ Java (**같은 기술**) | 0.680 | 오히려 더 낮다 |
| "웹 서버 구축 기술" ↔ "백엔드 서버 개발 능력" | 0.783 | 진짜 비슷한 문장이 오탐 쌍보다 낮다 |

두 신호가 같이 가리킬 때만 받으면 이 종류를 막는다. 그래서 각 신호의 개별 바닥을 종속보다 낮춰도
된다(글자 0.45 · 의미 0.60) — **합의가 확신을 대신한다.**

**③ 글자 유사도는 편집거리와 2-gram Dice 중 높은 쪽.** 편집거리만 쓰면 앞에 글자가 붙은 쌍
("myspringboot" vs "springboot")에 약하고, 2-gram만 쓰면 짧은 이름의 오타에 약하다.

```
2-gram Dice = 2 × |공통 2글자 묶음| / (|A의 묶음| + |B의 묶음|)
"abc" → {ab, bc},  "abd" → {ab, bd}  →  2×1/(2+2) = 0.5
```

**④ 화면에 남기는 점수는 두 신호의 평균.** RRF 내부 값은 0.03 같은 수라 "유사도"로 쓸 수 없고,
`SKILL.similarity_score`는 `DECIMAL(5,4)`라 0~1이어야 한다.

### 한계 (코드에도 적어 뒀다)

표기 체계가 아예 다른 입력("리액트" vs "React.js")은 글자 순위가 전혀 못 잡아 **합의가 성립하지 않는다.**
그건 `SKILL_ALIAS` 사전이 맡는 영역이고, 억지로 받으면 오탐이 늘어난다.

```bash
mvn -o test -Dtest=RankFusionTest          # RRF 융합 8개
mvn -o test -Dtest=HybridSkillMatcherTest  # 경계·글자 유사도 10개
```

## 5. 자카드 유사도 + 동시 출현 (협업 필터링)

### 문제

"같은 직무를 준비하는 사람들이 **실제로** 무엇을 더 익혔는지"를 보여 줄 수 없었다.
`JOB_REQUIRED_SKILL`은 "직무가 요구하는 것"이라 다른 정보다.

### 왜 단순 빈도가 아니라 자카드로 가중하나

인기 기술은 **아무 상관 없는 사람도** 갖고 있다. 단순 빈도로 세면 늘 같은 기술이 1등이다.
나와 기술 구성이 비슷한 사람이 가진 기술에 더 무게를 주면 "나와 비슷한 길을 걷는 사람들의 다음 걸음"에
가까워진다.

```
자카드(A, B) = |A ∩ B| / |A ∪ B|

추천 점수(기술 X) = Σ  자카드(내 기술, 그 사람 기술)
                  그 사람이 X를 가진 또래
```

### 합집합으로 나누는 것이 왜 중요한가

교집합만 세면 **기술을 아주 많이 등록한 사람**이 늘 "비슷한 사람"이 된다.

```
내 기술 = {Java, Spring}

또래 A = {Java, Spring, SQL}            교집합 2, 합집합 3  →  자카드 0.67
또래 B = {Java, Spring, +8개 더}        교집합 2, 합집합 10 →  자카드 0.20
```

A가 "비슷한 길"이고 B는 "아무거나 많이 넣은 사람"이다. 합집합이 그 차이를 잡는다(테스트로 고정했다).

### 우리 코드에서 바꾼 것

**① 겹치는 기술이 하나도 없는 사람은 아예 제외한다.** 자카드 0인 사람의 기술은 추천 근거가 아니다.

**② 개인정보 — 집계만 내보낸다.** 누가 가졌는지는 돌려주지 않고 화면에는 "N명 중 M명"만 나간다.
**표본이 모자라면 아무것도 보여 주지 않는다.**

| 기준 | 값 | 이유 |
| --- | --- | --- |
| 최소 또래 수 | 3명 | 2~3명으로 "많이 익혔다"고 말하면 틀린 말이다 |
| 기술별 최소 보유자 | 2명 | 한 사람의 선택은 추천 근거가 못 된다 |

사람이 적을 때는 추천 자체가 **특정 개인의 프로필을 드러낼 수 있다.** 데이터 인사이트의 또래 비교와
같은 태도다.

**③ 조회에서 빼는 대상**: 본인 · 논리 삭제 · 탈퇴 신청 · 테스트 계정(`is_test`) · `skill_id IS NULL`.

**④ 동점이면 `skillId` 순으로 고정.** 호출마다 추천 순서가 바뀌면 사용자가 혼란스럽다.

### 직접 확인하기

```bash
mvn -o test -Dtest=SkillCooccurrenceServiceTest  # 자카드·순위 13개 (DB 없음)
mvn -o test -Dtest=SkillCooccurrenceDaoTest      # 제외 조건이 실제로 걸리는지 2개
```

관련 파일: `service/SkillCooccurrenceService.java` · `dao/SkillCooccurrenceDao.java`

## 6. EWMA + z-score (시계열 이상 감지)

### 문제

트렌드가 "이번 달 언급 비율 높은 순"이면 **원래 항상 높은 기술**(Java처럼 늘 30%대)이 늘 1등이라
"요즘 뜨는 기술"을 알 수 없다. 알고 싶은 것은 절대값이 아니라 **평소보다 얼마나 튀었는지**다.

### 왜 단순 평균이 아니라 EWMA인가

단순 평균은 1년 전 값과 지난달 값을 **같게** 본다. 채용 시장은 최근이 더 중요하다.
EWMA(지수가중이동평균)는 최근에 큰 가중을 줘서 "평소"에 더 가깝다.

```
mean_t = α · x_t + (1-α) · mean_(t-1)
var_t  = α · (x_t - mean_(t-1))² + (1-α) · var_(t-1)

z = (이번 달 값 - 과거 기준선) / 과거 표준편차
```

α가 클수록 최근에 민감하다. 우리는 **0.4** — 쌓인 달이 많지 않아(수집 시작 2026-09) 과거에 눌리지
않게 잡은 값이고, 더 크면 기준선이 지난달 하나에 휘둘린다.

### 동작 예시

```
언급 비율(%)  1.0  1.1  0.9  1.0  →  이번 달 5.0

과거 EWMA 기준선 ≈ 1.0,  표준편차 ≈ 0.2 (바닥값)
z = (5.0 - 1.0) / 0.2 = 20       →  급상승 ✅  "평소의 5배"

Java 같은 기술: 30.0  31.0  29.5  30.5  →  이번 달 31.0
기준선 ≈ 30.4,  z ≈ 0.9          →  급상승 아님 ✅  (절대값은 1등이어도)
```

### 우리 코드에서 바꾼 것

**① 이번 달 값은 기준선에 넣지 않는다.** 넣으면 자기 자신 때문에 기준선이 올라가 z가 작아진다
(테스트로 고정했다).

**② 배지를 아껴 붙이려고 조건 넷을 뒀다.**

| 조건 | 값 | 이유 |
| --- | --- | --- |
| z 임계값 | ≥ 2.0 | 정규분포라면 상위 약 2% |
| 비율 바닥 | ≥ 1% | 0.1%→0.4%도 z는 크지만 공고 몇 건 차이다 |
| 최소 과거 | 3달 | 수집을 막 시작했으면 "평소"를 모른다 |
| 표준편차 바닥 | 0.2 | 완전히 평평했던 기술은 작은 변화에 z가 무한대로 튄다 |

**③ 위로 튄 것만 본다.** 아래로 떨어진 달도 z의 절댓값은 크다.

**④ 빠진 달(null)은 0건으로 보고 계산을 멈추지 않는다.**

### 직접 확인하기

```bash
mvn -o test -Dtest=SpikeDetectorTest   # 12개 (DB 없음)
```

관련 파일: `service/SpikeDetector.java` · `service/InsightService.java`

## 7. 토큰 버킷 + 서킷 브레이커 (안정성 패턴)

### 문제

지금까지는 **실패한 뒤에 기다렸다.** Groq 한도를 넘으면 429를 받고 재시도 정책이 20·40·60초를 기다리고,
깃허브 403이나 고용24 장애에서는 사용자마다·요청마다 같은 실패를 반복하며 타임아웃만큼 멈췄다.

두 장치는 **보내기 전에** 막아서, FR-111·112가 말하는 "캐시·안내 문구로 대체"가 즉시 일어나게 한다.

### 토큰 버킷 — 호출 횟수 제한

```
버킷에 토큰을 일정 속도로 채운다 (capacity까지만)
호출마다 토큰 하나를 쓴다
없으면 거절한다

남은 토큰 = min(capacity, 남은 토큰 + 경과 시간 × 초당 채우는 수)
```

**창(window)을 끊어 세는 방식과 다른 점**: "분당 30회"를 창으로 세면 창이 바뀌는 순간 60회가 몰릴 수
있다(경계 문제). 토큰 버킷은 연속적으로 채워서 그 문제가 없고, 평소에 안 쓰면 쌓인 토큰으로
잠깐 몰리는 호출을 받아 준다.

적용: Groq 분당 30회, 한꺼번에 10개까지(화면 하나가 추천 이유를 여러 개 만든다).

**시계가 뒤로 가도 토큰을 깎지 않는다** — 시간 동기화로 음수가 되면 영원히 막힌다.

### 서킷 브레이커 — 계속 실패하면 끊는다

```
        연속 실패 누적                시간 경과
CLOSED ──────────────▶ OPEN ──────────────▶ HALF_OPEN
  ▲                      ▲                      │
  │        실패          │         성공         │
  └──────────────────────┴──────────────────────┘

CLOSED    평소. 전부 통과
OPEN      끊긴 상태. 전부 거절 (바로 대체 동작으로)
HALF_OPEN 한 번만 떠본다. 성공이면 CLOSED, 실패면 다시 OPEN
```

**반만 열어 한 번 떠보는 단계가 필요한 이유**: 바로 CLOSED로 돌리면 아직 죽어 있는 상대에게 모든
요청이 동시에 몰려 또 한꺼번에 실패한다. HALF_OPEN에서는 떠보는 호출 **하나만** 통과시킨다.

| 대상 | 임계값 | 차단 시간 | 비고 |
| --- | --- | --- | --- |
| Groq | 연속 5회 | 1분 | 형식 오류(422)는 실패로 세지 않는다 — 상대는 살아 있고 우리 프롬프트 문제다 |
| 트렌드 수집 | 연속 3회 | 10분 | **출처별로 하나씩** (깃허브·HN·dev.to·Lobsters·GeekNews) |
| 고용24 | 연속 3회 | 5분 | 응답은 왔지만 API가 오류 코드를 준 경우(키 만료·한도)도 실패로 센다 |

트렌드를 출처별로 나눈 이유: 깃허브가 403을 주는 동안 **다른 출처 수집까지 멈추면 안 되고**, 반대로
깃허브에만 같은 실패를 매번 반복할 이유도 없다. 끊긴 출처는 그 회차에서 조용히 건너뛴다.

### 두 장치의 역할 차이

| | 토큰 버킷 | 서킷 브레이커 |
| --- | --- | --- |
| 막는 이유 | **우리가** 너무 많이 보낸다 | **상대가** 받지 못한다 |
| 상태 | 남은 토큰 수 | 연속 실패 수 + 끊긴 시각 |
| 풀리는 조건 | 시간이 지나 토큰이 채워짐 | 차단 시간 경과 후 떠본 호출이 성공 |

### 우리 코드에서 바꾼 것 — 설계를 한 번 되돌렸다

처음에 호출 한도를 `static`으로 뒀더니 **테스트 수백 개가 같은 버킷을 비워** 뒤쪽 테스트가 429로 깨졌다.
운영은 JVM 전체 공유가 맞지만(한도는 API 키 단위) **인스턴스 필드로 바꿔** 기본값만 공유 객체로 두고
테스트가 자기 것을 끼우게 했다. 설정을 바꾼 사본도 같은 한도·서킷을 이어 쓴다 — 같은 API 키라
따로 세면 안 된다.

**시간을 주입받게 만든 이유**: `sleep` 없이 테스트하려면 시간을 앞으로 돌려야 한다. 테스트가 느려지면
전체 1,000여 개가 같이 느려진다. 프로젝트의 `AppClock`은 시뮬레이션용 **날짜** 기반이라 밀리초 단위에
맞지 않아 `LongSupplier`를 따로 받는다.

### 직접 확인하기

```bash
mvn -o test -Dtest=TokenBucketTest       # 8개, sleep 없음
mvn -o test -Dtest=CircuitBreakerTest    # 9개, sleep 없음
```

관련 파일: `util/TokenBucket.java` · `util/CircuitBreaker.java` · `util/GroqLlmClient.java` ·
`service/TrendSourceClient.java` · `service/work24/Work24Client.java`

## 8. FULLTEXT 역색인 — ngram 파서

### 문제

스펙 아카이브에 **검색이 아예 없었다.** 제목·본문을 `LIKE '%키워드%'`로 찾으면 앞에 와일드카드가 있어
**인덱스를 전혀 타지 못하고**, 본문이 `TEXT`라 글이 쌓일수록 전수 조회가 된다.

### 왜 기본 FULLTEXT 파서로는 안 되나

기본 파서는 **공백으로 단어를 자른다.** 한국어는 조사가 붙고 복합어를 띄어 쓰지 않는 경우가 많아,
"스프링 부트"를 한 덩이로만 보고 **"프링"으로는 못 찾는다.**

**ngram 파서**는 글자 N개씩 겹쳐 쪼개 넣는다(`ngram_token_size`, 기본 2).

```
"스프링 부트"  →  스프, 프링, 링, 부트   (2글자 묶음)
검색 "프링"    →  토큰 "프링"이 있으니 걸린다 ✅
```

### 적용 전에 실측했다

공유 DB: **MySQL 9.7.2 · ngram 플러그인 ACTIVE · `ngram_token_size = 2`**

| 검색어 | 결과 |
| --- | --- |
| `스프링` | 스프링 부트 · 스프링 프레임워크 ✅ |
| `프링` (중간 글자) | 둘 다 ✅ |
| `Spring` (영문) | Spring Boot ✅ |
| `스프링 부트` (자연어 모드) | 점수순 — 부트 1.06, 프레임워크 0.46 ✅ |
| `자` (한 글자) | **0건** — token_size가 2라 인덱스에 토큰이 없다 |

`EXPLAIN`으로 인덱스 사용까지 확인했다.

```
-> Full-text index search on TECH_ARTICLE using ft_tech_article_text (title = '스프링')
```

### 우리 코드에서 바꾼 것

**① 한 글자만 LIKE 폴백.** 인덱스를 못 타지만 "검색은 되는데 한 글자만 안 된다"가 더 이상하다.
`token_size`를 1로 낮추는 선택도 있었지만 **인덱스가 급격히 커지고 흔한 글자가 전부 걸려** 느려진다.

**② 사용자 입력을 BOOLEAN MODE 검색식으로 바꾼다.** 낱말마다 `+`와 따옴표를 붙여 "모두 포함"으로 만든다.

```
"스프링 부트"  →  +"스프링" +"부트"
```

입력에 든 연산자(`+ - * ~ < > ( ) " @`)는 **전부 지운다** — 안 지우면 "C++"의 `+`가 연산자로 해석돼
구문 오류나 엉뚱한 결과가 된다. `#`은 연산자가 아니라 남긴다(**"C#"은 실제 기술명**이다).
"C++"처럼 연산자를 지우면 한 글자가 되는 입력은 자연히 LIKE 폴백이 받는다.

**③ 관리자 회원 검색에는 넣지 않았다.** `USERS`는 **쓰기가 잦은 표**라 FULLTEXT 인덱스의 유지 비용이
붙는다. 관리자 검색은 호출이 드물고 대상 행도 적어 LIKE로 충분하다 — 가장 바쁜 표에 인덱스를 더할
이유가 없다. **알고리즘을 적용하지 않는 것도 판단이다.**

## 복잡도 정리

| 알고리즘 | 시간 | 공간 | 우리 규모에서의 실제 비용 |
| --- | --- | --- | --- |
| 위상 정렬 | O(V + E) | O(V + E) | 라운드 기술 5개 — 무시할 수준 |
| DFS 순환 검사 | O(V + E) | O(V) | 관계 수십 개 — 무시할 수준 |
| SM-2 | O(1) | O(1) | 복습 한 건당 산술 몇 번 |
| 0/1 배낭 | O(n × 용량) | O(n × 용량) | 60 × 365 = 21,900칸 (상한) |
| RRF | O(목록 길이 합) | O(후보 수) | 후보 10개 × 2목록 |
| 자카드 가중 | O(또래 수 × 기술 수) | O(기술 수) | 또래 수십 명 × 기술 10여 개 |
| EWMA + z | O(달 수) | O(1) | 4달 |
| FULLTEXT | 역색인 조회 | 인덱스 저장 | DB가 처리 — `EXPLAIN`으로 확인 |

가장 비싼 것이 배낭인데, 상한을 둬서 최악에도 2만여 칸이다. 화면 한 번에 한 번만 돈다.

## 공부 순서 추천

처음 보는 사람이라면 이 순서가 읽기 쉽다.

1. **2번 SM-2** — 식 하나, 상태 세 개. 알고리즘이 코드가 되는 가장 작은 예시.
2. **5번 자카드** — 집합 연산 두 개. "왜 합집합으로 나누나"가 핵심.
3. **6번 EWMA + z-score** — 점화식 두 줄. "왜 이번 값을 기준선에서 빼나"가 핵심.
4. **1번 위상 정렬** — 그래프 입문. 진입차수만 이해하면 끝.
5. **3번 배낭** — DP 입문. 표를 손으로 한 번 채워 보는 것이 가장 빠르다.
6. **7번 안정성 패턴** — 알고리즘보다 상태 기계. 실무에서 가장 자주 쓴다.
7. **4번 RRF** — "척도가 다른 점수를 어떻게 합치나"라는 실전 문제.
8. **8번 FULLTEXT** — DB가 해 주는 일이라 원리(역색인·토크나이저)만 알면 된다.

각 절의 "직접 확인하기"에 적힌 테스트를 돌리고 **값을 바꿔 깨뜨려 보는 것**이 가장 빠른 공부다.
예를 들어 `SpikeDetector.MIN_Z`를 1.0으로 낮추면 어떤 테스트가 깨지는지 보면, 그 임계값이 무엇을
막고 있었는지 알 수 있다.
