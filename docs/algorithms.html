01 기술 선수관계 그래프 — 위상 정렬(Kahn) + DFS 순환 검사

그래프 O(V+E) SkillPrerequisiteService

문제

로드맵 순서를 "필수냐 우대냐"와 티어로만 정했습니다. 그래서 Spring이 Java보다 먼저 나오는 순서가 만들어질 수 있었고, "왜 이 순서냐"에 답할 근거가 없었습니다.

왜 위상 정렬인가

"A를 하기 전에 B"는 방향 그래프의 간선입니다. 이런 제약을 모두 지키는 일렬 순서를 찾는 것이 위상 정렬이고, 그 순서가 존재하려면 순환이 없어야(DAG) 합니다. 단순 정렬로는 안 됩니다 — "Spring 전에 Java"는 SQL이 어디 들어갈지를 말해 주지 않으므로 비교 함수를 만들 수 없습니다.

동작 — Kahn 알고리즘

진입차수(indegree) = 그 노드가 기다려야 하는 선수 노드 수

1. 진입차수 0인 노드를 전부 준비 큐에 넣는다
2. 큐에서 하나 꺼내 결과에 붙인다
3. 그 노드가 풀어 주는 노드들의 진입차수를 1 줄인다
4. 0이 된 노드를 큐에 넣는다 — 큐가 빌 때까지 반복

결과 길이 < 노드 수  →  순환이 있다 (못 꺼낸 노드가 남는다)

입력 순위 [Spring, SQL, Java], 간선 Spring → Java일 때:

단계진입차수준비 큐결과
시작Spring:1, SQL:0, Java:0SQL, Java—
1회JavaSQL
2회Spring:0SpringSQL, Java
3회—SQL, Java, Spring

우리 코드에서 바꾼 것

  1. 원래 순위를 최대한 유지합니다. 준비 큐에서 아무거나 꺼내면 매번 다른 순서가 나옵니다. 항상 "지금 꺼낼 수 있는 것 중 격차 분석 순위가 가장 앞선 것"을 꺼냅니다 — 위 예시에서 SQL이 Java보다 먼저 나온 것이 그 효과입니다. 관계없는 기술은 자기 자리를 지킵니다.
  2. 순환이 있어도 멈추지 않습니다. 교과서는 "순환이면 오류"로 끝냅니다. 우리는 정렬하지 못한 노드를 원래 순서로 뒤에 붙입니다 — 관리자 화면이 막지만 DB를 직접 고치면 생길 수 있고, 그때 로드맵 생성이 실패하면 안 됩니다(FR-111과 같은 태도).
  3. 라운드 밖 노드는 끌어오지 않습니다. 끌어오면 이번 라운드 구성이 통째로 바뀌고, 그 기술은 다음 라운드에 어차피 들어옵니다.

순환 검사는 DFS

관리자가 "A 전에 B"를 추가할 때, B에서 간선을 따라가다 A에 닿으면 순환입니다.

wouldCreateCycle(A, B):
    A == B 이면 true              # 자기 자신이 가장 짧은 순환
    스택 = [B];  visited = {}
    while 스택이 비지 않음:
        현재 = 스택.pop()
        현재를 visited에 넣지 못하면 continue    # 이미 본 곳
        현재 == A 이면 true
        현재의 선수들을 스택에 push
    return false

재귀가 아니라 명시적 스택을 쓴 이유는 관계가 길게 이어지면 스택이 넘칠 수 있기 때문입니다. visited가 있는 이유는 기존 데이터에 이미 순환이 있어도 검사가 무한히 돌지 않아야 하기 때문입니다 — 망가진 데이터 위에서도 관리자가 다른 관계를 추가할 수 있어야 합니다.

DB 제약에서 막힌 것

CHECK (skill_id <> prereq_skill_id)를 걸려다 MySQL이 거부했습니다 — ERROR 3823: Column 'skill_id' cannot be used in a check constraint: needed in a foreign key constraint referential action. ON UPDATE CASCADE가 걸린 컬럼은 CHECK에 쓸 수 없습니다. FK 관례를 깨지 않고, 자기 참조는 DFS가 잡는 가장 짧은 순환으로 코드에서 막았습니다.

02 간격 반복 복습 — SM-2

수치 모델 O(1) SpacedRepetition

문제

복습 주기가 티어로만 고정이었습니다(입문 30일 · 핵심 60 · 심화 90 · 전문가 120). 같은 사람이 쉬운 기술과 어려운 기술을 같은 주기로 복습했습니다.

왜 SM-2인가

사람의 기억은 복습할수록 오래 갑니다(간격 효과). SM-2는 Anki·SuperMemo가 쓰는 공식으로, 사용자의 자기 평가를 받아 항목마다 다음 간격을 늘리거나 줄입니다. 고정 주기로는 사람마다·기술마다 잊는 속도가 다른 것을 반영할 수 없고, 통과/실패 2단계로는 정보가 너무 적습니다.

동작

EF' = EF + (0.1 − (5−q) × (0.08 + (5−q) × 0.02))

q=5 쉬웠다  →  EF +0.10
q=4 보통    →  EF 변화 없음
q=3 어려웠다 →  EF −0.14
q=2 거의 잊음 →  EF −0.32, 연속 기록 초기화

다음 간격 = 지난 간격 × EF'

입문 기술, EF 2.5에서 시작했을 때:

복습평가EF간격
1회보통 (q=4)2.5030일 티어 기본
2회보통 (q=4)2.5030 × 2.5 = 75일
3회어려움 (q=3)2.3675 × 2.36 = 177일
4회거의 잊음 (q=2)2.047일 연속 기록 0

우리 코드에서 바꾼 것

첫 간격을 1일·6일이 아니라 티어 기본 주기로

원래 SM-2는 매일 카드를 보는 플래시카드용이라 I(1)=1일, I(2)=6일로 시작합니다. 우리 복습은 "기술 하나를 다시 정리해 글로 내는" 일이라 하루 뒤에 또 하라고 하면 쓸 수 없습니다. 팀이 정한 티어 주기를 출발점으로 두고 두 번째부터 EF로 늘립니다 — 덕분에 기존 동작과도 이어집니다.

  • EF 상한 2.8을 추가 — 원래 공식에는 하한(1.3)만 있습니다. 상한이 없으면 "쉬웠다"를 몇 번 누르는 것만으로 간격이 몇 년이 됩니다.
  • 못 외운 경우는 1일이 아니라 7일 — 글로 내는 복습에 하루는 너무 짧습니다.
  • 간격 자체를 1년으로 끊음 — 넘기면 사실상 다시 안 보게 됩니다.
  • 일정 갱신을 점수 적립과 같은 트랜잭션에서 — 점수는 들어갔는데 다음 일정이 안 잡히면 그 기술이 영원히 돌아오지 않습니다.

03 D-day 계획 — 0/1 배낭 문제 (동적 계획법)

동적 계획법 O(n × 용량) DdayPlanner

문제

D-day 화면은 "며칠 남았다"만 보여 줬습니다. 남은 기간에 무엇부터 하면 좋은지는 사용자가 직접 골라야 했습니다.

배낭 문제우리 문제
가방 용량D-day까지 남은 일수
물건 무게그 단계를 끝내는 데 걸리는 일수
물건 가치그 단계로 받는 점수 (StepPointCalculator)

0/1인 이유: 한 단계는 쪼갤 수 없고(절반만 완료는 없다) 한 번만 담을 수 있습니다. 쪼갤 수 있으면 분할 가능 배낭이고 그건 그리디로 최적이 나옵니다.

왜 그리디가 아니라 DP인가

점수/일수(밀도)가 높은 것부터 담는 그리디는 밀도 1등을 담고 남은 칸에 아무것도 안 들어가는 경우에 무너집니다. 후보가 (6일 100점)·(4일 60점)·(3일 55점)일 때 남은 기간이 6일이면 그리디는 밀도 1등인 3일 55점을 담고 남은 3일을 버려 55점에서 멈추지만, DP는 6일 100점 하나로 100점을 찾습니다. 용량이 작을수록 그 확률이 커집니다. DP는 "담지 않는 선택"도 표에 남기기 때문에 그걸 피합니다.

어느 기준을 쓰든 그리디는 0/1 배낭에서 최적을 보장하지 않습니다 — 쪼갤 수 있는 분할 가능 배낭에서만 밀도 그리디가 최적입니다. 아래 데모에서 용량을 바꿔 보면 차이가 나는 지점을 바로 볼 수 있습니다.

동작

best[i][d] = 앞의 i개 물건만 쓰고 용량이 d일 때의 최대 가치

best[0][*] = 0
best[i][d] = max( best[i−1][d],           i번째를 안 담는다
               best[i−1][d − w(i)] + v(i) )  담는다 (d ≥ w(i)일 때만)

답 = best[n][용량]

표를 직접 채워 보기

물건: (6일 100점) · (4일 60점) · (3일 55점)

무엇을 담았는지 되살리기

d = 용량
for i = n ... 1:
    best[i][d] != best[i-1][d] 이면 i번째를 담은 것 → d -= w(i)

1차원 배열로 공간을 줄일 수도 있지만, 되살리기가 필요해 2차원을 썼습니다.

우리 코드에서 바꾼 것

잠긴 단계는 후보에서 뺍니다

로드맵은 앞 티어를 끝내야 다음이 열리는 계단식 잠금입니다. 잠긴 단계를 추천하면 "할 수 없는 일"을 알려 주는 셈입니다. 복습처럼 사다리에 없는 티어는 언제든 할 수 있습니다.

  • 표 크기 상한 두 군데 — 계획 기간 1년(넘는 D-day에 계획은 의미가 없다), 후보 60개(로드맵이 길면 미완료가 수백 개 — 밀도 높은 것부터 자르므로 좋은 후보는 남는다). 상한 때문에 최적해를 놓칠 수 있다는 것은 인지하고 채택했습니다.
  • 무게를 규칙 테이블로 — 소요 일수는 추정이라 SCORING_RULE의 EFFORT_DAYS_*로 둬서 관리자가 조정할 수 있습니다. 입문 3 · 핵심 7 · 심화 5 · 전문가 4 · 자격증 21 · 프로젝트 10 · 복습 1.
  • 화면 순서는 짧게 끝나는 것부터 — DP가 고른 집합은 순서가 없습니다. "오늘 뭐부터"로 읽히게 정렬합니다.

04 하이브리드 기술명 매칭 — RRF 순위 융합

정보 검색 O(목록 길이 합) RankFusion · HybridSkillMatcher

문제

기술명 매칭은 "정확 일치 → 접두·부분 → 편집거리(0.75) → 임베딩(0.75)"을 차례로 시도하고 각 단계가 자기 임계값을 못 넘으면 거기서 끝입니다. 그래서 두 신호가 모두 "조금 비슷하다"고 말하는 입력을 놓쳤습니다.

왜 점수를 더하지 않고 RRF인가

편집거리 유사도와 코사인 유사도는 분포가 전혀 다릅니다. 완전히 무관한 두 기술도 문장 임베딩에서는 코사인이 0.5~0.7이 나옵니다(바닥이 높음). 그대로 더하면 코사인이 항상 이기고, 정규화하려면 각 분포를 알아야 하는데 입력에 따라 달라집니다. RRF는 점수가 아니라 순위만 씁니다.

score(d) = Σi∈목록   1 / (k + ranki(d))    k = 60 (정보 검색 관례값)

k가 작으면 1등에 너무 쏠리고, 크면 순위 차이가 뭉개진다

동작 예시:

글자 순위:  1. Spring   2. Spring Boot   3. SQL
의미 순위:  1. Java     2. Spring Boot   3. Kotlin

Spring       = 1/(60+1)              = 0.01639
Spring Boot  = 1/(60+2) + 1/(60+2)   = 0.03226   ← 양쪽에서 2등이지만 1등
Java         = 1/(60+1)              = 0.01639

한쪽 1등보다 양쪽 2등이 이깁니다 — 이게 RRF를 쓰는 이유입니다.

우리 코드에서 바꾼 것

기존 동작을 전혀 바꾸지 않습니다

종속(임베딩 → 편집거리)이 뭐라도 찾으면 그대로 돌려주고, 못 찾았을 때만 RRF가 돕니다. 없던 결과만 더하고 있던 결과는 안 건드립니다. 기존 매칭 테스트가 하나도 깨지지 않은 것이 그 증거입니다.

"합의" 조건 — RRF 1등이 두 순위에서 모두 상위 3등 안에 있어야 받습니다. 한쪽만 좋아하는 후보가 바로 알려진 오탐입니다. 코드에 적혀 있는 실측값이 근거입니다.

쌍코사인뜻
Java ↔ JavaScript (다른 기술)0.805임베딩만 보면 1등인데 글자로는 전혀 아니다
자바 ↔ Java (같은 기술)0.680오히려 더 낮다
"웹 서버 구축 기술" ↔ "백엔드 서버 개발 능력"0.783진짜 비슷한 문장이 오탐 쌍보다 낮다

두 신호가 같이 가리킬 때만 받으면 이 종류를 막습니다. 그래서 각 신호의 개별 바닥을 종속보다 낮춰도 됩니다(글자 0.45 · 의미 0.60) — 합의가 확신을 대신합니다.

  • 글자 유사도는 편집거리와 2-gram Dice 중 높은 쪽 — 편집거리만 쓰면 앞에 글자가 붙은 쌍("myspringboot" vs "springboot")에 약하고, 2-gram만 쓰면 짧은 이름의 오타에 약합니다. 2×|공통 묶음| / (|A| + |B|), 예: "abc"{ab,bc}와 "abd"{ab,bd} → 2×1/(2+2)=0.5
  • 화면에 남기는 점수는 두 신호의 평균 — RRF 내부 값은 0.03 같은 수라 "유사도"로 쓸 수 없고, SKILL.similarity_score는 DECIMAL(5,4)라 0~1이어야 합니다.

표기 체계가 아예 다른 입력("리액트" vs "React.js")은 글자 순위가 전혀 못 잡아 합의가 성립하지 않습니다. 그건 SKILL_ALIAS 사전이 맡는 영역이고, 억지로 받으면 오탐이 늘어납니다. 임베딩 모델이 없는 PC에서는 합의할 두 번째 신호가 없어 이 단계를 건너뜁니다.

05 함께 익힌 기술 추천 — 자카드 유사도 + 동시 출현

협업 필터링 O(또래 수 × 기술 수) SkillCooccurrenceService

문제

"같은 직무를 준비하는 사람들이 실제로 무엇을 더 익혔는지"를 보여 줄 수 없었습니다. JOB_REQUIRED_SKILL은 "직무가 요구하는 것"이라 다른 정보입니다.

왜 단순 빈도가 아니라 자카드로 가중하나

인기 기술은 아무 상관 없는 사람도 갖고 있습니다. 단순 빈도로 세면 늘 같은 기술이 1등입니다. 나와 기술 구성이 비슷한 사람이 가진 기술에 더 무게를 주면 "나와 비슷한 길을 걷는 사람들의 다음 걸음"에 가까워집니다.

자카드(A, B) = |A ∩ B| / |A ∪ B|

추천 점수(기술 X) = ΣX를 가진 또래 자카드(내 기술, 그 사람 기술)

합집합으로 나누는 것이 왜 중요한가

교집합만 세면 기술을 아주 많이 등록한 사람이 늘 "비슷한 사람"이 됩니다.

내 기술 = {Java, Spring}교집합합집합자카드
또래 A = {Java, Spring, SQL}230.67
또래 B = {Java, Spring, +8개 더}2100.20

A가 "비슷한 길"이고 B는 "아무거나 많이 넣은 사람"입니다. 합집합이 그 차이를 잡습니다 (테스트로 고정했습니다).

우리 코드에서 바꾼 것

개인정보 — 집계만 내보냅니다

누가 가졌는지는 돌려주지 않고 화면에는 "N명 중 M명"만 나갑니다. 표본이 모자라면 아무것도 보여 주지 않습니다 — 또래 3명 미만이거나 그 기술을 가진 사람이 2명 미만이면 추천하지 않습니다. 2~3명으로 "많이 익혔다"고 말하면 틀린 말이고, 사람이 적을 때는 추천 자체가 특정 개인의 프로필을 드러낼 수 있습니다. 데이터 인사이트의 또래 비교와 같은 태도입니다.

  • 겹치는 기술이 하나도 없는 사람은 제외 — 자카드 0인 사람의 기술은 추천 근거가 아닙니다.
  • 조회에서 빼는 대상: 본인 · 논리 삭제 · 탈퇴 신청 · 테스트 계정(is_test) · skill_id IS NULL. 제외가 실제로 걸리는지 DB 테스트로 확인했습니다 — SQL 컬럼 이름 오타는 런타임에만 드러납니다.
  • 동점이면 skillId 순으로 고정 — 호출마다 추천 순서가 바뀌면 사용자가 혼란스럽습니다.

06 급상승 기술 감지 — EWMA + z-score

시계열 이상 감지 O(달 수) SpikeDetector

문제

트렌드가 "이번 달 언급 비율 높은 순"이면 원래 항상 높은 기술(Java처럼 늘 30%대)이 늘 1등이라 "요즘 뜨는 기술"을 알 수 없습니다. 알고 싶은 것은 절대값이 아니라 평소보다 얼마나 튀었는지입니다.

왜 단순 평균이 아니라 EWMA인가

단순 평균은 1년 전 값과 지난달 값을 같게 봅니다. 채용 시장은 최근이 더 중요합니다. EWMA(지수가중이동평균)는 최근에 큰 가중을 줘서 "평소"에 더 가깝습니다.

meant = α · xt + (1−α) · meant−1
vart  = α · (xt − meant−1)² + (1−α) · vart−1

z = (이번 달 값 − 과거 기준선) / 과거 표준편차

α = 0.4 — 쌓인 달이 많지 않아(수집 시작 2026-09) 과거에 눌리지 않게 잡은 값.
더 크면 기준선이 지난달 하나에 휘둘린다.

동작 예시

언급 비율(%)  1.0  1.1  0.9  1.0  →  이번 달 5.0
과거 EWMA 기준선 ≈ 1.0, 표준편차 ≈ 0.2 (바닥값)
z = (5.0 - 1.0) / 0.2 = 20        →  급상승 ✅  "평소의 5배"

Java 같은 기술: 30.0  31.0  29.5  30.5  →  이번 달 31.0
기준선 ≈ 30.4,  z ≈ 0.9           →  급상승 아님 ✅  (절대값은 1등이어도)

우리 코드에서 바꾼 것

이번 달 값은 기준선에 넣지 않습니다

넣으면 자기 자신 때문에 기준선이 올라가 z가 작아집니다 — 테스트로 고정했습니다.

배지를 아껴 붙이려고 조건 넷을 뒀습니다.

조건값이유
z 임계값≥ 2.0정규분포라면 상위 약 2%
비율 바닥≥ 1%0.1%→0.4%도 z는 크지만 공고 몇 건 차이다
최소 과거3달수집을 막 시작했으면 "평소"를 모른다
표준편차 바닥0.2완전히 평평했던 기술은 작은 변화에 z가 무한대로 튄다
  • 위로 튄 것만 봅니다 — 아래로 떨어진 달도 z의 절댓값은 큽니다.
  • 빠진 달(null)은 0건으로 보고 계산을 멈추지 않습니다.

07 토큰 버킷 + 서킷 브레이커 (안정성 패턴)

안정성 패턴 O(1) TokenBucket · CircuitBreaker

문제

지금까지는 실패한 뒤에 기다렸습니다. Groq 한도를 넘으면 429를 받고 재시도 정책이 20·40·60초를 기다리고, 깃허브 403이나 고용24 장애에서는 사용자마다·요청마다 같은 실패를 반복하며 타임아웃만큼 멈췄습니다. 두 장치는 보내기 전에 막아서 FR-111·112가 말하는 "캐시·안내 문구로 대체"가 즉시 일어나게 합니다.

토큰 버킷 — 호출 횟수 제한

남은 토큰 = min(capacity, 남은 토큰 + 경과 시간 × 초당 채우는 수)

호출마다 토큰 하나를 쓴다 — 없으면 거절
창(window)을 끊어 세는 방식과 다른 점

"분당 30회"를 창으로 세면 창이 바뀌는 순간 60회가 몰릴 수 있습니다(경계 문제). 토큰 버킷은 연속적으로 채워서 그 문제가 없고, 평소에 안 쓰면 쌓인 토큰으로 잠깐 몰리는 호출을 받아 줍니다.

적용: Groq 분당 30회, 한꺼번에 10개까지(화면 하나가 추천 이유를 여러 개 만듭니다). 시계가 뒤로 가도 토큰을 깎지 않습니다 — 시간 동기화로 음수가 되면 영원히 막힙니다.

서킷 브레이커 — 계속 실패하면 끊는다

        연속 실패 누적                시간 경과
CLOSED ──────────────▶ OPEN ──────────────▶ HALF_OPEN
  ▲                      ▲                      │
  │        실패          │         성공         │
  └──────────────────────┴──────────────────────┘

CLOSED     평소. 전부 통과
OPEN       끊긴 상태. 전부 거절 (바로 대체 동작으로)
HALF_OPEN  한 번만 떠본다. 성공이면 CLOSED, 실패면 다시 OPEN
반만 열어 한 번 떠보는 단계가 필요한 이유

바로 CLOSED로 돌리면 아직 죽어 있는 상대에게 모든 요청이 동시에 몰려 또 한꺼번에 실패합니다. HALF_OPEN에서는 떠보는 호출 하나만 통과시킵니다.

대상임계값차단비고
Groq연속 5회1분형식 오류(422)는 실패로 세지 않는다 — 상대는 살아 있고 우리 프롬프트 문제다
트렌드 수집연속 3회10분출처별로 하나씩 (깃허브·HN·dev.to·Lobsters·GeekNews)
고용24연속 3회5분응답은 왔지만 API가 오류 코드를 준 경우(키 만료·한도)도 실패로 센다

트렌드를 출처별로 나눈 이유: 깃허브가 403을 주는 동안 다른 출처 수집까지 멈추면 안 되고, 반대로 깃허브에만 같은 실패를 매번 반복할 이유도 없습니다. 끊긴 출처는 그 회차에서 조용히 건너뜁니다.

두 장치의 역할 차이

토큰 버킷서킷 브레이커
막는 이유우리가 너무 많이 보낸다상대가 받지 못한다
상태남은 토큰 수연속 실패 수 + 끊긴 시각
풀리는 조건시간이 지나 토큰이 채워짐차단 시간 경과 후 떠본 호출이 성공
설계를 한 번 되돌렸습니다

처음에 호출 한도를 static으로 뒀더니 테스트 수백 개가 같은 버킷을 비워 뒤쪽 테스트가 429로 깨졌습니다. 운영은 JVM 전체 공유가 맞지만(한도는 API 키 단위) 인스턴스 필드로 바꿔 기본값만 공유 객체로 두고 테스트가 자기 것을 끼우게 했습니다. 설정을 바꾼 사본도 같은 한도·서킷을 이어 씁니다 — 같은 API 키라 따로 세면 안 됩니다.

시간을 주입받게 만든 이유: sleep 없이 테스트하려면 시간을 앞으로 돌려야 합니다. 테스트가 느려지면 전체 1,000여 개가 같이 느려집니다. 프로젝트의 AppClock은 시뮬레이션용 날짜 기반이라 밀리초 단위에 맞지 않아 LongSupplier를 따로 받습니다.

08 스펙 아카이브 검색 — FULLTEXT 역색인 (ngram)

검색 엔진 역색인 TechArticleDao

문제

스펙 아카이브에 검색이 아예 없었습니다. 제목·본문을 LIKE '%키워드%'로 찾으면 앞에 와일드카드가 있어 인덱스를 전혀 타지 못하고, 본문이 TEXT라 글이 쌓일수록 전수 조회가 됩니다.

왜 기본 FULLTEXT 파서로는 안 되나

기본 파서는 공백으로 단어를 자릅니다. 한국어는 조사가 붙고 복합어를 띄어 쓰지 않는 경우가 많아, "스프링 부트"를 한 덩이로만 보고 "프링"으로는 못 찾습니다.

ngram 파서 — 글자 N개씩 겹쳐 쪼개 넣는다 (ngram_token_size, 기본 2)

"스프링 부트"  →  스프, 프링, 부트
검색 "프링"    →  토큰 "프링"이 있으니 걸린다 ✅

적용 전에 실측했습니다

공유 DB: MySQL 9.7.2 · ngram 플러그인 ACTIVE · ngram_token_size = 2

검색어결과
스프링스프링 부트 · 스프링 프레임워크 ✅
프링 (중간 글자)둘 다 ✅
Spring (영문)Spring Boot ✅
스프링 부트 (자연어 모드)점수순 — 부트 1.06, 프레임워크 0.46 ✅
자 (한 글자)0건 — token_size가 2라 인덱스에 토큰이 없다

EXPLAIN으로 인덱스 사용까지 확인했습니다.

-> Full-text index search on TECH_ARTICLE using ft_tech_article_text (title = '스프링')

우리 코드에서 바꾼 것

  • 한 글자만 LIKE 폴백 — 인덱스를 못 타지만 "검색은 되는데 한 글자만 안 된다"가 더 이상합니다. token_size를 1로 낮추는 선택도 있었지만 인덱스가 급격히 커지고 흔한 글자가 전부 걸려 느려집니다.
  • 사용자 입력을 BOOLEAN MODE 검색식으로 — 낱말마다 +와 따옴표를 붙여 "모두 포함"으로 만듭니다("스프링 부트" → +"스프링" +"부트"). 입력에 든 연산자(+ - * ~ < > ( ) " @)는 전부 지웁니다 — 안 지우면 "C++"의 +가 연산자로 해석돼 구문 오류나 엉뚱한 결과가 됩니다. #은 연산자가 아니라 남깁니다("C#"은 실제 기술명). "C++"처럼 연산자를 지우면 한 글자가 되는 입력은 자연히 LIKE 폴백이 받습니다.
관리자 회원 검색에는 넣지 않았습니다

USERS는 쓰기가 잦은 표라 FULLTEXT 인덱스의 유지 비용이 붙습니다. 관리자 검색은 호출이 드물고 대상 행도 적어 LIKE로 충분합니다 — 가장 바쁜 표에 인덱스를 더할 이유가 없습니다. 알고리즘을 적용하지 않는 것도 판단입니다.

공부 순서 추천

처음 보는 사람이라면 이 순서가 읽기 쉽습니다.

  1. 2번 SM-2 — 식 하나, 상태 세 개. 알고리즘이 코드가 되는 가장 작은 예시.
  2. 5번 자카드 — 집합 연산 두 개. "왜 합집합으로 나누나"가 핵심.
  3. 6번 EWMA + z-score — 점화식 두 줄. "왜 이번 값을 기준선에서 빼나"가 핵심.
  4. 1번 위상 정렬 — 그래프 입문. 진입차수만 이해하면 끝.
  5. 3번 배낭 — DP 입문. 위의 표를 손으로 한 번 채워 보는 것이 가장 빠릅니다.
  6. 7번 안정성 패턴 — 알고리즘보다 상태 기계. 실무에서 가장 자주 씁니다.
  7. 4번 RRF — "척도가 다른 점수를 어떻게 합치나"라는 실전 문제.
  8. 8번 FULLTEXT — DB가 해 주는 일이라 원리(역색인·토크나이저)만 알면 됩니다.
가장 빠른 공부법

각 절의 "직접 확인하기" 테스트를 돌리고 값을 바꿔 깨뜨려 보세요. 예를 들어 SpikeDetector.MIN_Z를 1.0으로 낮추면 어떤 테스트가 깨지는지 보면, 그 임계값이 무엇을 막고 있었는지 알 수 있습니다.
